# بررسی علت «گرفتن دسترسی کامل توسط کاربر جدید»

**موضوع:** در «سیستم ← کاربران» (و «تنظیمات ← نقش‌ها و دسترسی‌ها») وقتی کاربر جدیدی ساخته و چند دسترسی به او داده می‌شود،
کاربر دسترسی کامل (مثل مدیر) می‌گیرد یا دسترسی‌هایی خارج از آنچه تعیین شده به دست می‌آورد.

**نتیجهٔ بررسی:** مشکل یک باگ واحد نیست؛ یک **لایهٔ قدیمیِ نقش (Role) در کنار لایهٔ جدید RBAC** وجود دارد و آن لایهٔ قدیمی
با «حدس زدن از روی نام نقش» پر می‌شود. نام نقش‌های فارسی (هرچیزی که «مدیر» داشته باشد) ⇒ کاربر «Admin» می‌شود و
«Admin» در سراسر برنامه یعنی دسترسی کامل — کاملاً بی‌ربط به تیک‌های دسترسی که مدیر داده است.

## ۱) علت اصلی — نقش Admin از «نام» نقش RBAC حدس زده می‌شود ⚠️ بحرانی

**فایل:** `inventory/src/Inventory.Api/Services/Core/AuthService.cs` — متد `DeriveLegacyRole` (خط ۲۲۳)

```csharp
if (rbacRoleNames.Any(n => n.Equals("Admin", …) || n.Contains("مدیر") || n.Contains("ادمین")))
    return "Admin";                                   // ← هر نقش با «مدیر» در نام ⇒ مدیر کل
if (rbacRoleNames.Any(n => n.Equals("Referrer", …) || n.Contains("معرف")))
    return "Referrer";
if (rbacRoleNames.Count > 0)
    return "Operator";                                // ← هر نقش دیگر ⇒ اپراتور
```

این متد در `SaveUserAsync` (خط ۲۴۴–۲۴۷) صدا زده می‌شود و نتیجه‌اش **مستقیماً در ستون `Users.Role` ذخیره و در JWT می‌نشیند**
(claim نوع `Role`). پس:

| نقش RBAC انتخاب‌شده برای کاربر | ستون `Users.Role` | نتیجهٔ واقعی |
|---|---|---|
| «مدیر فروش» (حتی با ۲–۳ دسترسی) | `Admin` | **دسترسی کامل به همه‌چیز** |
| «مدیر انبار»، «مدیر پروژه»، «مدیر مالی»، «کارشناس مدیر»… | `Admin` | **دسترسی کامل به همه‌چیز** |
| «فروشنده»، «انباردار»، «کارشناس»… | `Operator` | عبور از دروازهٔ همهٔ کنترلرهای عملیاتی (بند ۶) |
| «معرف» | `Referrer` | فقط پنل معرف |

نکتهٔ کلیدی: تشابه نام دو نقش «مدیر فروش» و «فروشنده» است، ولی نتیجه‌شان زمین تا آسمان فرق دارد — و همین توضیح می‌دهد
چرا مشکل «خیلی وقتا» و غیرقابل‌پیش‌بینی رخ می‌دهد.

### چرا Admin یعنی دسترسی کامل؟

* **کلاینت:** ۲۱۷ مورد `Auth.IsAdmin` در صفحات (منوها، دکمه‌ها، تب‌ها، فرم‌ها) — مثل `CanSeeSettings` در منو
  (`NavMenu.razor:805`) و گاردهای صفحات.
* **سرور:** ۲۴ مورد `User.IsInRole("Admin")` + ۵ مورد `ClaimTypes.Role == "Admin"` + ۳ اندپوینت `[Authorize(Roles="Admin")]`
  + پالیسی «RadisHrAccess» در `Program.cs:364`.
  فهرست مهم‌ها:
  * منابع انسانی: `HrPayController:28`، `HrPerfController:28`، `HrTimeController:31`، `AttendanceController:64,664`، `LeaveRequestsController:54,67`، `HrCoreController:778`
  * دارایی‌های IT: `ItVaultController:37` (گاوصندوق رمزها 🔐)، `IpamController:34`، `ServersController:46`، `WorkOrdersController:30`
  * گزارش‌ساز: `ReportStudioController:63`، `RsAccessService:60`، `RsRowSecurity:68`
  * سیستم: `AuditLogsController:24` (لاگ عملیات)، `ArchiveController:162`، `CompanyContextController:19`، `NotificationsController:330`، `HttpsController:37`
  * نرم‌افزار تیم توسعه: `DevTeamController:23`
* **ماژول رادیس‌اچ‌آر:** در زمان ورود، کاربر `Admin` همهٔ نقش‌های legacy ماژول
  (`hr, ceo, guard, hse, warehouse, production, finance, accounting`) را یک‌جا می‌گیرد (`AuthService.cs:150`).
* **فال‌بک سراسری:** اگر روزی نقش‌های RBAC کاربر حذف/غیرفعال شود، `EffectivePermissions.GetAsync` (خط ۶۳) و
  `RbacControllerBase.HasAsync` (خط ۲۹) برای نقش قدیمی `Admin` **همهٔ مجوزها را true می‌کنند**.

### همین منطق در کلاینت هم تکرار شده
`Users.razor:589` → `IsAdminRole(n) => n == "Admin" || n.Contains("مدیر") || n.Contains("ادمین")`
(برای پنهان‌کردن نقش‌های مدیر از اپراتور). یعنی رفتار فرم کاربر هم به نام نقش گره خورده، نه به دسترسی‌های واقعی.

### تست سریع روی دیتابیس (کاربرانی که اشتباهی مدیر شده‌اند)

```sql
SELECT u.Id, u.Username, u.FirstName, u.LastName, u.Role, r.Name AS RbacRoleName
FROM Users u
JOIN UserRoles ur ON ur.UserId = u.Id
JOIN Roles r      ON r.Id = ur.RoleId
WHERE u.Role = 'Admin' AND r.Name <> 'Admin'
ORDER BY u.Id;
```

هر ردیفی که برمی‌گردد، کاربری است که به‌خاطر نام نقش، «مدیر کل» شده است. خودِ `admin` پیش‌فرض در این لیست نیست
(چون نقش RBAC ندارد و از مسیر legacy ساخته شده — `DbInitializer.cs:314`).

## ۲) کاربر جدیدِ بدون نقش RBAC هم «مدیر کامل» می‌شود ⚠️

دو طرف این قضیه هم‌دست داده‌اند:

* **کلاینت:** `Users.razor:681` — فرم «کاربر جدید» پیش‌فرض `Role = "Admin"` می‌گذارد.
* **کلاینت:** `Users.razor:741` — انتخاب «حداقل یک نقش» فقط وقتی اجباری می‌شود که `allRoles.Count > 0` باشد.
  اگر فهرست نقش‌ها لود نشود (خطای شبکه/۵۰۰؛ در `Load()` داخل `catch` فقط یک Toast می‌دهد و `allRoles = new()` می‌شود)
  کاربر **بدون هیچ نقشی** ذخیره می‌شود.
* **سرور:** `AuthService.cs:244` — `if (dto.RoleIds is { Count: > 0 } …)` یعنی اگر RoleIds خالی/تهی بیاید، اصلاً
  `DeriveLegacyRole` اجرا نمی‌شود و همان `Role = "Admin"` ارسالی کلاینت ذخیره می‌شود، با صفر نقش RBAC.

نتیجه: `Users.Role = 'Admin'` و `UserRoles` خالی ⇒ در ورود بعدی، مسیر «کاربر قدیمی بدون نقش RBAC» (خط ۱۰۳) **همهٔ
پرمیشن‌ها** را به کاربر می‌دهد و به‌علاوه `IsLegacyAdminAsync` برایش true است ⇒ در همهٔ چک‌های RBAC هم عبور می‌کند.

## ۳) سرور «نام نقش» را چک می‌کند، نه «دسترسی‌های نقش» (مسیر ارتقای دسترسی) ⚠️

در `SaveUserAsync` بررسی «اپراتور نمی‌تواند کاربر مدیر بسازد» روی نتیجهٔ *حدسِ نام* است، نه روی RoleIds:

```csharp
if (!callerIsAdmin && dto.Role == "Admin")   // خط ۲۵۶ — فقط بعد از DeriveLegacyRole
    throw new InvalidOperationException("اپراتور نمی‌تواند کاربر با نقش «مدیر» ایجاد کند…");
```

پس اگر نقش Admin موجود در سیستم (مثلاً در «تنظیمات ← نقش‌ها و دسترسی‌ها» نامش عوض شود به `SystemOwner`) دیگر
«مدیر» در نامش نیست؛ در این حالت:

* `DeriveLegacyRole` ⇒ `Operator` (پس چک بالا رد نمی‌شود)،
* ولی خودِ نقش RBAC، **همهٔ** پرمیشن‌ها را دارد ⇒ کاربر عملاً همهٔ دسترسی‌های RBAC (شامل Settings و SystemUsers) را می‌گیرد.

یعنی قفل «اپراتور نتواند نقش قوی بدهد» قابل دور زدن است، چون معیارش نام است نه محتوای دسترسی‌ها.

## ۴) هر کاربر لاگین‌شده می‌تواند نقش‌ها و دسترسی‌ها را تغییر دهد ⚠️ (تنظیمات ← نقش‌ها و دسترسی‌ها)

* `RolesController` (`Controllers/System/RolesController.cs:10`) هیچ گیت نقشی ندارد — فقط `[Authorize]` پیش‌فرض پروژه
  (`DefaultAuthorizeConvention` = «هر کس لاگین کرده»). یعنی **GET/POST/PUT/DELETE روی `/api/roles`** برای هر کاربر
  وارد‌شده باز است.
* `PermissionsController` (`PermissionsController.cs:8`) هم همین‌طور: فهرست کامل ماژول/اکشن‌ها را به هر کاربر می‌دهد.
* در کلاینت، صفحهٔ `/settings/roles` (`Roles.razor`) **هیچ گاردی ندارد** (هیچ `Auth.IsAdmin` در آن نیست)؛ فقط لینکِ
  منویش از صفحهٔ تنظیمات (که Admin است) دیده می‌شود. با زدن آدرس به‌صورت مستقیم، صفحه باز می‌شود.
* باگ جانبی: `Roles.razor` هم برخلاف بقیهٔ صفحات تنظیمات، هدر `Authorization` را روی `HttpClient` ست نمی‌کند و
  صرفاً به‌خاطر این‌که آن `HttpClient` بین صفحات مشترک است و صفحه‌های دیگر (مثل «کاربران»/«تنظیمات») هدر را ست
  کرده‌اند کار می‌کند؛ در یک جلسهٔ تازه (رفرش مستقیم روی همین صفحه) پاسخ ۴۰۱ می‌گیرد و پیام خطا نشان می‌دهد.

**نتیجه:** یک کاربر معمولی می‌تواند نقش خودش (یا هر نقش دیگری) را ویرایش کند و همهٔ تیک‌ها را بزند، یا نقش جدید بسازد
⇒ دقیقاً همان «دسترسی‌های اشتباهی که داده می‌شود».

## ۵) نقشِ غیرفعال (IsActive=false) همچنان دسترسی می‌دهد

در `LoginAsync` (`AuthService.cs:82`) شناسهٔ نقش‌ها **بدون فیلتر `IsActive`** خوانده می‌شود و سپس پرمیشن‌های همان‌ها
به توکن می‌رود (خط ۹۰–۹۶)، در حالی که همهٔ مسیرهای دیگر ( `EffectivePermissions:51`، `RbacControllerBase:31`،
`WorkOrdersController.HasAsync`) فقط نقش‌های **فعال** را معیار می‌گیرند. چون چند کنترلر (HrPay/HrPerf/HrTime و پالیسی
`RadisHrAccess`) پرمیشن را از **claim توکن** می‌خوانند، دسترسی نقش خاموش‌شده واقعاً اعمال می‌شود.
همچنین `RolesController.Delete` هیچ پاک‌سازی روی `UserRoles`/`RolePermissions` ندارد (رابطهٔ `UserRole→Role` در
`AppDbContext.cs:834` حتی به‌عنوان FK پیکربندی نشده) ⇒ رکوردهای یتیم که در محاسبهٔ ورود شمرده می‌شوند.

## ۶) ریشهٔ ساختاری — «هر نقش ⇒ Operator» و کنترلرهای بدون چک پرمیشن

* `DeriveLegacyRole` هر نقش دیگر را `Operator` می‌کند (خط ۲۳۲).
* `ApiControllerBase` فقط `[Authorize(Roles = "Admin,Operator")]` است (`ApiControllerBase.cs:12`).
* این کنترلرها **هیچ** چک `Module.Action` ندارند (شمارش `HasAsync`/`ForbiddenUnless` = صفر):
  `Catalog/Products`، `Catalog/Orders`(Sales)، `Catalog/Parties`، `Catalog/GoodsIssues`، `Catalog/Stock`، `Catalog/Warehouses`،
  `Catalog/Units`، `Catalog/Categories`، `Finance/Expenses`، `Reports`، `Repairs`، `System/Settings`.
* فقط این‌ها چک دقیق دارند: `OfficeMachinesController` (۱۲ مورد)، `RbacControllerBase` (۸ مورد) و کنترلرهایی که
  از آن ارث می‌برند (مثل `WorkOrdersController`) و کنترلرهای IT Assets که با `IEffectivePermissions` کار می‌کنند.

⇒ کاربری که فقط نقش «فروشنده» با مجوز «مشاهدهٔ کالا» گرفته، از منو چیزی نمی‌بیند، ولی با فراخوانی مستقیم API می‌تواند
کالا/طرف حساب/فاکتور/هزینه بسازد، ویرایش و حذف کند. (پنهان‌کردن منو = امنیت نیست.)

## جمع‌بندی: چرا «خیلی وقتا» رخ می‌دهد؟

۱. اگر در نام نقش کلمهٔ «مدیر»/«ادمین» باشد ⇒ **Admin کامل** (بی‌ربط به تیک‌ها).
۲. اگر فهرست نقش‌ها هنگام ساخت کاربر لود نشود ⇒ **Admin کامل** با پیش‌فرض فرم.
۳. اگر نام آن نقشی که Admin را Admin می‌کند عوض شود ⇒ **همهٔ پرمیشن‌های RBAC**.
۴. اگر نقش غیرفعال شود ⇒ دسترسی‌ها در توکن می‌ماند.
۵. اگر نقش «معمولی» باشد ⇒ **Operator** و دروازهٔ همهٔ کنترلرهای عملیاتی باز.

# اصلاحات اعمال‌شده (همین حالا روی کد)

## ۱) `AuthService.DeriveLegacyRole` — حذف حدس از روی نام ✅
`inventory/src/Inventory.Api/Services/Core/AuthService.cs`

* سطح «مدیر کل» **فقط** با نقش دقیقاً `Admin` داده می‌شود. نام‌هایی مثل «مدیر فروش»، «مدیر انبار»، «مدیر پروژه» دیگر
  کاربر را مدیر کل نمی‌کنند و سطحشان «اپراتور» می‌شود.
* نام‌های فارسی «معرف…» عمداً همچنان سطح `Referrer` می‌دهند (بدترین حالتش «کاهش» دسترسی است، نه اعطای دسترسی اضافه).

## ۲) خودترمیمی داده‌های موجود هنگام ورود ✅ (خودکار)
متد جدید `SelfHealLegacyRoleAsync` در زمان هر ورود، ستون `Users.Role` را از روی نقش‌های RBAC **فعال** کاربر
بازمحاسبه می‌کند؛ یعنی کاربرانی که تا امروز اشتباهاً «مدیر کل» شده‌اند، با اولین ورود بعد از به‌روزرسانی به سطح درست
برمی‌گردند — بدون نیاز به ویرایش دستی.

* کاربران قدیمی بدون نقش RBAC (مثل `admin` پیش‌فرض) دست‌نخورده می‌مانند.
* **محافظ:** آخرین مدیر فعال سیستم هرگز خودکار پایین آورده نمی‌شود (جلوگیری از قفل‌شدن مدیریت).
* هر اصلاح در **«تنظیمات ← لاگ عملیات»** با ماژول `Auth` و اکشن `SelfHealRole` ثبت می‌شود
  (متن: «اصلاح خودکار سطح دسترسی: Admin ← Operator …»).

## ۳) جلوگیری از ساخت کاربر بدون نقش / با پیش‌فرض Admin ✅
* **سرور (`SaveUserAsync`):** کاربر جدید بدون نقش RBAC اصلاً ثبت نمی‌شود (پیام: «حداقل یک نقش برای کاربر جدید انتخاب کنید»).
  اگر نقش‌های ارسالی معتبر نباشند هم خطای روشن داده می‌شود.
* **پاک‌کردن همهٔ نقش‌ها هم بسته شد:** اگر کسی (از طریق API) همهٔ نقش‌های یک کاربر موجود را خالی کند، کاربر به
  «سطح قدیمی» برمی‌گشت که همان دسترسی گسترده است؛ حالا رد می‌شود و برای قطع دسترسی باید کاربر «غیرفعال» شود.
* فقط نقش‌های **موجود** در جدول `UserRoles` ذخیره می‌شوند (رکورد یتیمِ نقش حذف‌شده ساخته نمی‌شود).
* **UI (`Users.razor`):** پیش‌فرض نقش قدیمیِ کاربر جدید از `Admin` به `Operator` تغییر کرد؛ و اگر فهرست نقش‌ها لود نشود،
  دکمهٔ ذخیره کار نمی‌کند و پیام خطا نشان داده می‌شود (قبلاً کاربر بی‌نقش = مدیر کل ذخیره می‌شد).

## ۴) هشدار در فرم کاربر ✅
اگر مدیری در حال ویرایش کاربری باشد که الان «مدیر کل» است و نقشی غیر از `Admin` انتخاب کند، در فرم هشدار داده می‌شود
که «دسترسی کامل از این کاربر گرفته می‌شود» تا اشتباهاً مدیر واقعی پایین آورده نشود.

# کارهایی که پس از انتشار باید انجام دهید

1. **بررسی کنید چه کسانی اصلاح شده‌اند:** «تنظیمات ← لاگ عملیات» → فیلتر ماژول `Auth` / اکشن `SelfHealRole`.
2. **نقش‌های مدیریتی سفارشی:** اگر نقش واقعیِ مدیر دارید که نامش دقیقاً `Admin` نیست (مثل «مدیر کل»، «مدیر سیستم»)،
   یا نام آن نقش را دقیقاً `Admin` بگذارید، یا در فرم کاربر علاوه بر آن، نقش `Admin` را هم انتخاب کنید؛ در غیر این صورت
   آن کاربران از ورود بعدی در سطح «اپراتور» خواهند بود (دسترسی‌های RBAC خودشان سر جایشان است، ولی سطح «مدیر کل»
   و بخش‌هایی مثل تنظیمات/لاگ عملیات/منابع انسانی مدیریتی/گاوصندوق از آن‌ها گرفته می‌شود).
3. **لیست کاربران مشکل‌دار (برای بازبینی دستی)** — این کوئری کاربرانی را نشان می‌دهد که «مدیر» بودن‌شان از نام نقش آمده بود:
   ```sql
   SELECT u.Id, u.Username, u.Role, r.Name AS RbacRoleName
   FROM Users u JOIN UserRoles ur ON ur.UserId = u.Id JOIN Roles r ON r.Id = ur.RoleId
   WHERE u.Role = 'Admin' AND r.Name <> 'Admin';
   ```
   (بعد از اجرای برنامه، ورود این کاربران مقدار `u.Role` را خودکار اصلاح می‌کند.)
4. **راه‌اندازی مجدد سرور** تا سرویس `AuthService` با کد جدید بالا بیاید.

# موارد باقی‌مانده (پیشنهاد برای مرحلهٔ بعد)

این‌ها در این نسخه عمداً تغییر نکردند (خارج از دامنهٔ اصلاح بحرانی بودند) و هرکدام یک ریسک امنیتی مستقل است:

1. **گیت مدیریت نقش‌ها:** `POST/PUT/DELETE` روی `/api/roles` (و `PermissionsController`) فقط `[Authorize]` است ⇒
   هر کاربر وارد‌شده می‌تواند نقش‌ها/دسترسی‌ها را عوض کند. صفحهٔ `/settings/roles` در کلاینت هم گارد ندارد.
2. **نقش‌های غیرفعال:** در `LoginAsync` هنوز همهٔ `UserRoles` (حتی نقش خاموش) پرمیشن می‌دهند و `RolesController.Delete`
   رکوردهای `UserRoles`/`RolePermissions` را پاک نمی‌کند ⇒ ترجیحاً یکسان‌سازی با `IsActive`.
3. **کنترلرهای بدون چک پرمیشن** (کالا، فروش، طرف حساب، هزینه، گزارش‌ها، تعمیرات، تنظیمات سیستم…) که فقط با نقش قدیمی
   «Admin/Operator» باز می‌شوند؛ تا وقتی «هر نقش غیرِ Admin ⇒ اپراتور» است، هر کاربر با هر نقشی می‌تواند از API این بخش‌ها
   استفاده کند (منو مخفی است، API باز است).
4. **بررسی دسترسی‌های نقش انتخاب‌شده** در `SaveUserAsync` به‌جای نام نقش (اپراتور نباید بتواند نقش پرقدرت به کسی بدهد).
