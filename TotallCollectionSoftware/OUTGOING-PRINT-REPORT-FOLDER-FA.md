# ریشه‌یابی «چاپ نامهٔ صادره درست انجام نمی‌شود» — مسیر `Report/outgoingletter`

تاریخ بررسی: ۱۴۰۵/۰۸/۰۶ (2026-10-28) — دامنه: نامهٔ صادره (`OutgoingLetters`) روی سربرگ شرکت، A4 و A5.

## ۱) پاسخ کوتاه: مشکل خودِ `Report/outgoingletter` این است که «مسیر اجرا» نیست

هیچ‌جای کد این پوشه را نمی‌خواند. جست‌وجوی کل مخزن برای `Report/outgoingletter` در کد
(`*.cs`, `*.razor`, `*.json`, `*.csproj`) هیچ نتیجه‌ای ندارد؛ تنها ارجاع‌ها به مسیر دیگری است:

```text
inventory/src/Inventory.Api/Reports/OutgoingLetters/Companies/{CompanyId}/Outgoing-{A4|A5}.mrt
```

* این مسیر در `Inventory.Api.csproj` با `Content Include="Reports/**/*.mrt"` کنار خروجی
  Build/Publish کپی می‌شود و `FindCompanyTemplate` آن را از ContentRoot / BaseDirectory /
  پوشهٔ جاری می‌جوید (ریشه از `Reporting:Stimulsoft:TemplateRoot`).
* پس هر ویرایش در `Report/outgoingletter/**` (طرح MRT، تصویر سربرگ، فونت) **بی‌اثر** است.
* `Report/outgoingletter/{3,1003}/index.html` هم پیش‌نمایش مرورگری است، نه خروجی چاپ؛ سه لینک
  PDF آن (`Report_A5_OutgoingLetter_Preview.pdf`، `Report_A4_OutgoingLetter_Preview.pdf`،
  `Preview_OutgoingLetter_Company*_A5_A4.pdf`) در مخزن وجود ندارند و ۴۰۴ می‌دهند.

## ۲) حتی با ویرایش مسیر درست، بخشی از MRT اصلاً اعمال نمی‌شود

سرور قالب Stimulsoft را «اجرا» نمی‌کند؛ چاپ با QuestPDF ساخته می‌شود. از هر MRT فقط این‌ها خوانده
می‌شد: `Watermark/ImageBytes` (تصویر سربرگ). کادرهای متنی قالب — `GirandeAsli`، `TitleLetter`،
`TextLetter`، جای تصویر امضاها — در چاپ اعمال نمی‌شدند و چیدمان متن/موضوع/گیرنده/امضا را کد
`OutgoingLetterPrintService` می‌ساخت. بنابراین «جابه‌جا کردن کادرها در قالب» انتظار درستی نداشته.

## ۳) باگ واقعی چاپ: چیدمان فقط برای دو شناسه کالیبره شده بود

در `OutgoingLetterPrintService` (نسخهٔ `inventory/src`) شاخه‌های چیدمان چنین بودند:

```csharp
var isHomepaLetterhead = hasLetterhead && letterheadCompanyId == HomepaCompanyId;   // 1003
var isAriaLetterhead   = hasLetterhead && letterheadCompanyId == AriaCompanyId;     // 1005
```

هر شرکت دیگری به شاخهٔ عمومی می‌افتاد که مقدارها را **سفید** و با فاصله‌های ثابت می‌نوشت.
پیامد اندازه‌گیری‌شده روی تصویر سربرگ‌های موجود در مخزن:

| شرکت | طرح تصویر | رفتار قبلی کد | نتیجه |
|---|---|---|---|
| `1003` | هومپا (نوار آبی) | شاخهٔ کالیبره‌شدهٔ هومپا | درست |
| `3` | **همان طرح هومپا** (تصویر `homepa_company3_letterhead.png` بایت‌به‌بایت همان `…1003…png` است) | شاخهٔ عمومی: مقدار سفید، `PaddingTop 60` | مقدارها ~۲۱pt **پایین‌تر از برچسب‌ها** (برچسب‌های تصویر در ۶۲٫۶/۸۰٫۴/۹۹٫۴pt هستند و مقدارها روی ۸۴/۱۰۲/۱۲۰ می‌افتادند) و متن نامه از ۲۱۴pt شروع می‌شد در حالی که طرح تا ۲۳۲pt ادامه دارد؛ یعنی متن روی تزئینات پایین نوار |
| `1`, `2` | فروغ آریا (کاغذ سفید، برچسب‌های تیره) | شاخهٔ عمومی: مقدار **سفید** روی کاغذ سفید | شماره/تاریخ/پیوست عملاً نامرئی |
| `1005` | آریا همیار ژنراتور | شاخهٔ کالیبره‌شدهٔ آریا | درست |

قالب هر شرکت خودش دقیقاً گفته مقدارها کجا و با چه رنگی باشند:

```xml
<!-- Companies/3/Outgoing-A4.mrt (طرح هومپا) -->
<ClientRectangle>-0.19,0.45,1.14,0.2</ClientRectangle><TextBrush>White</TextBrush>   <!-- شماره -->
<!-- Companies/1/Outgoing-A4.mrt (طرح فروغ) -->
<ClientRectangle>0,0.3,0.9,0.2</ClientRectangle><TextBrush>Black</TextBrush>          <!-- شماره -->
```

کد این اطلاعات را نادیده می‌گرفت. ضمناً دو درخت کد موازی وجود دارد و اسکریپت‌های استقرار با هم
اختلاف دارند:

| اسکریپت | درختی که منتشر می‌کند |
|---|---|
| `publish-server.bat`، `deploy-single.ps1`، `rebuild.ps1` (ریشه) | `src/Inventory.Api` (نسل قدیمی چاپ) |
| `inventory/publish-server.bat`، `inventory/deploy-single.ps1`، `inventory/start.bat` | `inventory/src/Inventory.Api` (نسل جاری) |

## ۴) چه چیزی اصلاح شد

### ۴-۱. مقدارهای شماره/تاریخ/پیوست از قالب خود شرکت خوانده می‌شوند
فایل جدید: `Services/Office/Outgoing/LetterheadMetaFields.cs` (در هر دو درخت `inventory/src` و `src`)

* سه جزء متنی قالب را با عبارت‌های `{DataSource1.LetterNumber}`، `{DataSource1.DateShams}` و
  `{DataSource1.Peyvast}` پیدا می‌کند و از هر کدام می‌خواند: `ClientRectangle` (+ `Margins` صفحه
  و `ReportUnit`)، `TextBrush` (رنگ)، `Font` (اندازه و توپُر بودن) و `HorAlignment`.
* محاسبهٔ مختصات: `(Margin + ClientRectangle) × UnitToPoints` — همان قراردادی که مختصات
  کالیبره‌شدهٔ هومپا/آریا از آن ساخته شده بود. برای هومپا خروجی این محاسبه **عیناً** همان اعداد
  `HomepaLetterheadLayout` است (۱۴٫۴/۶۰٫۴۸ …)، پس رفتار ۱۰۰۳ تغییر نمی‌کند.
* اگر قالب موجود نباشد یا این سه جزء را اعلام نکند، `null` برمی‌گردد و چیدمان قبلی دست‌نخورده
  اجرا می‌شود (بدون رگرسیون برای شرکت‌هایی که فقط فایل سربرگ ثبت‌شده دارند).

### ۴-۲. شاخهٔ عمومی هدر از همین اعلان‌ها استفاده می‌کند
در `BuildContentPdf`، شاخهٔ `else if (hasLetterhead)`:

```csharp
var declared = ReadDeclaredMetaFields(FindCompanyTemplate(...));
if (declared != null) { /* AddDeclaredField: مستطیل/رنگ/فونت/تراز از قالب */ }
else { /* چیدمان قبلی، بدون تغییر */ }
```

`pageTopMargin` هم به‌صورت متغیر مشترک با `page.MarginTop` محاسبه می‌شود، چون `page.Header()`
بعد از حاشیهٔ بالا شروع می‌شود و مختصات قالب «مطلق» است. مقادیر منفی (مستطیلی که کمی بالاتر از
حاشیه است، مثل تاریخ در قالب شرکت ۱) با `Math.Max(0, …)` مهار می‌شوند تا QuestPDF خطا ندهد.
نتیجهٔ عملی: `1`, `2` سیاه و روی خط‌چین خودشان، `1005` و `1003` مثل قبل.

### ۴-۳. شناسهٔ هومپا فقط ۱۰۰۳ نیست

```csharp
private static readonly int[] DefaultHomepaCompanyIds = { 3, HomepaCompanyId };
private static readonly int[] DefaultAriaCompanyIds   = { AriaCompanyId };
```

همان چیدمان کالیبره‌شده (مقدار سفید روی نوار، فاصلهٔ ۸۰/۲۸ برای شروع متن، رزرو پانوشت، شمارهٔ
صفحه، پس‌زمینهٔ شفاف) چاپ می‌شود.

* لینک‌های PDF شکسته از `index.html` حذف و به یک یادداشت جایگزین شد؛ عنوان صفحهٔ ۱۰۰۳ هم که

`Report/outgoingletter/3/*` برابر `inventory/.../3` است. یعنی این پوشه آینهٔ دو درخت مختلف است.

### ۴-۵. ریشهٔ سوم (مهم‌ترین علت «طرح شرکت دیگر»): شناسهٔ عددی شرکت

قالب با شمارهٔ پوشه پیدا می‌شود (`Companies/{CompanyId}`) و این شماره بین نصب‌ها یکی نیست.
`SystemCompanies` شناسه را خودکار می‌سازد، پس در نصب تازه شرکت‌ها `1`,`2`,`3` می‌شوند و پوشه‌های
موجود این طرح‌ها را دارند:

| پوشه | طرح داخل تصویر |
|---|---|
| `1`, `2` | فروغ آریا |
| `3` | هومپا |
| `1003` | هومپا (نسخهٔ دیگر تصویر، همان جای برچسب) |
| `1005` | آریا همیار ژنراتور |

یعنی اگر شرکتِ واقعیِ شما هومپا باشد ولی شناسه‌اش `1` باشد، نامه روی **سربرگ فروغ آریا** چاپ
می‌شود و هیچ خطایی هم دیده نمی‌شود؛ و اگر شناسه `4` یا `6` باشد، چاپ با «سربرگ پیدا نشد» متوقف
می‌شود. آزمون سریع (`simulated search order`) روی هر شناسه این را نشان می‌دهد؛ برای `999` هیچ
قالبی پیدا نمی‌شود.

### اصلاح
* `FindCompanyTemplate` اکنون اول «طرح نگاشت‌شده» و بعد پوشهٔ هم‌نام خود شرکت را می‌جوید:

```csharp
foreach (var designId in DesignCompanyIds(companyId)) { ... }
```

* نگاشت در `appsettings.json` و بدون بیلد:

```json
"Reporting": { "OutgoingLetters": { "CompanyTemplateMap": { "4": "1003" } } }
```

* انتخاب چیدمان (ارتفاع هدر، شروع بدنه، رزرو پانوشت، رنگ/جای مقدارها) هم از **طرح** پیروی می‌کند،
  نه شناسهٔ خام: `designCompanyId = TemplateDesignId(letterheadCompanyId)`. پس یک نگاشت، تمام
  رفتار چاپ را یک‌جا درست می‌کند. بدون نگاشت، رفتار دقیقاً مثل قبل است.
* هنگام استفاده از نگاشت، یک خط `LogInformation` مسیر و طرح انتخابی را ثبت می‌کند.

### ۴-۶. ابزار همگام‌سازی برای خودِ پوشهٔ `Report/outgoingletter`

`Report/outgoingletter/sync-to-api-templates.bat` فایل‌های `Report_{A4,A5}_OutgoingLetter.mrt`
را برای شرکت‌های `3` و `1003` به مسیر واقعی چاپ در هر دو درخت کد کپی می‌کند
(`sync-to-api-templates.bat inventory|src` برای یکی از دو درخت). قبلاً برای اعمال یک تغییر طراحی
باید مسیرها را دستی می‌شناختید؛ اکنون یک فرمان کافی است.

### ۴-۷. علامت اصلی شما: «صفحهٔ چاپ در حال بارگذاری می‌ماند و بعد خطا می‌دهد»

این علامت یک باگ چیدمان نبود، بلکه **سقف زمانی کلاینت** بود. در `LetterPrintWorkflow` یک
مهلت ثابت **۱۵ ثانیه** برای مجموع دو کار وجود داشت: «دریافت PDF از سرور» و «تحویل PDF به
مرورگر». ساخت PDF روی سربرگ برای اولین چاپ (خواندن قالب چند مگابایتی، ثبت فونت، رندر
QuestPDF برای متن و سپس PDFsharp روی تصویر سربرگ ۲۴۸۱×۳۵۰۸) از ۱۵ ثانیه می‌گذشت؛ درخواست
قطع می‌شد، پنجره قرمز «خطا» می‌شد و در همان لحظه سرور داشت رندر را تمام می‌کرد. برای همین
هر بار «چاپ آماده نمی‌شد».

اصلاح‌ها (در **هر دو** درخت `src/` و `inventory/src/`):

| موضوع | قبل | بعد |
|---|---|---|
| مهلت دریافت | ۱۵ ثانیه، مشترک با تحویل | ۹۰ ثانیه (تلاش اول) / ۶۰ ثانیه (تلاش مجدد) |
| مهلت تحویل به مرورگر | از همان ۱۵ ثانیه کم می‌شد | ۳۰ ثانیهٔ جدا |
| بازخورد به کاربر | فقط «در حال آماده‌سازی» تا لحظهٔ خطا | بعد از ۸ ثانیه: «در حال ساخت PDF روی سربرگ شرکت…» (`window.ltxPrintStatus`) |
| تکرار رندر در «تلاش مجدد» | هر بار از صفر | کش رندر ۹۰ ثانیه‌ای روی سرور (کلید = SHA-256 دادهٔ مؤثر نامه) |
| خطای غیرمنتظرهٔ سرور | `500` خالی | `500` با متن علت + `LogError` با شناسهٔ نامه |
| فونت فارسی غایب | بی‌صدا نادیده گرفته می‌شد | خطای صریح با مسیر فایل |

جزئیات فنی که در تست‌ها قفل شده‌اند:

* کلید کش: `outgoing-print-v2:` + `SHA256(letterId, size, flags, companyId, شماره‌ها, تاریخ‌ها,`
  `عنوان/متن/گیرنده, تعداد و وضعیت امضاها, تعداد رونوشت, تعداد پیوست)`؛ با هر ویرایش نامه کلید
  عوض می‌شود، پس چاپِ بعدی هرگز نسخهٔ کهنه نمی‌دهد.
* درخواست‌های هم‌زمان (مثلاً دوبار کلیک) یک رندر را با هم استفاده می‌کنند: رکورد کش پیش از
  شروع رندر منتشر می‌شود و همه فقط `await` می‌کنند
  (`CachedRender` بر پایهٔ `TaskCompletionSource<byte[]?>` با
  `TaskCreationOptions.RunContinuationsAsynchronously` — **نه** `Lazy<Task<T>>`؛ دلیل در بخش ۴-۹).
* خروجی `null` و هر استثنا از کش حذف می‌شود؛ خطا هرگز کش نمی‌شود.
* PDF به‌صورت **باینری (Uint8Array)** به مرورگر می‌رود، نه base64؛ در نتیجه حجم انتقال و زمان
  آماده‌سازی کمتر است.

**کدام درخت منتشر می‌شود؟** اسکریپت‌های ریشهٔ مخزن (`publish-server.bat`، `deploy-single.*`،
`RUN.ps1`) `src/` را منتشر می‌کنند و `inventory/publish-server.bat` مسیر `inventory/src/` را.
قبلاً اصلاحات فقط در `inventory/` بود؛ اکنون `src/Inventory.Client` هم همان
`LetterPrintWorkflow` را دارد، همان سطح JS چاپ (`ltxPrintBegin/Ready/Fail/Status/WaitForAction/`
`DirectPage/Cancel`) و همان کش/خطای سرور در `src/Inventory.Api`. چهار صفحهٔ چاپ (نامهٔ داخلی،
کارتابل صادره، نمایش نامه، دبیرخانه) در هر دو درخت از همین سرویس مشترک استفاده می‌کنند.

### ۴-۸. «سربرگ‌های طراحی‌شده در `Reports/OutgoingLetters/Companies` خوانده نمی‌شوند»

طرح‌ها همان‌جا هستند و فایل‌ها هم با بیلد منتشر می‌شوند؛ پس مشکل در مسیر فایل نیست، در
**انتخاب شرکت و انتخاب منبع** است. سه علت که هر سه در کد پیدا و اصلاح شدند:

| # | علت | چه اتفاقی می‌افتاد |
|---|---|---|
| ۱ | **اولویت فایل ثبت‌شده** | `letterheadPath = registeredPath ?? templateLetterheadPath` — اگر روی رکورد شرکت (`SystemCompanies.LetterheadFileName`) فایلی ثبت شده باشد (مثل `wwwroot/uploads/letterheads/homepa_company1003_letterhead.jpg`)، طرح داخل MRT **هرگز خوانده نمی‌شد**. |
| ۲ | **نامهٔ بدون شرکت (CompanyId = NULL)** | در فرم نامه، کمبوی «شرکت صادرکننده» فقط «شرکت فعال» را نشان می‌داد و پیش‌فرضش `0` («بدون شرکت») بود. اگر شرکت فعال قابل تشخیص نبود (کاربر بدون ردیف دسترسی شرکت)، هیچ شرکتی قابل انتخاب نبود و نامه با `CompanyId = NULL` ذخیره می‌شد. در چاپ، «اولین شرکت فعالِ دارای سربرگ» انتخاب می‌شد؛ یعنی نامه روی طرح **شرکت دیگر** چاپ می‌شد. |
| ۳ | **نام فایل قالب** | فقط `Outgoing-A4.mrt` / `Outgoing-A5.mrt` با همان حروف دقیق خوانده می‌شد؛ فایلی با نام دیگر (مثلاً `Report_A4_OutgoingLetter.mrt`) بی‌صدا نادیده می‌رفت و علتش هم فقط در سطح `Debug` لاگ می‌شد (یعنی در سطح پیش‌فرض `Information` هیچ اثری نداشت). |

#### اصلاح‌ها

1. **انتخاب شرکت**
   * فرم نامه: همهٔ شرکت‌های فعال در کمبو می‌آیند و پیش‌فرض «شرکت فعال» کاربر است
     (`CompanyOptions` در `ComposeOutgoingModal.razor`).
   * سرور: اگر کلاینت شرکتی نفرستد، `CompanyId` نامه با «شرکت فعالِ همان درخواست»
     (`X-Company-Id` اعتبارسنجی‌شده) پر می‌شود — نه `NULL`
     (`DefaultCompanyIdForLetter` در `OutgoingLetterService`). ویرایش نامه هم دیگر
     `CompanyId` را پاک نمی‌کند.
2. **انتخاب منبع سربرگ (پیکربندی)**
   * کلید تازه: `Reporting:OutgoingLetters:PreferTemplateLetterhead`
     (`false` = رفتار قبلی، `true` = طرح پوشهٔ `Companies` اولویت دارد).
   * اگر فایل ثبت‌شده بر طرح مقدم باشد، یک خط `Information` می‌گوید کدام فایل برنده شد و

### ۴-۹. خطای ساخت پروژه: `VSTHRD011` روی `Lazy<Task<byte[]?>>`

هنگام اجرا/ساخت پروژه در Visual Studio این خطا گرفته می‌شد:

```text
Error VSTHRD011  Lazy<Task<T>>.Value can deadlock. Use AsyncLazy<T> instead.
File: inventory/src/Inventory.Api/Services/Office/Outgoing/OutgoingLetterPrintService.cs
```

علت: کش رندر چاپ با `Lazy<Task<byte[]?>>` ساخته شده بود و هر دو خواندنِ `cached.Render.Value`
و `render.Value` را داشت. قاعدهٔ `VSTHRD011` (بستهٔ `Microsoft.VisualStudio.Threading.Analyzers`)
این الگو را **خطا** می‌داند، چون کارخانهٔ مقدار، زمینهٔ اولین فراخوان را به ارث می‌برد و اگر آن
زمینه به رشتهٔ اصلی (UI) نیاز داشته باشد، می‌تواند deadlock کند. (توجه: قاعده فقط
`Lazy<T>` با نوع awaitable را می‌گیرد؛ جای دیگری که در همین سرویس `Lazy<CachedLetterheadAsset>`
داریم — کش decode تصویر سربرگ — نه awaitable است و نه در کارخانه‌اش
`JoinableTaskFactory.Run` صدا زده می‌شود، پس مشمول این قاعده نیست.)

**اصلاح:** کش رندر بدون `Lazy` بازنویسی شد و همان رفتار (یک رندر مشترک برای درخواست‌های هم‌زمان)
حفظ شد:

```csharp
private sealed class CachedRender
{
    private readonly TaskCompletionSource<byte[]?> _completion =
        new(TaskCreationOptions.RunContinuationsAsynchronously);

    public CachedRender(DateTime createdUtc) => CreatedUtc = createdUtc;
    public DateTime CreatedUtc { get; }
    public Task<byte[]?> Render => _completion.Task;
    public void Complete(byte[]? pdf) => _completion.TrySetResult(pdf);
    public void Fail(Exception error) => _completion.TrySetException(error);
}
```

و در `GeneratePdfAsync`:

```csharp
var (cached, startedHere) = RentRenderedPdf(cacheKey);   // TryAdd پیش از شروع رندر
if (!startedHere) return await cached.Render;            // فقط await، بدون .Value

try
{
    var pdf = await GeneratePdfCoreAsync(...);
    if (pdf == null) RenderedPdfs.TryRemove(new KeyValuePair<string, CachedRender>(cacheKey, cached));
    cached.Complete(pdf);
    return pdf;
}
catch (Exception ex)
{
    RenderedPdfs.TryRemove(new KeyValuePair<string, CachedRender>(cacheKey, cached));
    cached.Fail(ex);   // همهٔ منتظرانِ همان رندر همان خطا را می‌گیرند
    throw;
}
```

نکته‌های رفتار:

* رکورد **قبل** از رندر در `RenderedPdfs` ثبت می‌شود (`TryAdd`)، پس دوبار کلیک = یک رندر.
* رکورد منقضی با مقایسهٔ **خودِ نمونه** حذف می‌شود
  (`TryRemove(KeyValuePair<...>)`) تا رکورد تازهٔ درخواست دیگری پاک نشود.
* `Fail` باعث می‌شود بقیهٔ درخواست‌های در انتظار به‌جای معلق ماندن، خطای واقعی بگیرند.
* در رقابت شدید (۵ تلاش ناموفق `TryAdd`) بدون کش رندر می‌شود تا درخواست کاربر معلق نماند.
* این تغییر در **هر دو درخت** (`src/` و `inventory/src/`) اعمال شد و یک تست هم اضافه شد که
  وجود `Lazy<Task` را در این سرویس ممنوع می‌کند تا خطای ساخت برنگردد.

هرگز تکرار نمی‌شوند. تنها فاصلهٔ رزروشده، بالای گرافیک پابرگ است (`FooterReserve`).

**۲) افتادن ویرگول/نقطه به ابتدای خط (bidi).**
ریشه: جهت پایهٔ پاراگراف در چند نقطه قطعی نبود. اصلاح: هر پاراگراف، هر آیتم فهرست، هر سلول
جدول و هر مقدار (گیرنده/عنوان/نام/سمت/شماره/تاریخ) با `RLM` (`\u200F`) در ابتدا و انتها
محصور می‌شود؛ در نتیجه «،با سلام» و «.نمایند» و «۱۴۰۵/۰۸/۰۷.» درست می‌نشینند.

**۳) تداخل متن با قوس آبی سربرگ.**
ریشه: مختصات خودِ طرح برای گیرنده (y≈۱۷۴) داخل هنر سربرگ است، در حالی که هنر تا ≈۲۳۲pt
(A4) کشیده می‌شود. اصلاح: `HomepaLetterheadLayout.HeaderArtBottom(isA5)` (۲۳۲/۱۶۳) اضافه شد و
متن از پایین همان نقطه شروع می‌شود (با حداقل ۱۰pt فاصله).

**۴) ناخوانایی شماره/تاریخ/پیوست.**
این سه مقدار در طرح **سفید** بودند و روی چاپ لیزری محو می‌شدند؛ از لبهٔ چپ هم فقط ۱۴pt (≈۵mm)
فاصله داشتند — کمتر از حاشیهٔ چاپ‌نشدنی چاپگر لیزری. اصلاح:
- رنگ پیش‌فرض `#111827` و بولد بود (به‌درخواست کارفرما در بخش ۴-۱۴ به سفید برگشت).
- حاشیهٔ امن **۱۵ میلی‌متر** از لبهٔ چپ (`DesignMetaSafeLeftMm`); اگر متن جا نشد، `ScaleToFit`
  کمی کوچک می‌کند. در A5 این حاشیه خودکار کم می‌شود تا مقدار خوانا بماند.
- مقدارها مثل پیش‌نمایش خودِ طرح **راست‌چین** شدند تا به برچسبِ چاپ‌شده روی سربرگ بچسبند
  (قبلاً چپ‌چین بودند و از برچسب دور می‌افتادند).
- هر سه مقدار یک اندازه و یک وزن دارند؛ در طرح «پیوست» ۱۲ و دو تای دیگر ۱۰ بود (علت
  «یکی کم‌رنگ، یکی پررنگ»). برچسب‌ها روی خودِ تصویر سربرگ چاپ شده‌اند و کد آن‌ها را تکرار نمی‌کند.

**۵) لایهٔ متنی PDF (ToUnicode) و افتادن حروفی مثل «ی».**
این خرابی از موتور فونت (Skia در QuestPDF) می‌آید؛ خودِ فونت سالم است (هر دو
`Vazirmatn-Regular/Bold.ttf` همهٔ U+06CC/U+06A9/U+06AF/U+067E/U+0686/U+0698 را دارند و GSUB
هم دارند). روی چاپ/نمایش اثری ندارد، فقط کپی و جست‌وجوی درون‌سندی را خراب می‌کند.
کاری که انجام شد: عنوان/موضوع/کلیدواژه‌های PDF (`document.Info`) با متن سادهٔ نامه پر می‌شود
(`WithDocumentInfo`) تا **بایگانی و فهرست‌بندی** سند سالم بماند؛ هر خطایی در این مرحله نادیده
گرفته می‌شود تا چاپ متوقف نشود. رفع کامل کپی/جست‌وجوی درون‌سندی نیاز به جایگزینی موتور تولید
متن PDF دارد و در این تغییر انجام نشده است.

### ۴-۱۳. دو ایراد دیگر گزارش‌شده: چسبیدن برچسب به مقدار، و به‌هم‌ریختگی فهرست

**۶) «گیرنده نامهجناب آقای …» — بدون فاصله و به‌هم‌چسبیده.**
ریشه: ردیف گیرنده/عنوان یک `Row` بود که ستون مقدارش `RelativeItem` (کل عرض باقی‌مانده) بود و
برچسب دقیقاً بعد از آن می‌نشست؛ فاصله‌ای بین‌شان نبود و مقدار راست‌چین هم به برچسب می‌چسبید.
اصلاح در `AddDesignRow`:
- مقدار در ستون خودش (`RelativeItem`) و برچسب در ستون ثابت به عرض کادر طرح (`caption.Width`).
- یک ستون فاصلهٔ ثابت بین‌شان: `row.ConstantItem(_designPrint.LabelGap)` (طرح: ۰٫۱ اینچ = ۷٫۲pt).
- دو نقطه در انتهای برچسب و چسبیده به سمت مقدار: «گیرنده نامه: جناب آقای …».
- چون مقدار ستون اختصاصی دارد، متن بلند در همان ستون می‌شکند و خط دوم **زیر برچسب نمی‌رود**
  (hanging indent).
- برچسب ۱۲pt و مقدار ۱۴pt است؛ برای نشستن روی یک خط، اختلاف با یک `PaddingTop` کوچک
  (`baselineShift`) جبران می‌شود.

**۷) به‌هم‌ریختگی آیتم‌های فهرست.**
ریشه: شماره و متنِ آیتم در **یک** بلوک متنی بودند (`text.Span(marker)` + محتوای آیتم)؛ آیتم
بلند در خط دوم به زیر شماره می‌رفت و شمارهٔ آیتم بعدی به انتهای همان خط می‌چسبید. واژه‌های
لاتین (مثل `Workflow`) هم بدون جداسازی، علائم کنارشان را جابه‌جا می‌کردند.
اصلاح در `RichLetterPdfRenderer`:
- هر آیتم یک `Row` دو ستونی است: متن در `RelativeItem`، شماره/گلوله در `ConstantItem`
  (مثل `list-style-position: outside`) → تورفتگی آویزان درست و شماره هرگز از متنش جدا نمی‌شود.
- شماره به شکل «۱.» با `RLM` و نقطهٔ چپِ عدد؛ شماره‌های دو رقمی ستون پهن‌تر می‌گیرند.
- فاصلهٔ عمودی یکسان بالای فهرست، بین آیتم‌ها و بعد از فهرست (`PaddingVertical`).
- واژه‌های لاتین با `LRI/PDI` (`U+2066/U+2069`) جدا می‌شوند — همان کار `<bdi>` در HTML.

**تغییر عددی برای «نامهٔ متوسط یک‌صفحه‌ای بماند»:** رزرو پابرگ مسیر طرح از ۱۱۶ به **۱۴۲**
(A4) رفت (اندازه‌گیری روی تصویر سربرگ: روبان‌های روشن گوشهٔ پایین-چپ از ≈۶۸۹pt و پله‌های تیره
از ≈۷۳۶pt شروع می‌شوند)، فاصلهٔ بالای بلوک امضا ۲۲→۱۴، فاصله از هنر سربرگ ۱۰→۸ و
`bodyLineHeight` ۱٫۵۲→۱٫۴۵.

### ۴-۱۴. بازطراحی نامهٔ صادره با **قالب مشترک** نامهٔ داخلی (هفت ایراد گزارش‌شده)

خواستهٔ کارفرما: «نامهٔ صادره دقیقاً مثل نامهٔ داخلی چاپ شود؛ اگر قالب مشترک را تغییر می‌دهی،
مطمئن شو چاپ نامهٔ داخلی خراب نشود.» پس به‌جای کپی‌کردن چیدمان نامهٔ داخلی، خودِ آن به یک
فایل مشترک منتقل شد.

**فایل تازه: `Services/Office/LetterPrintTemplate.cs`** (برای هر دو مسیر چاپ)
- `Separator(...)`: خط افقی نازک خاکستری — ضخامت `0.7f`، رنگ `#999999`، فاصلهٔ بالا/پایین
  `5` (همان عددهای قبلیِ نامهٔ داخلی، عیناً) — تنها جایی که این عددها تعریف شده‌اند.
- `InfoBlock(...)`: بلوک اطلاعات دوستونه (برچسب چسبیده به لبهٔ راست متن، مقدار در ستون چپش،
  فاصلهٔ ثابت `labelGap` بین‌شان، تورفتگی آویزان، ردیف‌های خالی چاپ نمی‌شوند).
- `PageNumberFooter`: «صفحه ۲ از ۲» با ارقام فارسی، **فقط** وقتی `TotalPages > 1`
  (`IDynamicComponent`؛ چون تعداد صفحه‌ها تا پایان چیدمان معلوم نیست).
- `PersianDigits`، `PersianDate` (تقویم شمسی)، `IsolateMixedText` (LRI/PDI = `<bdi>`)،
  `MmToPoints`، و ثابت‌های `BodyLineHeight = 1.6f`، `ParagraphSpacing = 6f`،
  `SideMarginMillimeters = 15f`، `MetaValueColor = "#111827"`.

**نامهٔ داخلی (`InnerLetterPdfRenderer.cs`)** فقط دو چیز را از قالب می‌خواند: خط جداکننده و
ارقام فارسی. هیچ عدد یا اندازه‌ای عوض نشده؛ ساختار، کپشن‌ها، حاشیه‌ها و فونت سر جای خود است
(تست `test_inner_letter_layout_is_untouched` این را قفل می‌کند).

**ایراد ۱ — ساختار ناهم‌خوان با نامهٔ داخلی.**
`OutgoingLetterPrintService.BuildDesignContentPdf` بازنویسی شد و حالا ساختارش همان نامهٔ
داخلی است: سربرگ (شماره/تاریخ/پیوست) ← بلوک اطلاعات ← متن ← امضا/نام/سمت.
(ترتیب نهایی بلوک اطلاعات در بخش ۴-۱۶ آمده: گیرندهٔ بدون برچسب ← «موضوع:» و عنوان ←
رونوشت/عطف به شماره؛ خط جداکننده هم برداشته شد.) «مهر» در برنامه اصلاً وجود ندارد (نه فیلد، نه تصویر)، پس اگر روزی اضافه شود
جای همین بلوک است.
**ردیف «ایجادکننده» به درخواست کارفرما چاپ نمی‌شود** و کوئری/محاسبهٔ آن هم حذف شد (یک
رفت‌وبرگشت کمتر به پایگاه داده در هر چاپ).

**ایراد ۲ — ناحیهٔ سربرگ (شماره/تاریخ/پیوست).**
`AddDesignMetaGrid` جای سه تابع قبلی (`PlaceDesignMetaText`، `AddDesignRow`، `FindRowCaption` —
حذف شدند) را گرفت. **هر مقدار با `Top` خودش چاپ می‌شود و هیچ جدولی در کار نیست.**
- نسخهٔ اولِ همین تابع سه مقدار را در یک **جدول پیوسته** (سه ردیف پشت سر هم) می‌چید. آن روش
  فاصله‌های عمودیِ خودِ قالب (`y = 0.45 / 0.68 / 0.91` اینچ) را دور می‌ریخت و خطای هر ردیف
  روی ردیف بعد جمع می‌شد: شماره ۰٫۴۵pt، تاریخ ۳٫۴pt و **پیوست ۶٫۶pt بالاتر از برچسبش**
  (اندازه‌گیری پیکسلی روی چاپ واقعی). برای همین جدول کنار گذاشته شد.
- الان برای هر فیلد: `host.AlignLeft().AlignTop().PaddingLeft(left).PaddingTop(field.Top)`
  و یک کادر هم‌اندازهٔ کادرِ همان فیلد در قالب. یعنی مقدار هر فیلد مستقل و در مختصات مطلق
  صفحه جای می‌گیرد و خطای یک ردیف به ردیف بعد سرریز نمی‌کند.
- علاوه بر کد، **خودِ فایل `.mrt` هم اصلاح شد** (بخش ۴-۱۵): `ClientRectangle` سه مؤلفه
  طوری بازمحاسبه شد که مرکز کادر دقیقاً روی مرکز جوهر برچسب چاپ‌شده بیفتد.
- رنگ: **سفید** — همان رنگ برچسب‌های چاپ‌شده روی نوار آبی و همان چیزی که قبلاً بود
  (`Reporting:OutgoingLetters:MetaValueColor = "#FFFFFF"`). برای رنگ تیره‌تر `"#111827"` و
  برای رنگِ تعریف‌شده در خودِ قالب `"design"` را بگذارید.
- اندازه: یکی برای هر سه (`DesignMetaFontSize = 10`)، و مقدار بلند (مثل `۲۲۱/۱۴۰۵/IT`) با
  `FitFontSize` در همان یک خط جا می‌شود (کف ۷pt) تا هیچ رقم/حرفی بریده نشود.
- پیوست: فقط «دارد» یا «ندارد» — تعداد برگ جلوی آن نوشته نمی‌شود (درخواست کارفرما).
- این سه مقدار در `page.Foreground()` (لایهٔ سراسری صفحه) با **مختصات مطلق صفحه** چاپ
  می‌شوند، نه داخل حاشیه‌ها؛ وگرنه در A5 که برچسب‌های چاپ‌شده نزدیک لبه‌اند، کادر مقدارها
  به سمت راست رانده می‌شد و روی برچسب‌ها می‌افتاد. لایهٔ Foreground روی هر صفحه تکرار می‌شود.
- برچسب‌های ۱۰۰۳ روی خودِ سربرگ چاپ شده‌اند؛ برای سربرگ بدون برچسب،
  `DesignMetaLabels = "drawn"` خودِ برنامه برچسب‌ها را می‌نویسد.

**ایراد ۳ — ناحیهٔ امن.**
`contentTop = max(HeaderArtBottom + DesignContentTopGapMm, پایین ناحیهٔ شماره/تاریخ/پیوست + ۶)`
و سقفِ «دست‌کم ۲۰۰pt متن در صفحهٔ اول»؛ یعنی متن ۱۰ میلی‌متر زیر پایان هنر سربرگ شروع
می‌شود (نه روی قوس آبی، نه با فاصلهٔ خالی). پایین صفحه هم با `DesignFooterReserve` (۱۴۲/۱۰۰)
از گرافیک تزئینی دور می‌ماند. حاشیهٔ چپ/راست: ستون متن وسط صفحه می‌نشیند
(`sideMargin = (pageWidth - textWidth) / 2`) و هرگز کمتر از ۱۵ میلی‌متر نیست.

**ایراد ۴ — جهت و فونت.**
همهٔ بلوک‌ها `DirectionFromRightToLeft` دارند، دونقطه در انتهای برچسب است، و متن فارسی
داخل قالب با `RLM`/`LRI` محصور می‌شود (پاراگراف با `forceRtlParagraph: true`). ارقام با
`PersianDigits` فارسی می‌شوند (۴۵۶ نه ٤٥٦ و نه 456). فونت وزیرمتن (Regular/Bold) همان‌طور که
در نامهٔ داخلی ثبت می‌شود در PDF جاسازی می‌شود.

**ایراد ۵ — صفحه‌بندی و کاغذ.**
A4 و A5 با اندازهٔ واقعی (`PageSizes.A4/A5`)، فونت ۱۱/۹ (مثل نامهٔ داخلی؛ اگر طرح عدد
کوچک‌تری خواسته باشد همان) و همهٔ فاصله‌ها نسبی. شماره/تاریخ/پیوست در `page.Header()` هستند و
روی هر صفحه تکرار می‌شوند؛ عنوان/گیرنده در بدنه‌اند و تکرار نمی‌شوند.
«صفحه ۲ از ۲» فقط در نامهٔ چندصفحه‌ای. امضا با `ShowEntire()` (page-break-inside: avoid) و
قفل‌شده به آخرین پاراگراف کوتاه (`keepWithTrailingText`) → نامهٔ کوتاه یک صفحه می‌ماند و
امضا تنها به صفحهٔ بعد نمی‌رود.
*نکتهٔ صادقانه دربارهٔ «متن قابل کپی»*: لایهٔ متنی QuestPDF/Skia برای بعضی حروف فارسی
(`ی`,`ت`,`پ`) در استخراج متن ناقص است؛ این محدودیت کتابخانه است نه فونت. جاسازی فونت +
متادیتای جست‌وجو (`WithDocumentInfoIfDesignDriven`) انجام شده، اما تأیید نهاییِ کپی/جست‌وجو
روی بیلد واقعی لازم است.

**ایراد ۶ — «گیرنده نامهجناب آقای …».**
در `LetterPrintTemplate.InfoBlock` مقدار و برچسب دو ستون جدا هستند و بین‌شان
`ConstantItem(labelGap)` (۷٫۲pt) نشسته: «گیرنده نامه: جناب آقای …». مقدار ستون خودش را دارد،
پس خط دوم زیر برچسب نمی‌رود (تورفتگی آویزان). برچسب و مقدار **هم‌اندازه** و روی یک خط‌اند
(اختلاف اندازه و `baselineShift` قبلی حذف شد).

**ایراد ۷ — آیتم‌های فهرست.**
`RichLetterPdfRenderer` از قبل شماره را در ستون خودش می‌گذاشت؛ این‌بار فاصلهٔ پاراگراف‌ها هم
اضافه شد (`paragraphSpacing` در `AddTo`/`RenderChildren`/`RenderList`/`RenderTable` با
`BlockGap()` که فقط **بین** بلوک‌ها اعمال می‌شود) تا فهرست و پاراگراف‌ها به هم نچسبند.
شماره «۱.»، LRI/PDI برای واژه‌های لاتین (`Workflow`) و تورفتگی یکسان همه سر جای خود است.

**تنظیمات تازه (هر دو درخت، `appsettings.json` → `Reporting:OutgoingLetters`)**

| کلید | مقدار پیش‌فرض | کار |
|---|---|---|
| `DesignSideMarginMm` | ۱۵ | حاشیهٔ برابر چپ/راست (کف) |
| `DesignContentTopGapMm` | ۱۰ | فاصلهٔ بلوک اطلاعات از هنر سربرگ |
| `DesignMetaLabels` | `printed` | `drawn` = برنامه خودش برچسب‌ها را بنویسد |
| `MetaValueColor` | `#FFFFFF` | رنگ مقدارهای شماره/تاریخ/پیوست (سفید مثل قبل) |

**تغییر عددی این مرحله:** `bodyLineHeight` ۱٫۴۵→**۱٫۶**، رزرو بالای امضا ۱۴/۱۸→**۱۲**،
ارتفاع تصویر امضا سقف **۵۲/۴۰**pt (طرح ۷۵٫۶ بود و نامهٔ متوسط را بی‌دلیل دوصفحه می‌کرد)،
اندازهٔ قلم متن ۱۲/۱۴ (طرح) → **۱۱/۹** مثل نامهٔ داخلی.

**نکتهٔ صفحه‌بندی:** `page.Footer().Height(16)` در QuestPDF داخل ناحیهٔ محتوا (بالای حاشیهٔ
پایین) می‌نشیند، پس ۱۶pt از ارتفاع متن کم می‌کند؛ مدل تست و پیش‌نمایش هم همین را حساب می‌کنند.

## ۵) تست‌ها و بررسی‌هایی که انجام شد

```bash
python3 -m unittest discover -s inventory/tests/OutgoingLetterhead -p 'test_*.py' -v   # ۹۳ تست، OK
```

تست‌های تازه (در همان فایل) این‌ها را قفل می‌کنند:

* هر ده قالب (`1`,`2`,`3`,`1003`,`1005` × `A4`,`A5`) هر سه مقدار را اعلام می‌کنند.

آزموده شد؛ اما کامپایل و چاپ واقعی باید روی ماشین شما انجام شود:

```powershell
dotnet build inventory/Inventory.sln -c Debug
dotnet build Inventory.sln -c Debug            # اگر از درخت ریشه استفاده می‌کنید
```

## ۶) اگر بعد از این تغییرها هنوز چاپ درست نبود، به ترتیب این‌ها را ببینید

0. **شناسهٔ شرکت را با پوشهٔ قالب مقایسه کنید** (پیش از هر چیز):
   ```sql
   SELECT Id, Name, IsActive FROM SystemCompanies ORDER BY Id;
   ```
   اگر شناسه در `{1,2,3,1003,1005}` نیست، یا طرحش با طرح شرکت شما فرق دارد، در
   `Reporting:OutgoingLetters:CompanyTemplateMap` نگاشتش کنید (مثال: `"4": "1003"`).
1. **کدام درخت ساخته/منتشر شده؟** اگر با `publish-server.bat` ریشه منتشر می‌کنید، `src/` را
   منتشر می‌کنید. هر دو درخت اصلاح شده‌اند، ولی فایل‌های منتشرشده روی سرور باید تازه باشند.
2. **اگر پنجرهٔ چاپ باز شد ولی «آماده نشد»:** دو لاگ زیر را با هم ببینید (هر دو در سطح Information):
   * کلاینت (کنسول مرورگر / لاگ Blazor): `LetterPrintClientTiming Stage=… StageMs=… TotalMs=…`
     مراحل: `print-surface-ready`، `pdf-download`، `browser-print-handoff`، `complete`؛ در خطا:
     `preparation-failed`، و پیام خطا.
   * سرور (فایل لاگ API): `OutgoingLetterPrintTiming LetterId=… Stage=… StageMs=…`
     مرحله‌های `questpdf-compose-and-render` و `pdfsharp-letterhead-overlay` می‌گویند کدام قسمت
     کند است. اگر مجموع دو مرحله در تلاش اول حدود ۱۰–۲۰ ثانیه است، رفتار فعلی طبیعی است و
     تلاش مجدد به‌خاطر کش رندر تقریباً فوری تمام می‌شود.
   * اگر پاسخ `500` با متن `ساخت PDF نامه ناموفق بود (<نوع خطا>): <متن>` دیدید، همان متن علت
     واقعی است (فونت غایب، امضای ناقص، قالب شرکت، دسترسی دیتابیس).
3. **لاگ قالب/چیدمان** (`OutgoingLetterPrintService`) را بخوانید:
   `LetterCompanyId`، `SelectedCompanyId`، `RegisteredPath`، `TemplatePath`، `FinalPath`،
   `FromTemplate` و خط «مقادیر شماره/تاریخ/پیوست از قالب شرکت خوانده شد».
   اگر `FinalPath` روی `wwwroot/uploads/letterheads/...` است، **فایل ثبت‌شده بر قالب MRT اولویت
   دارد**؛ برای استفاده از طرح داخل MRT باید `SystemCompanies.LetterheadFileName` خالی شود.
4. **قالب روی سرور هست؟** پوشهٔ `Reports/OutgoingLetters/Companies/{id}` باید کنار فایل اجرایی
   API باشد (csproj آن را کپی می‌کند؛ انتقال دستی فایل‌ها کافی نیست).
5. **کش‌ها:** تصویر سربرگ در `%TEMP%/totall-letterheads` (کلید = طول و زمان تغییر فایل) و خروجی
   چاپ تا ۹۰ ثانیه در حافظهٔ API. برای دیدن اثر تغییر قالب، ۹۰ ثانیه صبر کنید یا سرویس API را
   ری‌استارت کنید؛ حذف فایل کش سربرگ هم امن است.
6. **گیت‌های چاپ** (اگر پیام خطا می‌گیرید، نه خروجی غلط): مجوز دبیرخانه/ایجادکننده/دریافت‌کننده،
   کامل بودن امضاها، و وجود `Resources/fonts/Vazirmatn-Regular.ttf` کنار API — این مورد دیگر
   بی‌صدا نادیده گرفته نمی‌شود و پیام صریح می‌دهد.

## ۷) پیشنهادهای بعدی (انجام نشده)

### ۴-۱۶. حذف برچسب‌های «عنوان نامه:/گیرنده نامه:»، آوردن «موضوع:» و برداشتن خط جداکننده (۱۰۰۳)
