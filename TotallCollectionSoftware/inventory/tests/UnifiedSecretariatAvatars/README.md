# اصلاح عکس کاربران در دبیرخانهٔ یکپارچه

این مرحله، **خود صفحهٔ یکپارچه** و هر دو بخش وارده/صادره را بررسی می‌کند؛ نه فقط مدال گردش یا پنل وارده به‌صورت مستقل.

## موارد اصلاح‌شده

- **وارده، ثبت‌شده‌ها:** عکس کاربر لاگینِ ثبت‌کننده کنار نام او افزوده شد. مبدأ بیرونی در سطر جداگانه باقی می‌ماند و عکس یک کاربر به سازمان مبدأ نسبت داده نمی‌شود.
- **وارده، بایگانی:** ردیفِ دارای ارجاع، عکس/نام «ارجاع‌دهنده» را از همان `SenderUserId` نشان می‌دهد؛ ردیف مستقیم، عکس/نام «ثبت‌کننده» را نشان می‌دهد. برای ردیف مستقیم، سرور اکنون شناسه و نام واقعی `CreateUserId` را برمی‌گرداند، نه متن مبدأ با شناسهٔ صفر. نام ثبت‌کنندهٔ فهرست ثبت‌شده‌ها نیز از رکورد واقعی کاربر می‌آید، نه عنوان عمومی «شما».
- **پاسخ قدیمی وارده:** اگر سرور قدیمی در بایگانی مستقیم فقط `Sender = Ferestande` داده و شناسه‌ای ندارد، کلاینت آن را کاربر فرض نمی‌کند؛ «کاربر نامشخص» و تصویر پیش‌فرض نمایش داده می‌شود.
- **صادره، فهرست دبیرخانه:** عکس ایجادکننده و عکس کاربرِ «ثبت دبیرخانه» با نقش‌های جدا نمایش داده می‌شوند. این دو شخص لزوماً یکی نیستند. شناسهٔ ثبت دبیرخانه از فیلد واقعی `DabirkhaneUserId` می‌آید؛ از روی نام مشابه، ایجادکننده یا کاربر جاری حدس زده نمی‌شود.
- **صادره، نمایش نامه:** بخش وضعیت دبیرخانه، همان عکس/نام کاربر ثبت دبیرخانه را نشان می‌دهد؛ عکس سربرگ همچنان متعلق به ایجادکنندهٔ اصلی است.
- **صادره، درخت بایگانی:** عکس ایجادکنندهٔ هر نامه کنار نامش افزوده شد. پوشه‌ها همچنان نماد پوشه دارند؛ شناسهٔ صاحب پوشه، گره بایگانی یا بایگانی‌کننده به‌جای شناسهٔ ایجادکننده استفاده نمی‌شود.
- **ریل کناری وارده:** پس از تغییر تب از والد، پنل فرزند صریحاً دوباره رندر می‌شود؛ ردیف‌ها و عکس‌های تب قبلی روی صفحه نمی‌مانند. شمارهٔ صفحه و انتخاب‌ها طبق منطق قبلی مدیریت می‌شوند.
- **موبایل:** عنوان صفحه، نام/عکس و ردیف بایگانی خوانا می‌مانند؛ دکمه‌های عملیات وارده نیز داخل عرض کارت می‌شکنند تا از سمت چپ بریده نشوند. منطق دکمه‌ها تغییر نکرده است.

تمام شناسه‌های این عکس‌ها از مسیر `UserAvatar.LoginUserId` و `/api/auth/users/photo/{id}` استفاده می‌کنند. کامپوننت مشترک `UserAvatar`، رفتار پیش‌فرض، آدرس پایهٔ API و قرارداد کش آن دست‌نخورده‌اند.

## تغییرات سمت سرور و محدوده

تغییرات این مرحله نسبت به اصلاح قبلی وارده، محدود به **۱۰ فایل محصول** است:

| بخش | فایل | تغییر |
|---|---|---|
| API | `Services/Office/IncomingLetterService.cs` | نام/شناسهٔ واقعی ثبت‌کننده در projection ثبت‌شده و بایگانی مستقیم؛ ارجاع‌های دریافتی دست‌نخورده |
| API | `Services/Office/Outgoing/OutgoingLetterService.cs` | بازگرداندن `DabirkhaneUserId` موجود در فهرست و جزئیات |
| API | `Services/Office/ArchiveService.cs` | انتقال شناسهٔ ایجادکننده در همان واکشی گروهی درخت صادره |
| Shared | `Dtos/OutgoingLetterDtos.cs` | دو فیلد nullable نمایشی `DabirkhaneUserId` در DTO فهرست دبیرخانه و جزئیات صادره |
| Shared | `Dtos/LetterDtos.cs` | فیلد nullable نمایشی `CreatorUserId` برای برگ بایگانی دبیرخانه |
| Client | `Pages/Office/Letters/Incoming/IntegratedIncomingPanel.razor` | عکس/نقش صحیح ردیف‌ها، رندر تغییر تب از والد و چیدمان موبایل |
| Client | `Pages/Office/Letters/Outgoing/OutgoingDabirkhane.razor` | تفکیک تصویر ایجادکننده و ثبت‌کنندهٔ دبیرخانه |
| Client | `Pages/Office/Letters/Outgoing/OutgoingLetterView.razor` | تصویر ثبت‌کنندهٔ دبیرخانه در نمایش نامه |
| Client | `Pages/Office/Letters/Outgoing/DabirkhaneArchiveTree.razor` | تصویر ایجادکنندهٔ نامه در برگ‌های بایگانی |
| Client | `wwwroot/css/letters.css` | استایل‌های محدود به دبیرخانه |

مسیرهای API/Client/Shared جدول، نسبت به پروژهٔ مربوط در `src/Inventory.*` هستند.

**بدون تغییر entity، دیتابیس یا Migration.** شناسه‌ها از ستون‌های موجود خوانده می‌شوند. محدودهٔ دسترسی، مجوزها، شمارش و صفحه‌بندی سرور، وضعیت ثبت/امضا، ارجاع، پاسخ، پیوست، ارسال ایمیل و عملیات چاپ/بایگانی تغییر نکرده‌اند. API جدید یا lookup بر اساس نام اضافه نشده است. اطلاعات عکسِ فهرست، نیازمند واکشی جزئیات تک‌تک نامه‌ها نیست.

اصلاح قبلی گردش حفظ شده است: بازکردن گردش وارده فقط درخت را می‌خواند، نه `GetDetailAsync` دارای اثر جانبی. بازکردن واقعی جزئیات وارده و نمایش صادره، رفتار معمول خوانده‌شدن را همچنان دارند. کاربر ثبت دبیرخانه به‌صورت یک ارجاع ساختگی وارد نمودار گردش نمی‌شود.

## نتیجهٔ آزمون نهایی

| مجموعه | نتیجه |
|---|---:|
| دبیرخانهٔ یکپارچه: کامپوننت‌های واقعی Razor و lifecycle کامل صفحه | **۵۲ موفق** |
| دبیرخانه: بررسی سورس/کامپایل عبارات projection و قرارداد JSON | **۲۳ موفق** |
| دبیرخانه: Chromium دسکتاپ و موبایل | **۲۶ موفق** |
| بازگشت وارده: Razor + مرورگر | **۷۳ + ۲۸ موفق** |
| بازگشت صادره: Razor + مرورگر | **۵۱ + ۱۷ موفق** |
| بازگشت داخلی | **۴۵ موفق** |

جمع دسته‌ها: **۲۲۱ بررسی Razor، ۲۳ بررسی سورس/projection و ۷۱ بررسی مرورگر**. `git diff --check` نیز موفق است.

مرورگر روی دسکتاپ ۱۳۶۵×۹۶۰ و موبایل لمسی ۳۹۰×۸۴۴ اجرا شد. عکس‌های آزمایشی واقعاً بارگذاری شدند (`naturalWidth > 0`)، شناسهٔ 99 پاسخ 404 می‌دهد و fallback بررسی می‌شود. عکس‌های موبایل پس از اسکرول داخل viewport کنترل می‌شوند؛ صرفِ وجود تگ تصویر کافی نیست. نام‌های تکراری، شناسهٔ نامعتبر، پاسخ قدیمی بدون ID، ایجادکننده/ثبت‌کنندهٔ متفاوت، صفحه‌بندی، فیلتر، انتخاب، ریل والد، بایگانی، نمایش نامه و هر سه نمای گردش پوشش دارند. خطای JavaScript صفحه رخ نداد.

### محدودیت اعتبارسنجی

- تمام کاربران، نامه‌ها و عکس‌ها **ساختگی** هستند؛ هیچ دادهٔ تولیدی خوانده یا تغییر داده نشده است.
- Razor و سرویس‌های کلاینت/DTOهای واقعی، همراه CSS و اسکریپت‌های محصول کامپایل می‌شوند. میزبان مرورگر Blazor Server تعاملی است، نه خروجی انتشار WebAssembly.
- تست projection، عبارت‌های واقعیِ فیلدهای هویت را از فایل‌های API استخراج و با Roslyn کامپایل می‌کند و روی دادهٔ LINQ ساختگی اجرا می‌کند. نحو هر سه فایل API، اتصال IDها، fallback نام و JSON بررسی می‌شود. **این آزمون، اجرای کل سرویس API یا ترجمه/اجرای query در EF/SQL نیست.**
- بیلد متمرکز موفق است؛ هشدار Nullable قبلیِ `MinutesApiService.cs(42,12)` در وابستگی مشترک خارج از این اصلاح باقی مانده است.
- **بیلد کامل API/Client، تست دیتابیس واقعی، پوش و استقرار در این مرحله انجام نشده‌اند.**

## اجرای تست‌ها

از `TotallCollectionSoftware/inventory` با SDK .NET 8:

```sh
dotnet run --project tests/UnifiedSecretariatAvatars/UnifiedSecretariatAvatars.csproj
dotnet run --project tests/IncomingLetterAvatars/IncomingLetterAvatars.csproj
dotnet run --project tests/OutgoingLetterAvatars/OutgoingLetterAvatars.csproj
dotnet run --project tests/InnerLetterAvatars/InnerLetterAvatars.csproj
```

پروژهٔ دبیرخانه به `OutgoingLetterAvatars` و از آن طریق به `InnerLetterAvatars/UiProbe` ارجاع دارد تا از همان Razor واقعی استفاده کند. سورس محصول در تست کپی نشده است. Roslyn از SDK نصب‌شده استفاده می‌شود.

ترمینال اول، میزبان مرورگر:

```sh
dotnet run --project tests/UnifiedSecretariatAvatars/UnifiedSecretariatAvatars.csproj -- --serve --urls http://0.0.0.0:5135
```

ترمینال دوم:

```sh
cd tests/UnifiedSecretariatAvatars
npm install --no-save --package-lock=false playwright@1.58.2
npx playwright install chromium
# در صورت نیاز در لینوکس: npx playwright install-deps chromium
node browser-smoke.cjs
```

`SECRETARIAT_TEST_URL` آدرس اختیاری همین میزبان آزمایشی و `SECRETARIAT_SCREENSHOTS` مسیر اختیاری تصاویر است. اسکریپت پیش از تغییر داده، نشانگر `UnifiedSecretariatAvatars` و `syntheticData: true` را کنترل می‌کند. میزبان ساختگی را به‌عنوان سامانهٔ اصلی منتشر نکنید.

برای بیلد کم‌حافظه:

```sh
DOTNET_PROCESSOR_COUNT=2 DOTNET_GCHeapHardLimit=0x20000000 DOTNET_GCConserveMemory=9 \
  dotnet build tests/UnifiedSecretariatAvatars/UnifiedSecretariatAvatars.csproj \
  --nologo -v minimal -m:1 -p:UseSharedCompilation=false -p:RunAnalyzers=false -p:NuGetAudit=false
```

## بسته و پایهٔ اعمال

برای جلوگیری از ناسازگاری، **ZIP تجمیعی شامل اصلاح قبلی وارده نیز هست**: ۱۳ فایل محصول، ۷ فایل آزمون وارده و ۸ فایل آزمون دبیرخانه. راهنماهای قبلیِ داخل پوشهٔ تست‌ها گزارش مرحلهٔ قبلی‌اند؛ الزامات API/انتشار این مرحله در همین راهنما آمده است.

دو Patch جایگزین در بسته هستند؛ **فقط یکی را متناسب با پایه اعمال کنید**:

1. `unified-secretariat-user-avatars.patch`: فقط این مرحله، روی سورسی که بستهٔ قبلی `IncomingLetters-avatars-update.zip` دقیقاً روی آن اعمال شده است (۱۸ فایل: ۱۰ محصول + ۸ آزمون جدید).
2. `incoming-and-secretariat-user-avatars.patch`: تجمیعی وارده + دبیرخانه، روی `37441756bef2cd2bfd5ac20142796e4555cf4b9e` (۲۸ فایل).

پایهٔ `3744175` سورس محلیِ شامل اصلاحات قبلی نقش‌ها/صادره روی `e18e60e` است. پوش قبلی آن دو اصلاح ناموفق بود؛ این پایه را با main ریموت یکسان فرض نکنید. تغییرات نقش‌ها/صادرهٔ قبلی باید در پایه موجود باشند؛ این بسته جایگزین کل مخزن نیست.

از ریشهٔ مخزن، پس از حفظ تغییرات محلی، با Patch مناسب:

```sh
git apply --check unified-secretariat-user-avatars.patch
git apply unified-secretariat-user-avatars.patch
# یا، فقط برای پایهٔ 3744175، Patch تجمیعی را به‌جای آن استفاده کنید.
```

جایگزین‌کردن فایل‌های ZIP با حفظ مسیرها، روش دیگری است؛ با اعمال Patch جمع نشود. روی پایهٔ متفاوت ابتدا اختلاف‌ها را ادغام کنید، به‌ویژه `letters.css` یا سرویس‌هایی که تغییر جدیدتر دارند. گزارش آزمون‌ها و `SHA256SUMS.txt` داخل بسته‌اند.

## انتشار لازم

برخلاف اصلاح صرفاً نمایشیِ مرحلهٔ وارده، این مرحله metadata سمت سرور هم دارد: **API و Client هر دو باید از سورس هماهنگ بیلد و منتشر شوند. Migration لازم نیست.** سرور قدیمی که شناسهٔ جدید را برنمی‌گرداند، در کلاینت جدید تصویر پیش‌فرض می‌گیرد؛ هویت حدس زده نمی‌شود.

این بسته سورس است، نه خروجی Publish. پس از انتشار واقعی، بازخوانی کامل مرورگر انجام دهید. پوش گیت به‌تنهایی معادل استقرار سرور نیست.
