# چاپ داخلی شرکت ۱۰۰۳ — تست بدون دیتابیس

## رفتار مورد انتظار

- در کارتابل، دکمهٔ A4 یا A5 پنجرهٔ انتخاب «با هامش / بدون هامش» را باز می‌کند؛ چاپ تنها پس از انتخاب نسخه شروع می‌شود.
- `GET /api/letters/{id}/print?size=A4&withHamesh=true` و معادل A5 از همان کنترل دسترسی قبلی نامه استفاده می‌کنند. مقدار پیش‌فرض `withHamesh` برابر `false` است.
- شرکت از زمینهٔ اعتبارسنجی‌شدهٔ درخواست تعیین می‌شود. دانلود PDF با کلاینت مشترک، توکن و `X-Company-Id` را ارسال می‌کند.
- برای شرکت ۱۰۰۳ فقط `Reports/InnerLetters/Companies/1003/Inner-{A4|A5}.mrt` خوانده می‌شود. نبودن/خرابی قالب، خطای روشن می‌دهد؛ سربرگ شرکت دیگری یا خروجی بی‌سربرگ جایگزین نمی‌شود.
- موتور MRT اجرا نمی‌شود؛ فقط تصویر جاسازی‌شده خوانده و روی هر صفحه تکرار می‌شود. پاراگراف‌ها و متن بلند امکان ادامه به صفحات بعد را دارند.
- «با هامش» فقط گیرنده، عنوان اقدام و متن ارجاع‌های حذف‌نشدهٔ نوع `هامش` را اضافه می‌کند؛ پاسخ‌های خصوصی چاپ نمی‌شوند. «بدون هامش» این ردیف‌ها را حتی از دیتابیس نمی‌خواند.
- امضا، مهر، عبارت تشکر، کادر یا شمارهٔ صفحهٔ خودکار اضافه نمی‌شود. متن نوشته‌شدهٔ خود کاربر و طرح ثابت سربرگ تغییر نمی‌کنند.
- هیچ migration، تغییر ساختار داده، تنظیم connection string یا اجرای API برای این قابلیت لازم نیست.

## بررسی‌های آفلاین انجام‌شده

از ریشهٔ مخزن:

```sh
python3 inventory/tests/InnerLetterPrinting/test_inner_printing.py -v
python3 inventory/tests/OutgoingLetterhead/test_letterheads.py -v
git diff --check
```

۳۱ تست قرارداد کد/قالب داخلی (شامل ۶ تست بدنهٔ HTML نامه) و بقیهٔ مجموعه‌های تست پاس شدند. تصویر هر دو قالب نیز کامل decode شد و نحو ۶ فایل C# با parser کنترل شد. این بررسی‌ها **Build یا رندر واقعی C# نیستند**.

## تست رندر واقعی روی سیستم دارای .NET 8 SDK

```sh
dotnet run --project inventory/tests/InnerLetterPrinting/InnerLetterPrinting.csproj
```

این پروژهٔ مستقل مستقیماً فایل‌های renderer، loader و مختصات سربرگِ کد تولید را کامپایل می‌کند؛ به پروژهٔ API ارجاع نمی‌دهد، `Program` آن را اجرا نمی‌کند و به دیتابیس دسترسی ندارد. نسخهٔ بسته‌ها با API یکسان است. فونت‌ها و قالب‌ها در خروجی تست کپی می‌شوند.

۸ نمونهٔ PDF: A4/A5 × کوتاه/بلند × با/بدون هامش، در `bin/Debug/net8.0/inner-print-probe` ساخته می‌شوند (زیر `bin` و خارج از Git). تست، اندازهٔ صفحه، چندصفحه‌ای شدن متن بلند، ارجاع تصویر پس‌زمینه در همهٔ صفحات، حفظ شکست خطوط، ادامهٔ هامش بلند در صفحات جدید، حذف آن در نسخهٔ بدون هامش و خطای نبودن قالب را بررسی می‌کند.

در محیط فعلی SDK وجود ندارد؛ اجرای این پروژه و Build کلاینت/API **هنوز انجام نشده است**. تأیید ظاهری نهایی باید روی PDF واقعی باشد: جای شماره/تاریخ/پیوست، فارسی، نبودن هم‌پوشانی متن با لوگو و طرح پایین سربرگ، تکرار تصویر در صفحات دوم به بعد، تفاوت هامش و نبودن بخش امضا/مهر خودکار را کنترل کنید. برای تست API از محیط آزمایشی با دیتابیس امن استفاده کنید؛ شروع عادی API ممکن است ارتقای خودکار دیتابیس را اجرا کند.

## چیدمان نامهٔ داخلی ۱۰۰۳ = چیدمان نامهٔ صادره، بدون امضا (۱۴۰۵/۰۸/۰۷)

درخواست کارفرما: «تاریخ و پیوست و شماره باید بیاد پایین‌تر سرجای خودشون قرار بگیرن»، «متن خود نامه
باید از پایین‌تر شروع بشه» و «دقیقاً عین نامهٔ صادرهٔ ۱۰۰۳ باشد فقط امضا ندارد».

- **سربرگ:** مقادیر در `page.Foreground()` و با **مختصات مطلق صفحه** چاپ می‌شوند (نه نسبت به مبدأ
  `page.Header`). مبدأ صفحه در A4 ۲۴pt و در A5 ۱۶pt اختلاف داشت؛ همین باعث می‌شد مقدارها یک ردیف
  بالاتر از برچسب‌های چاپ‌شده بنشینند. کادرها از خود قالب MRT خوانده می‌شوند.
- **شروع متن:** پایین نوار آبی + ۹۷pt (`HomepaLetterheadLayout.ContentTop`) — مثل نامهٔ صادره.
- **بلوک اطلاعات:** همان `LetterPrintTemplate.InfoBlock` نامهٔ صادره؛ گیرندگان بدون برچسب، بعد
  «موضوع:» و عنوان، سپس ایجادکننده و تاریخ ارجاع. خط جداکنندهٔ خاکستری چاپ نمی‌شود.
- **بدون امضا/مهر/عبارت پایانی.** «با هامش» فقط ردیف‌های هامش را زیر متن اضافه می‌کند.
- قالب داخلی حالا سه کادر `Text10/Text11/Text12` دارد و تصویرش بایت‌به‌بایت همان تصویر قالب صادره است.

هندسهٔ همین اعداد با یک پیش‌نمایش HTML هم بررسی شده است (سربرگ واقعی + مقادیر در مختصات مطلق)؛ ولی
**PDF واقعی فقط روی سیستمی که .NET دارد** ساخته می‌شود: `dotnet run --project inventory/tests/InnerLetterPrinting/InnerLetterPrinting.csproj`.

## بدنهٔ HTML نامه: متن انگلیسی و صفحه‌های خالی (۱۴۰۵/۰۸/۰۹)

گزارش کارفرما روی PDF واقعی نامهٔ داخلی ۱۰۰۳: «در چندین صفحه متن های انگلیسی دارد و چند صفحه
خالی وجود داره». بررسی خودِ PDF (۲۲ صفحه) نشان داد:

- صفحه‌های ۳ تا ۱۹ **بایت‌به‌بایت یکسان**‌اند (`md5` استریم یکی است) و فقط سربرگ + شماره/تاریخ/
  پیوست دارند؛ یعنی هیچ متنی روی آن‌ها نیست.
- صفحهٔ ۱ و ۲ ته‌شان `Normal` / `0` / `false` / `EN-US` / `X-NONE` / `AR-SA` دارد و صفحه‌های
  ۲۰ و ۲۱ پر است از `/* Style Definitions */` و `{mso-style-name:"Table Normal";…}`.

**علت:** بدنهٔ ذخیره‌شدهٔ نامه یک «سند کامل HTML» است (خروجی Word/Outlook با `xmlns:w`،
`<style>`، `@font-face` و کامنت شرطی `<!--[if gte mso 9]><xml>…<![endif]-->`). تابع متنی‌سازی
چاپ فقط تگ‌ها را حذف می‌کرد:

```csharp
// قبل (InnerLetterPdfRenderer.PlainText)
text = WebUtility.HtmlDecode(Regex.Replace(text, "<[^>]+>", ""));
return Regex.Replace(text, @"[^\S\r\n]+", " ").Trim();
```

محتوای `head`/`style`/`xml` «تگ» نیست، متن است؛ پس روی کاغذ می‌آمد. و چون `\r\n` حفظ می‌شد،
هر خطِ سورسِ HTML (هر بلوک CSS یک خط) یک خط چاپی می‌شد و ده‌ها خط خالی/نامرئی می‌ساخت →
صفحه‌بندی ادامه پیدا می‌کرد ولی چیزی چاپ نمی‌شد.

**اصلاح:** `Services/Office/OfficeHtmlText.cs` (در هر دو درخت) با ترتیب درست:
کامنت‌ها با محتوا → بلوک‌های `head|style|script|title|xml|…` با محتوا → شکست‌های ساختاری
(`br`، پایان `p/div/li/tr/…`) به یک نشانهٔ موقت → حذف بقیهٔ تگ‌ها + رمزگشایی دوباره →
**جمع‌کردن همهٔ فضای سفید سورس** → نشانه به خط جدید (حداکثر یک خط خالی).
`InnerLetterPdfRenderer.PlainText` فقط به همین کمکی واگذار می‌شود (برای بدنه و ردیف‌های هامش).

تست‌ها: `test_inner_printing.py` الگوهای **خودِ کد** را می‌خواند (`private static readonly Regex`)
و همان زنجیره را روی یک بدنهٔ واقعی Word اجرا می‌کند؛ پس اگر الگوها تغییر کنند تست هم
همان را می‌سنجد. آزمون رگرسیون هم دارد: الگوریتم قبلی روی همان بدنه «Normal» و
«behavior:url» و بیش از ۱۰ خط خالی می‌ساخت.
