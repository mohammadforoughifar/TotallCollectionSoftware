# عکس کاربران در کارتابل دریافتی و گردش نامهٔ وارده

## علت و اصلاح

شناسه‌های `SenderUserId`، `ReciverUserId` و `CreatorUserId` در نامهٔ وارده مربوط به کاربران لاگین‌اند، اما نماهای قبلی آن‌ها را به `UserAvatar.SystemUserId` می‌دادند. مسیر درست این شناسه‌ها `/api/auth/users/photo/{id}` و پارامتر `LoginUserId` است؛ نه `/api/SystemUsers/photo/{id}`.

- **دریافتی / کارتابل جاری:** عکس و نام **ارجاع‌دهندهٔ مستقیم همان ردیف** با `SenderUserId` کنار هم نمایش داده می‌شوند. نام سازمان/فرستندهٔ بیرونی (`Ferestande`) با عنوان جداگانهٔ «فرستندهٔ مبدأ» حفظ شده است. دو ارجاع از یک نامه یا دو کاربر هم‌نام عکس‌های مستقل دارند. در پوشهٔ ثبت‌شده‌ها عنوان صحیح «ثبت‌کننده» استفاده می‌شود.
- **گردش، هر سه نمای لیستی، درختواره و فلوچارتی:** عکس فرستنده و گیرندهٔ **هر ارجاع** نمایش داده می‌شود. در درختواره و فلوچارت، عکس ارجاع‌دهنده نیز کنار نامش اضافه شده، نه فقط عکس گیرنده.
- **مبدأ گردش:** مبدأ بیرونی با نماد سازمان نمایش داده می‌شود و عکس یک کاربر به آن نسبت داده نمی‌شود. شناسهٔ ارجاع‌دهندهٔ سطر دیگر به‌عنوان ثبت‌کنندهٔ اولیه به مدال داده نمی‌شود. ثبت‌کننده اگر در ارجاع‌ها حضور داشته باشد، عکسش در همان ایستگاه و با همان نقش واقعی نمایش داده می‌شود؛ ثبت‌کننده از روی نام، نخستین گره یا کاربر جاری حدس زده نمی‌شود.
- **خواننده و مشاهدهٔ کامل:** عکس ثبت‌کننده از `CreatorUserId` واقعی کنار نام خودش قرار می‌گیرد. عکس گیرندگانِ خلاصهٔ گردش و فرستنده/گیرندهٔ هر ردیف تاریخچه نیز اصلاح/اضافه شده است.
- **شناسه/عکس ناموجود:** رفتار پیش‌فرض کامپوننت مشترک `UserAvatar` حفظ شده است؛ نام نامعلوم «کاربر نامشخص» است و عکس از روی شباهت نام انتخاب نمی‌شود.
- **موبایل:** نام‌های بلند کنار عکس می‌شکنند؛ در درختواره، وضعیت زیر نام/عکس قرار می‌گیرد تا متن به ستون بسیار باریک تبدیل نشود.
- **خطا و پاسخ دیررس:** خطای دریافت گردش صریح است. پاسخِ نامهٔ قبلی، پنجرهٔ بسته یا کامپوننت آزادشده نمی‌تواند تصاویر نامهٔ جدید را جایگزین کند.

## نکتهٔ مهم: نمایش عکس نباید نامه را خوانده‌شده کند

`IncomingLetterService.GetDetailAsync` در سرور، برخلاف یک خواندن صرف، ارجاع‌های خوانده‌نشدهٔ کاربر را خوانده‌شده می‌کند و ذخیره می‌کند. بنابراین برای نمایش گردش **هیچ درخواست جزئیات تازه‌ای اضافه نشده است**.

گردش فقط `GetGardeshAsync` را صدا می‌زند. نام مبدأ/عنوان/شماره/تاریخ از ردیف انتخاب‌شده یا جزئیاتِ از قبل بازشده می‌آیند و هویت افراد از دادهٔ هر ارجاع می‌آید. دکمهٔ «گردش کامل» در مدال جزئیات، همان DTO بارگذاری‌شده را به والد می‌دهد؛ والد دیگر جزئیات را دوباره واکشی نمی‌کند. هر دو مسیر کارتابل و دبیرخانه یکپارچه، از جمله مشاهدهٔ بایگانی، تطبیق داده شده‌اند.

**بازکردن واقعی متن/جزئیات نامه همچنان رفتار معمول خوانده‌شدن را دارد.** نمایش عکس و بازکردن/تغییر نمای گردش، ارجاع، پاسخ، امضا یا نوشتن دیگری ایجاد نمی‌کند.

## محدودهٔ فایل‌ها

مسیرهای زیر نسبت به `src/Inventory.Client` هستند:

| فایل | تغییر |
|---|---|
| `Pages/Office/Letters/Incoming/IncomingLetterCartable.razor` | عکس/نام ارجاع‌دهندهٔ ردیف، جداسازی مبدأ، عکس ثبت‌کننده و گیرندگان خواننده، فراخوانی گردش |
| `Pages/Office/Letters/Incoming/IncomingGardeshModal.razor` | عکس هر دو طرف ارجاع در سه نما، مبدأ غیرکاربری، خطا و محافظت پاسخ دیررس |
| `Pages/Office/Letters/Incoming/IncomingLetterViewModal.razor` | عکس ثبت‌کننده و تاریخچه، ارسال جزئیاتِ موجود به callback گردش |
| `Pages/Office/Letters/Incoming/IntegratedIncomingPanel.razor` | تطبیق فراخوانی گردش از ردیف و مدال مشاهده |
| `wwwroot/css/letters.css` | چیدمان عکس/نام، محدود به نماهای وارده؛ خوانایی موبایل |

بدون تغییر API، DTO مشترک، دیتابیس، Migration یا فایل مشترک `UserAvatar`. منطق ارجاع، انتخاب گیرنده، پاسخ، وضعیت، مجوز، پیوست و چاپ تغییر نکرده است. همهٔ فایل‌های این اصلاح را با هم اعمال کنید؛ قرارداد داخلی `Open` و callback گردش هماهنگ تغییر کرده‌اند.

## اعتبارسنجی انجام‌شده

| آزمون | نتیجه |
|---|---:|
| `IncomingLetterAvatars`، بررسی کامپوننت واقعی Razor | **۷۳ موفق** |
| وارده، Chromium دسکتاپ ۱۳۶۵×۹۶۰ و موبایل لمسی ۳۹۰×۸۴۴ | **۲۸ موفق** |
| بازگشت `OutgoingLetterAvatars`، Razor | **۵۱ موفق** |
| بازگشت صادره، Chromium دسکتاپ/موبایل | **۱۷ موفق** |
| بازگشت `InnerLetterAvatars` | **۴۵ موفق** |

مجموع: **۱۶۹ بررسی کامپوننت + ۴۵ بررسی مرورگر**.

تست وارده شامل نام تکراری، دو ارجاع از یک نامه، عکس ناموجود، شناسهٔ صفر/منفی، صفحه‌بندی و انتخاب ردیف، فیلترها، هر سه نمای گردش، خواننده، مدال مشاهده، مسیرهای دبیرخانه و بایگانی، حفظ متن/وضعیت، خطا/null، بازیابی، پاسخ‌های دیررس، بسته‌شدن و Dispose است. سرویس ساختگی اثر جانبی واقعی `GetDetailAsync` را مدل می‌کند تا صرفِ شروع‌شدن نام متد با `Get` به‌اشتباه به‌عنوان بی‌اثر بودن آن تلقی نشود.

مرورگر بارگذاری تصویر (`naturalWidth > 0`)، fallback در پاسخ 404، آدرس‌های شبکه، تعاملات، دسترسی لمسی و عرض چیدمان را کنترل می‌کند. برای اندازه‌گیری، پایان انیمیشن ورود منتظر می‌ماند. خطای JavaScript صفحه رخ نداد. `git diff --check` موفق بود. بیلد متمرکز .NET 8 موفق است؛ هشدار Nullable قدیمی `MinutesApiService.cs(42,12)` در وابستگی مشترک همچنان خارج از محدودهٔ این اصلاح است.

### محدودیت آزمون

تمام نامه‌ها، کاربران و عکس‌ها **ساختگی** هستند. مارک‌آپ آزمون، کپی صفحهٔ محصول نیست: فایل‌های Razor اصلی، سرویس‌ها/DTOها و CSS/فونت/اسکریپت اصلی کامپایل و اجرا می‌شوند. میزبان مرورگر برای تست از Blazor Server تعاملی استفاده می‌کند؛ این، تست انتشار واقعی WebAssembly، API یا دیتابیس تولیدی نیست. **بیلد کامل برنامه، پوش و استقرار سرور در این مرحله انجام نشده‌اند.**

## اجرای مجدد

از `TotallCollectionSoftware/inventory` با SDK .NET 8:

```sh
dotnet run --project tests/IncomingLetterAvatars/IncomingLetterAvatars.csproj
dotnet run --project tests/OutgoingLetterAvatars/OutgoingLetterAvatars.csproj
dotnet run --project tests/InnerLetterAvatars/InnerLetterAvatars.csproj
```

پروژهٔ وارده از `tests/InnerLetterAvatars/UiProbe` موجود برای وابستگی‌های مشترک استفاده می‌کند. فایل‌های دیگر وارده را مستقیماً از سورس اصلی کامپایل می‌کند.

میزبان تست مرورگر، در ترمینال اول:

```sh
dotnet run --project tests/IncomingLetterAvatars/IncomingLetterAvatars.csproj -- --serve --urls http://0.0.0.0:5133
```

ترمینال دوم:

```sh
cd tests/IncomingLetterAvatars
npm install --no-save --package-lock=false playwright@1.58.2
npx playwright install chromium
# در صورت نیاز در لینوکس: npx playwright install-deps chromium
node browser-smoke.cjs
```

`INCOMING_TEST_URL` آدرس اختیاری **همین میزبان ساختگی** و `INCOMING_SCREENSHOTS` پوشهٔ اختیاری تصاویر است. پیش از بازنشانی یا تغییر داده، اسکریپت نشانگر `IncomingLetterAvatars` و `syntheticData: true` را بررسی می‌کند. میزبان ساختگی را به‌عنوان سامانهٔ اصلی منتشر نکنید.

برای محیط کم‌حافظه، بیلد متمرکز با گزینه‌های زیر اجرا شد:

```sh
DOTNET_PROCESSOR_COUNT=2 DOTNET_GCHeapHardLimit=0x20000000 DOTNET_GCConserveMemory=9 \
  dotnet build tests/IncomingLetterAvatars/IncomingLetterAvatars.csproj \
  --nologo -v minimal -m:1 -p:UseSharedCompilation=false -p:RunAnalyzers=false -p:NuGetAudit=false
```

## پایه و اعمال بسته

پایهٔ این اصلاح **`37441756bef2cd2bfd5ac20142796e4555cf4b9e`** است: سورس محلیِ یکپارچه با تغییرات قبلی نقش‌ها و صادره روی `e18e60e`. پوش قبلی آن دو اصلاح ناموفق بود؛ پس این پایه را با `main` ریموت یا بسته‌های قدیمیِ مبتنی بر `bba32e9` یکسان فرض نکنید. Patch این مرحله فقط اصلاح وارده و آزمون‌های جدید آن را شامل می‌شود، نه تغییرات قبلی نقش‌ها/صادره.

از ریشهٔ مخزن، پس از حفظ تغییرات محلی و بررسی تطابق پایه:

```sh
git apply --check incoming-letters-user-avatars.patch
git apply incoming-letters-user-avatars.patch
```

یا فایل‌های ZIP را با حفظ مسیرها جایگزین کنید؛ این دو روش جایگزین یکدیگرند. روی پایهٔ متفاوت، اختلاف‌ها را ادغام کنید و `letters.css` دارای تغییرات جدیدتر را کورکورانه جایگزین نکنید.

بسته **سورس و تست** است، نه خروجی انتشار. برای مشاهدهٔ تغییر در سامانهٔ واقعی، Client باید بیلد و منتشر شود؛ سپس بازخوانی کامل مرورگر انجام شود. پوش به مخزن به‌تنهایی معادل استقرار نیست.
