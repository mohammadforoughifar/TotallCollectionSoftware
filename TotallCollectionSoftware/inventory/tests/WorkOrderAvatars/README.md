# نمایش تصویر کاربران در فرم دستورکار

## دامنهٔ تغییر

- تصویر کنار نام دستوردهنده در فهرست، کارت موبایل، کانبان و جزئیات.
- تصویر واقعی گیرندگان به‌جای حروف اول نام در ستون گیرندگان؛ حفظ حلقهٔ وضعیت و تعداد نمایش واکنش‌گرا.
- تصویر کنار نام‌ها در انتخاب گیرنده، چیپ‌های انتخاب‌شده، گیرندگان نامجاز قبلی و افزودن نفر به گردش.
- نمایش در سه نمای لیست، درختواره و فلوچارت گردش، توضیحات فرد انتخاب‌شده و تاریخچه.
- تصویر در جدول و سکوی عملکرد، نویسندهٔ گفت‌وگو، نقل‌قول و کادر پاسخ، انجام‌دهندهٔ چک‌لیست و گیرندهٔ پیامک.
- نمایش تصویر بارگذار پیوست با `ShowUploaderAvatar="true"`؛ ظاهر سایر مصرف‌کنندگان `AttachmentBox` به‌صورت پیش‌فرض تغییر نمی‌کند.
- استفاده از همان `UserAvatar` و مسیر عکس کاربر لاگین؛ رفتار تصویر پیش‌فرض برای کاربران بدون عکس حفظ شده است.

منظور، فیلدهای ساختاری نام کاربران در رابط فرم است؛ متن آزاد شرح/پیام‌ها و خروجی‌های Excel/PDF با تشخیص نام یا تصاویر جدید بازنویسی نشده‌اند.

## تغییر API و پایگاه داده

API اکنون `OwnerUserId` زیر‌دستور، `DoneByUserId` چک‌لیست، `RecipientUserId` پیامک و `ActorUserId` تاریخچه را همراه نام می‌فرستد. چک‌لیست پس از تغییر وضعیت نیز شناسهٔ انجام‌دهنده را در کلاینت به‌روزرسانی می‌کند.

ستون nullable جدید `WorkOrderLogs.ActorUserId` برای نگهداری هویت پایدار عامل رویداد افزوده شده است. ثبت رویداد در کنترلر دستورکار، ساخت دستور از هشدار سرور و تبدیل تسک توسعه، شناسهٔ کاربر را ذخیره می‌کنند. رویدادهای سیستمی همچنان بدون شناسهٔ کاربر هستند.

- Migration: `20261121120000_AddWorkOrderLogActorId`
- ترمیم idempotent هنگام راه‌اندازی برای SQL Server و SQLite: `WorkOrderActorSchemaV1`
- در ارتقای اولیه، رویداد انسانی `Created` از مالک دستور و سایر رویدادهای انسانی از نام ورودِ دارای تطابق یکتا شناسه می‌گیرند؛ نام نمایشی مبنای حدس کاربر نیست.
- رویدادهای سیستم، نام ورود نامعلوم/مبهم و رویداد ایجاد بدون مالک قابل‌شناسایی تصویر پیش‌فرض می‌گیرند.
- نگاشت فقط هنگام اضافه‌شدن ستون انجام می‌شود؛ با تغییر یا استفادهٔ مجدد از نام ورود، تاریخچه در راه‌اندازی‌های بعدی به فرد دیگری نسبت داده نمی‌شود.
- کلید خارجی حذف‌شونده تعریف نشده است تا حذف کاربر باعث ازبین‌رفتن تاریخچه نشود.

## اعمال و انتشار

1. از پایگاه داده پشتیبان بگیرید.
2. فایل‌های بستهٔ به‌روزرسانی را با حفظ مسیرها در **ریشهٔ مخزن Git** جایگزین کنید. جایگزین دیگر، از همان مسیر و روی نسخهٔ پایهٔ `432697e4`:

   ```sh
   git apply --check workorders-user-avatars.patch
   git apply workorders-user-avatars.patch
   ```

   اگر نسخهٔ شما تغییرات جدیدتری دارد، ابتدا اختلاف‌ها را بازبینی کنید؛ فایل‌ها را بدون بررسی روی تغییرات خودتان بازنویسی نکنید.

3. **API و Client را با هم** بیلد و منتشر کنید. انتشار فقط Client برای بخش‌های دارای شناسهٔ جدید کافی نیست:

   ```sh
   cd TotallCollectionSoftware/inventory
   dotnet build src/Inventory.Api/Inventory.Api.csproj
   dotnet build src/Inventory.Client/Inventory.Client.csproj
   ```

4. روال معمول به‌روزرسانی دیتابیس پروژه را اجرا کنید. Migration و ترمیم راه‌اندازی هر دو اضافه شده‌اند؛ موفقیت ارتقا و وجود ستون `ActorUserId` را بررسی کنید.
5. نسخهٔ جدید Client/PWA را بارگذاری کنید. با کاربر دارای عکس و بدون عکس، بخش‌های بالا و نمایش موبایل را بررسی کنید.

این بسته شامل سورس و آزمون‌هاست؛ ارسال تغییرات به مخزن جایگزین بیلد، ارتقای دیتابیس و استقرار روی سرور نیست.

## آزمون‌ها

از پوشهٔ `inventory`:

```sh
dotnet run --project tests/WorkOrderAvatars/WorkOrderAvatars.csproj
dotnet run --project tests/WorkOrderSmsUiOffline/WorkOrderSmsUiOffline.csproj
```

آزمون اول، **فایل واقعی Razor فرم و کامپوننت‌های مشترک** را در `UiProbe` کامپایل و با `HtmlRenderer` رندر می‌کند؛ قالب HTML بدل نیست. بارگذاری اولیهٔ صفحه، HTTP و JS با fixture جایگزین می‌شوند و وضعیت والد ثابت است؛ این آزمون جایگزین آزمون تعاملی مرورگر نیست.

ارتقای دیتابیس با entity و schema helper واقعی، روی SQLite حافظه‌ای و یک DbContext کوچک بررسی می‌شود: نصب تازه، دادهٔ قدیمی، نام تکراری/نامعلوم، رویداد سیستمی، اجرای مجدد، تغییر/استفادهٔ مجدد از نام ورود و حفظ تاریخچه پس از حذف کاربر. SQL Server زنده و کل DbContext تولیدی در این آزمون اجرا نمی‌شوند؛ اتصال Migration به SQL مشترک و قراردادهای API/نقاط ثبت با بررسی کد کنترل می‌شوند.

### نتیجهٔ اعتبارسنجی این تغییر

- کامپایل `UiProbe` و پروژهٔ آزمون موفق بود؛ هشدارهای قبلی سرویس‌های نامرتبط در بازسازی اولیه باقی‌اند.
- هر **۵۰ بررسی آواتار** موفق بود.
- هر **۹۳ بررسی قبلی وضعیت/تازه‌سازی پیامک** موفق بود.
- `git diff --check` بدون خطا بود.
- بیلد کامل Client و API در محیط ۲ گیگابایتی با `OutOfMemoryException` تکمیل نشد. بیلد کامل و آزمون نهایی روی محیط توسعه/استقرار شما همچنان لازم است.
