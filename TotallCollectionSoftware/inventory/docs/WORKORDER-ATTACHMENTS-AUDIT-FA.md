**تاریخ:** ۱۸ آبان ۱۴۰۵ · **دامنهٔ بررسی:** آپلود، فهرست، پیش‌نمایش، دانلود، حذف پیوست در دستور کار
**روش:** خواندن ایستای کد (dotnet در این محیط نیست، کامپایل نشد). هر یافته با فایل و شمارهٔ خط آمده تا خودتان هم ببینید.

## ۱) خلاصهٔ مدیریتی

- **بله، همین حالا چند باگ واقعی دارد.** دو مورد از آن‌ها از جنس «کار نمی‌کند» نیست، از جنس **نشت داده بین شرکت‌ها** و **دسترسی بدون ورود** است.
- ~~**محدودیت حجم وجود دارد**~~ → **رفع شد (بند ۸):** سقف حجم فایل در کل خط پیوست برداشته شد؛ آپلود استریم می‌شود و فایل مستقیم روی دیسک می‌نشیند.
- **محدودیت فرمت ذخیره‌سازی وجود ندارد** (هر پسوندی ذخیره می‌شود)؛ ولی **پیش‌نمایش** فقط برای خانوادهٔ PDF/تصویر/آفیس/متن کار می‌کند.
- **تعداد فایل و حجم مجموع سقفی ندارد** — نه در سرور، نه در دیتابیس؛ همین می‌تواند دیسک سرور را پر کند.

| شدت | تعداد | جنس |
|---|---|---|
| بحرانی (امنیت/داده) | ۴ | نشت بین‌شرکتی، دانلود بدون ورود، ماژول‌های محافظت‌نشده، فایل‌ها بیرون از بکاپ |
| مهم (کارکرد) | ۵ | پیام‌های گمراه‌کننده، گم‌شدن بی‌صدای پیوست، نبود کنترل وضعیت، مسیر موازی |

## ۳) باگ‌های موجود همین حالا (به ترتیب اولویت)

### 🔴 P0-۱ — پیوست دستور کار، ایزولهٔ «شرکت فعال» ندارد → نشت بین‌شرکتی

**فایل:** `Services/AttachmentGuard.cs` خط ۵۸–۷۲

```csharp
if (string.Equals(module, "WorkOrders", ...))
{
    var order = await _db.WorkOrders.AsNoTracking().FirstOrDefaultAsync(w => w.Id == refId); // ← شرکت چک نمی‌شود
    if (order == null) return AttachmentAccess.None;
    if (order.OwnerUserId == userId || await _db.WorkOrderAssignees.AnyAsync(...)) return AttachmentAccess.Download;
    ...
    return canView ? AttachmentAccess.Download : AttachmentAccess.None;   // مجوز View، سراسری است
}
```

- `WorkOrder` هیچ `HasQueryFilter` شرکتی ندارد (`Data/AppDbContext.cs` خط ۱۲۶۷ فقط `DeletedAt == null` است)، پس این کوئری شرکت را فیلتر نمی‌کند.
- `HasAsync("View")` هم مجوز **سراسری** است، نه «در همین شرکت».
- هم‌زمان، خودِ دستور کار کامل محافظت شده است: `Detail()` و همهٔ فهرست‌ها `w.CompanyId == companyId.Value` دارند (`WorkOrdersController.cs` خط ۱۱۱۶، ۱۲۹۲، ۲۰۰۵…). یعنی **بدنهٔ دستور کار محافظت دارد ولی پیوست‌هایش نه.**

**سناریوی بازتولید (کاربر عادی شرکت B با نقش دارای `WorkOrders/View`):**
```
GET /api/attachments/WorkOrders/1234          → فهرست نام فایل‌های شرکت A
GET /api/attachments/download/5678            → دانلود کامل فایل
GET /api/attachments/preview/5678             → پیش‌نمایش
POST /api/attachments/WorkOrders/1234         → حتی آپلود روی دستور کار شرکت دیگر
DELETE /api/attachments/5678                  → اگر آپلودکننده/مدیر باشد
```
فقط کافی است شناسه‌ها را حدس بزند یا از لینک قدیمی استفاده کند (شناسه‌ها عددی و ترتیبی‌اند).

**همین ایراد در مسیر قدیمی هم هست:** `CanSeeOrderAsync()` (`WorkOrdersController.cs` خط ۲۰۰۵–۲۰۱۲) شرکت را چک نمی‌کند.

**اصلاح پیشنهادی (کوچک و کم‌ریسک):** در `AttachmentGuard`، بلافاصله بعد از یافتن دستور کار:

```csharp
var active = _db.ActiveCompanyId;                 // از HttpContext می‌خواند؛ همین‌جا در دسترس است
if (active is 0) return AttachmentAccess.None;    // کاربر بدون شرکت
if (active is int cid && order.CompanyId != cid) return AttachmentAccess.None;
```
و همان سه خط در `CanSeeOrderAsync`. (نکته: `null` یعنی «زمینهٔ شرکتی تعیین نشده» — مثل اجرای پس‌زمینه — و باید مثل بقیهٔ برنامه بی‌فیلتر بماند.)

### 🔴 P0-۲ — فایل‌های `uploads/WorkOrders/...` بدون احراز هویت و بدون مجوز سرو می‌شوند

`Program.cs` خط ۸۰۳ به بعد فقط این مسیرها را برای سرو استاتیک می‌بندد:
`/SecureFiles`، `/uploads/projects`، پوشهٔ «فایل های صادره»، `/uploads/office/outgoingletter`، «فایل های ایمیل»، `/uploads/office/email`، و `uploads/DocVersion` (در `DocStaticProtection.cs`).
**`/uploads/WorkOrders` در هیچ‌کدام نیست** → با `app.UseStaticFiles(...)` (خط ۹۰۳) هر کسی که آدرس فایل را داشته باشد، **بدون توکن** دانلودش می‌کند:

```
GET https://server/uploads/WorkOrders/1234/8f3c...e1_قرارداد.pdf   → 200 OK
```

نام فایل GUID دارد (حدس‌زدن سخت)، ولی آدرس در تاریخچهٔ مرورگر، لاگ پراکسی/فایروال، هدر Referer و پیام‌های ارسالی می‌ماند و **منقضی‌شدنی نیست**. همین وضع برای `uploads/HrEmployee` (مدارک پرسنلی)، `uploads/HrApplicant` و `uploads/MeetingMinutes` هم برقرار است.

**اصلاح:** یا این مسیرها را مثل `DocVersion` ببندید (چند خط در همان میان‌افزار)، یا بهتر: ذخیره‌سازی پیوست‌ها را از `wwwroot` بیرون ببرید (همان کاری که برای آرشیو اسناد با `DocArchive:StorageRoot` شده است).

### 🔴 P0-۳ — ماژول‌های «محافظت‌نشده» پیوست‌هایشان برای هر کاربرِ واردشده باز است

`AttachmentGuard.cs` خط ۴۴ فقط سه ماژول را محافظت‌شده می‌داند: `DocVersion`، `HrEmployee`، `WorkOrders`؛ و در پایان تابع:

```csharp
// ---------- سایر ماژول‌ها ----------
// رفتار قبلی حفظ می‌شود: هر کاربر واردشده دسترسی دارد.
return AttachmentAccess.Download;
```

کامپوننت `AttachmentBox` در این‌ها استفاده می‌شود: `MeetingMinutes` (صورت‌جلسه) و `HrApplicant` (رزومهٔ متقاضی استخدام) — هر دو **بدون** محافظ. یعنی هر کاربری با شماره‌های ساده می‌تواند `GET /api/attachments/MeetingMinutes/12` و `download/{id}` بزند. برای دادهٔ منابع انسانی این جدی است.

**اصلاح:** این دو ماژول را با همان الگوی `HrEmployee` به `Protected` اضافه کنید و قانون دسترسی‌شان را بنویسید؛ همچنین پیش‌فرض را از «باز» به «بسته» عوض کنید و صریحاً ماژول‌های بی‌خطر را استثنا کنید.

### 🔴 P0-۴ — پیوست‌ها بیرون از بکاپ و داخل پوشهٔ برنامه‌اند (ریسک از دست رفتن داده)

1. **بکاپ خودکار، فقط دیتابیس است:** `Services/Backup/SqlServerBackupService.cs` خط ۱۰۸ فقط `BACKUP DATABASE` می‌گیرد. پوشهٔ `wwwroot/uploads` در هیچ بکاپی نیست. اگر دیتابیس را روی سرور دیگری برگردانید، همهٔ ردیف‌های پیوست هستند ولی فایل‌ها نیستند → «فایل در دسترس نیست».
2. **پوشهٔ برنامه با هر انتشار جایگزین می‌شود:** خودِ `FileStore.cs` در توضیحش نوشته که `wwwroot/uploads` همراه انتشار پاک می‌شود و برای همین مسیر بیرونی `DocArchive:StorageRoot` ساخته شد — **ولی پیوست دستور کار هنوز از آن مسیر استفاده نمی‌کند** و داخل `wwwroot` می‌نشیند.

**اصلاح:** یک کلید تنظیمات مشابه (`Attachments:StorageRoot` یا استفادهٔ همان `DocArchive:StorageRoot`) برای ماژول‌های پیوست، و افزودن پوشهٔ فایل‌ها به بکاپ (zip کنار `.bak`).

### ✅ P1-۵ — «بدون محدودیت حجم» دروغ بود: سه عدد ناسازگار — **رفع شد**

| لایه | قبل | بعد |
|---|---|---|
| متن داخل جعبهٔ پیوست | «بدون محدودیت تعداد و حجم» | همان (اکنون راست است) |
| پیش‌بررسی کلاینت | فایل > ۲۰ مگابایت حذف می‌شد | **حذف شد؛ فایلی دور ریخته نمی‌شود** |
| سرور (حاکم) | `> 10 * 1024 * 1024` → `400` | **برداشته شد** |

پیش‌تر فایل ۱۰ تا ۲۰ مگابایتی از فیلتر کلاینت رد می‌شد، آپلود می‌شد و سرور ردش می‌کرد با پیام «(400)». حالا سقفی نیست.

### 🟠 P1-۶ — پیوست در فرم «دستور کار جدید» بی‌صدا گم می‌شود

`Pages/ItAssets/WorkOrders.razor` خط ۴۴۶۷ و ۴۴۹۸:

```csharp
foreach (var f in newFiles) await UploadFile(created.Id, f);
...
var resp = await Http.PostAsync($"/api/workorders/{id}/attachments", content);   // ← نتیجه بررسی نمی‌شود
```

`Http.PostAsync` برای `400` استثنا نمی‌دهد؛ پس **هیچ پیامی** به کاربر نمی‌رسد: دستور کار ثبت می‌شود، توست سبز «دستور کار ثبت شد» می‌آید و پیوست وجود ندارد. **(رفع شد: پاسخ سرور بررسی و خطا با نام فایل اعلام می‌شود.)** اگر وسط حلقه شبکه قطع شود، بقیهٔ فایل‌ها هم بی‌صدا می‌مانند و پیوست‌های نیمه‌کاره ثبت می‌شوند.

`AttachmentBox.razor` خط ۴۹۸–۵۰۲:

### 🟠 P1-۸ — سرور وضعیت دستور کار (باز/بسته) را بررسی نمی‌کند

UI آپلود و حذف را روی دستور کار بسته می‌بندد (`CanUpload="detail.Status == Open"`)، ولی هیچ‌کدام از دو مسیر API این را چک نمی‌کنند (`ArchiveController.Upload/Delete`، `WorkOrdersController.Upload`). یعنی با ابزار توسعه‌دهنده یا اسکریپت، می‌شود روی دستور کار **بسته** پیوست افزود یا حذف کرد — مغایر با قاعدهٔ «بعد از بستن هیچ عملیاتی مجاز نیست» که در خودِ موجودیت نوشته شده است.

پیوست‌هایی که از فرم «دستور کار جدید» می‌آیند از مسیر قدیمی رد می‌شوند؛ پس **ردّ دسترسی (audit) ندارند** و در سناریوی محرمانگی هم همان قواعد را نمی‌بینند. بد نیست مسیر قدیمی حذف و فرم جدید هم به `AttachmentBox`/مسیر جاری منتقل شود (یا حداقل از لاگ و کنترل‌های مشترک استفاده کند).

### 🟡 P2-۱۰ — فهرست پیوست‌ها ستون `Data` را از دیتابیس می‌کشد

`ArchiveController.List` خط ۲۵۵–۲۵۹ و `WorkOrdersController.Attachments` خط ۲۶۹۳: بایت‌های کامل فایل انتخاب می‌شود و بعد فقط `a.Data.Length` استفاده می‌شود. برای آپلودهای جدید `Data` خالی است (بی‌ضرر) ولی **برای رکوردهای قدیمی که فایل داخل دیتابیس است**، هر بار باز کردن تب پیوست = خواندن همهٔ BLOBها. روی دستور کاری با چند پیوست سنگین قدیمی، کندی محسوس می‌دهد.

اصلاح: انتخاب `HasData = a.Data.Length > 0` به‌جای خودِ `Data` و محاسبهٔ حجم با `_store.Size(...)`.

### 🟡 P2-۱۱ — سقف بدنه در کل برنامه برداشته شده، ولی محدودیت واقعی بعد از بافر اعمال می‌شود

`Program.cs` خط ۴۳۶–۴۴۵: `MultipartBodyLengthLimit = long.MaxValue` و `MaxRequestBodySize = null` (و همان در خط ۷۲/۱۲۹ برای Kestrel). یعنی یک `POST` چند گیگابایتی **اول کامل روی دیسک موقت سرور می‌نشیند** و بعد در اکشن با «۱۰ مگابایت» رد می‌شود. این هم دروازهٔ پرکردن دیسک/کندی است، هم چون سقف ۱۰ مگابایتی فقط بعد از بافر اعمال می‌شود عملاً به کاربر «بی‌فایده انتظار» تحمیل می‌کند. اصلاح: یک `MaxRequestBodySize` منطقی (مثلاً ۱۵ مگابایت) برای همین endpoint و نگه‌داشتن سقف نامحدود فقط برای پیام‌رسان (که خودتان خواسته بودید).

### 🟡 P2-۱۲ — کد/جدول مرده

`WorkOrderAttachment` (در `Entities/ItAssets/WorkOrder.cs` خط ۲۳۷) و جدول `WorkOrderAttachments` هیچ‌جا استفاده نمی‌شوند؛ همهٔ پیوست‌ها در `AppAttachments` هستند. اگر در دیتابیس قدیمی رکوردی در آن جدول مانده باشد، هیچ‌جا نمایش داده نمی‌شود.

### 🟡 P2-۱۳ — فایل‌های `.doc/.xls/.ppt` دکمهٔ پیش‌نمایش می‌گیرند ولی پیش‌نمایش ندارند

`Kind(...)` آن‌ها را `office` می‌داند → `CanPreview = true` → کلیک → سرور پیام «فرمت قدیمی… یک نسخهٔ DOCX/PDF تهیه کنید» می‌دهد. پیام درست است، ولی بهتر است از ابتدا دکمهٔ پیش‌نمایش نگیرند (فقط دانلود).

### 🟡 P2-۱۴ — نبود سقف مجموع/سهمیه و نبود بررسی نوع فایل

تعداد فایل، حجم مجموع هر دستور کار و حجم کل سرور سقفی ندارد؛ پسوند هم بررسی نمی‌شود (یک `.exe` با نام `.pdf` ذخیره می‌شود؛ اسکن بدافزار هم وجود ندارد). اگر سرور در دسترس اینترنت است، حداقل یک فهرست سفید پسوند برای ماژول دستور کار توصیه می‌شود.

## ۷) چک‌لیست تست پس از اصلاح

1. کاربر دوشرکتی (A فعال): شناسهٔ پیوست شرکت B → `403` در `list`/`download`/`preview`/`upload`/`delete`.
2. همان آدرس مستقیم `https://server/uploads/WorkOrders/...` در حالت ناشناس → `404`.
3. فایل ۲۴ مگابایتی با سقف جدید → آپلود موفق + پیوست در فهرست و پیش‌نمایش.
4. فایل ۳۰ مگابایتی → پیام فارسی روشن (نه «(400)»).
5. ساخت دستور کار با پیوست ۲۴ مگابایتی → پیوست ثبت می‌شود و در تب دیده می‌شود.
6. دانلود و پیش‌نمایش روی دستور کار بسته → `403`؛ دانلود همچنان مجاز.
7. حذف دستور کار با پیوست → ردیف‌ها و فایل‌های دیسک هر دو حذف شوند.
8. بازگرداندن بکاپ روی محیط آزمایشی → پیوست‌ها موجود باشند.
9. کاربر بدون هیچ شرکتی → فقط پیام «شرکت فعال انتخاب نشده است»، بدون نشت داده.

> این گزارش فقط از خواندن کد به دست آمده و کامپایل/اجرا نشده است؛ پیش از انتشار، بندهای ۳ تا ۹ را روی محیط آزمایشی با یک کاربر دوشرکتی و یک فایل ۲۰+ مگابایتی تکرار کنید.

### چرا استریم مهم است

قبلاً کل فایل در `MemoryStream` کپی می‌شد؛ با برداشتن سقف، دو کاربر که هم‌زمان یک فایل ۲ گیگابایتی بفرستند، حافظهٔ سرور را از پا درمی‌آوردند. حالا بایت‌ها مستقیم روی دیسک نوشته می‌شوند (اتمیک: `.part` + Rename) و مصرف حافظه ثابت می‌ماند.

### سقف‌هایی که همچنان سر جایشان هستند (و عمدی‌اند)

- سقف بدنهٔ Kestrel/IIS: نامحدود (نیازی به تغییر نبود؛ `web.config` هم `maxAllowedContentLength=4294967295` دارد).
- **پیش‌نمایش** آفیس: ورودی ۴۰ مگابایت، خروجی HTML ۲۴ مگابایت، ضد zip-bomb — این سقف نمایش است نه ذخیره؛ فایل بزرگ‌تر ذخیره می‌شود ولی پیش‌نمایش سبک ندارد.
- تصویر بزرگ: پیش‌نمایش حداکثر ۵۰ مگاپیکسل / ریسایز به ۲۴۰۰ پیکسل.
- پیش‌نمایش PDF: زمان‌سنجی ۹۰ ثانیه‌ای دریافت؛ PDF چند صد مگابایتی ممکن است پیام «زمان دریافت به پایان رسید» بدهد (فایل سالم است و دانلود می‌شود).
- پیوست‌های سایر ماژول‌ها که UI خودشان سقفشان را صریح نوشته‌اند (نامهٔ داخلی/وارده/صادره ۲۰ مگابایت، ایمیل ۲۰ مگابایت، عکس پرسنل ۵ مگابایت، پیوست درخواست IT ۱۰ مگابایت) دست‌نخورده‌اند.

### ریسک جدیدی که باید بدانید

با نبود سقف، **پر شدن دیسک** تنها محدودیت واقعی است. توصیهٔ عملی:
1. پوشهٔ `uploads` را روی درایو داده (نه درایو سیستم) بگذارید و فضای آن را پایش کنید.
2. اگر خواستید، یک سقف خیلی بالا و قابل تنظیم (مثلاً `Attachments:MaxFileSizeMb` پیش‌فرض `0` = بدون سقف) اضافه می‌کنم تا در نصب‌های خاص بتوانید روشنش کنید.

### آزمون پذیرش این تغییر

1. آپلود فایل ۶۰ مگابایتی PDF در تب «پیوست‌ها» → موفق، در فهرست با حجم درست، پیش‌نمایش باز می‌شود.
2. همان فایل در فرم «دستور کار جدید» → پیوست روی دستور کار ثبت می‌شود.
3. فایل ۱۲۰ مگابایتی → آپلود موفق؛ پیش‌نمایش یا لود می‌شود یا پیام زمان به پایان رسید (نه خطای حجم).
4. فایل XLSX سنگین (>۴۰ مگابایت) → ذخیره می‌شود، پیش‌نمایش سبک پیام «حداکثر ۴۰ مگابایت» می‌دهد، دانلود سالم است.
5. قطع اینترنت وسط آپلود → پیام خطای فارسی با نام فایل، و فایل نیمه‌کاره روی دیسک نمی‌ماند.
6. آپلود هم‌زمان ۵ فایل ۵۰۰ مگابایتی → مصرف حافظهٔ سرور ثابت می‌ماند (استریم) و دیسک پر می‌شود (طبیعی).
