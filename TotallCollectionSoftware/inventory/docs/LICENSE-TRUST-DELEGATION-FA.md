# مجوز اعتماد کلید امضا (Trust Delegation) — کلید ریشه + کلید هر مشتری

این سند مدل تازهٔ اعتماد امضای لایسنس را توضیح می‌دهد: چرا لازم شد، چه چیزی در کد اضافه شده،
و پشتیبان چه‌کاری انجام می‌دهد.

## ۱) مسئله‌ای که حل می‌کند

پیش از این، تنها کلیدهایی که یک نصب می‌پذیرفت، همان‌هایی بودند که داخل اسمبلی جاسازی شده بودند
(`inventory/src/Inventory.Licensing/Keys/manifest.json`). نتیجه:

- برای هر مشتری که کلید دیگری داشت، باید **سورس دست‌کاری و بیلد تازه منتشر** می‌شد.
- با هر بار دانلود/بیلد تازه از گیت، پوشهٔ `bin/Debug/license-keys` نبود و پنل ناچار کلید
  تازه می‌ساخت ⇒ شناسه و اثر انگشت تازه ⇒ **ناهم‌خوانی همیشگی** با کلید نصب مشتری.
- اگر کلید خصوصی گم می‌شد، هیچ راهی برای امضا نبود.

## ۲) مدل تازه (دو لایه)

```
        کلید ریشه (root)  ── داخل اسمبلی، تغییرش = انتشار نسخهٔ تازه
              │  امضا می‌کند
              ▼
   مجوز اعتماد <customer>.trust.json  ── برای یک شناسهٔ نصب مشخص
              │  معرفی می‌کند
              ▼
   کلید امضای همان مشتری  ── در پنل ساخته می‌شود؛ کلید خصوصی هرگز جابه‌جا نمی‌شود
              │  امضا می‌کند
              ▼
                      license.lic
```

قاعده‌ها (همه در کد پیاده و آزمون شده‌اند):

| قاعده | نتیجهٔ نقض |
|---|---|
| مجوز اعتماد فقط با **کلید ریشهٔ جاسازی‌شده** سنجیده می‌شود | «کلید ریشهٔ … شناخته‌شده نیست» |
| زنجیره یک‌سطحی است؛ کلید نمایندگی نمی‌تواند مجوز بسازد | امضا با کلید نمایندگی به‌عنوان `issuedBy` رد می‌شود |
| مجوز فقط برای **همین شناسهٔ نصب** معتبر است | «برای نصب دیگری صادر شده است» |
| بازهٔ اعتبار (`issuedAt`/`validUntil`) | «منقضی شده است» / «تاریخ صدور در آینده» |
| فهرست ابطال (`revoked.txt`) | «در فهرست ابطال این نصب است» |
| کلید نمایندگی نمی‌تواند شناسهٔ کلید جاسازی‌شده را بگیرد | «همین حالا داخل بیلد جاسازی شده است» |
| دست‌کاری محتوای کلید عمومی | «اثر انگشت … با محتوای کلید نمی‌خواند» |

## ۳) محل فایل‌ها در نصب مشتری

| مسیر | محتوا |
|---|---|
| `…\License\license.lic` / جدول `LicenseGrants` | لایسنس امضاشده (مثل قبل) |
| `…\License\trusted-keys\*.trust.json` | مجوزهای اعتماد (کلید هر مشتری) |
| `…\License\trusted-keys\revoked.txt` | ابطال: هر خط یک `keyId` یا اثر انگشت یا نام فایل |
| `…\License\installation.id` | شناسهٔ نصب (مرجع قیدِ «همین نصب») |

مسیر پوشه با `Licensing:TrustedKeysFolder` در `appsettings` محصول قابل تغییر است؛ خالی ⇒
پیش‌فرض بالا. نبودن پوشه خطا نیست: نصب‌هایی که با کلید ریشه امضا شده‌اند مثل قبل کار می‌کنند.

پوشه هر لحظه دوباره خوانده می‌شود (کش با تغییر تاریخ/حجم فایل‌ها باطل می‌شود)، پس **افزودن کلید
تازه بدون ری‌استارت** اثر می‌کند.

## ۴) گردش‌کار پشتیبان — یک‌بار کلید ریشه

```powershell
# در ریشهٔ مخزن، یک‌بار:
dotnet run --project inventory\tools\RootKeyTool -- new `
    --key-id sup-202612 `
    --out C:\LicensingKeys `
    --password "<گذرواژهٔ کلید>" `
    --repo .
```

این ابزار:
1. جفت‌کلید RSA‑3072 می‌سازد.
2. کلید خصوصی رمزدار را **بیرون از مخزن** در `C:\LicensingKeys\sup-202612.private.pem` می‌نویسد
   (روی ویندوز ACL، روی لینوکس `600`).
3. کلید عمومی را در `inventory/src/Inventory.Licensing/Keys/sup-202612.pem` می‌گذارد.
4. `manifest.json` را به‌روز می‌کند (ردیف‌های قبلی **حذف نمی‌شوند** تا لایسنس‌های قدیمی معتبر بمانند).
5. `Inventory.Api/appsettings.json` را به‌روز می‌کند (`SigningKeyId`، `SigningKeyFingerprintSha256`)
   — بدون پاک‌کردن کامنت‌ها، با نسخهٔ پشتیبان `‎.bak-<تاریخ>`.

سپس: بیلد Release محصول ⇒ انتشار روی نصب مشتری ⇒ فایل درخواست تازه ⇒ امضا.

ابزارهای دیگر همین برنامه:

```powershell
dotnet run --project inventory\tools\RootKeyTool -- fingerprint --file C:\LicensingKeys\sup-202612.private.pem --password <...>
dotnet run --project inventory\tools\RootKeyTool -- inspect --trust trust.json --root C:\LicensingKeys\sup-202612.pem --installation <installationId>
```

## ۵) گردش‌کار هر مشتری (بدون دست‌زدن به سورس)

1. مشتری فایل درخواست می‌دهد؛ فایل، `supportedSigningKeys` و `signingKeyPolicy` را دارد.
2. پنل شناسهٔ کلید مورد انتظار را از فایل می‌خواند (نه از تنظیمات دستی).
3. اگر کلید خصوصی متناظر در گاوصندوق نبود، پنل برای همان مشتری جفت‌کلید می‌سازد
   (`C:\LicensingKeys\customers\<installationId>\`) و مجوز اعتماد را با کلید ریشه امضا می‌کند.
4. لایسنس با کلید مشتری امضا می‌شود (گیت هم‌خوانی سبز).
5. بستهٔ تحویل: `license.lic` + `<keyId>.trust.json` (+ راهنمای یک‌صفحه‌ای).
6. مشتری دو فایل را در `…\License\trusted-keys\` می‌گذارد و `license.lic` را آپلود می‌کند.

## ۶) کلید — نگه‌داری و ابطال

- کلید خصوصی **هیچ‌وقت** داخل پوشهٔ سورس/بیلد (`bin`, `support-panel/license-keys`) نباشد.
- دو نسخه پشتیبان: یکی رمزگذاری‌شده روی رسانهٔ بیرونی، یکی در گاوصندوق/مدیر رمز.
- گم‌شدن کلید ریشه ⇒ انتشار نسخهٔ تازه با ردیف تازه در `manifest.json` (کلید قدیمی می‌ماند تا
  لایسنس‌های موجود نمیرند).
- لو رفتن کلید یک مشتری ⇒ یک خط در `revoked.txt` با اثر انگشت همان کلید + صدور مجوز/کلید تازه.
  بقیهٔ مشتری‌ها دست‌نخورده می‌مانند؛ این بزرگ‌ترین مزیت مدل نمایندگی است.

## ۷) وضعیت پیاده‌سازی

| قطعه | جای کد | وضعیت |
|---|---|---|
| قالب و امضا/سنجش مجوز اعتماد | `Inventory.Licensing/Crypto/TrustCertificate.cs` | ✅ کامل، ۲۴ آزمون |
| پذیرش کلید نمایندگی در حلقه | `PublicKeyRing.FromEmbeddedAndTrusted` / `LoadTrustedKeys` | ✅ کامل |
| اتصال به API | `PublicKeyRingProvider.GetRing(installationId)` + `SignedFileLicenseProvider` | ✅ کامل |
| تنظیم مسیر | `LicensingOptions.TrustedKeysFolder` | ✅ کامل |
| ابزار کلید ریشه | `inventory/tools/RootKeyTool` | ✅ کامل، آزموده |
| پنل: ساخت کلید مشتری + صدور مجوز + بستهٔ تحویل + هشدار | `support-panel` | ✅ کامل |

### ۷-۱) پنل پشتیبان — دو تنظیم لازم

در `support-panel/appsettings.json` (یا متغیر محیطی، تا با هر publish از دست نرود):

```json
"Signer": {
  "RootKeyId": "sup-202612",
  "RootPrivateKeyPath": "C:\\LicensingKeys\\sup-202612.private.pem"
}
```
گذرواژهٔ کلید ریشه در متغیر محیطی `LICENSING_ROOT_KEY_PASSWORD` (نام متغیر با
`Signer:RootKeyPasswordEnvironmentVariable` قابل تغییر است). اگر گذرواژه ندهید و کلید
رمزدار باشد، پنل پیش از صدور، پیام روشن می‌دهد.

### ۷-۲) گردش‌کار پنل (صفحهٔ «جزئیات درخواست»)

1. کارت **«کلید امضای این مشتری و مجوز اعتماد»** وضعیت را نشان می‌دهد: کلید فعال پنل، کلید ریشه،
   و «مجوز معتبر دارد / ندارد».
2. دکمهٔ **«ساخت کلید مشتری و صدور مجوز اعتماد»**: جفت‌کلید مشتری در
   `<گاوصندوق>/customers/<installationId>/` ساخته می‌شود (رمزدار)، به‌عنوان کلید فعال پنل
   تنظیم می‌شود، و مجوزِ امضاشده با کلید ریشه در `<WorkFolder>/trust/<installationId>/` نوشته
   می‌شود. پیش از تحویل، سند **خودآزمون** می‌شود.
3. دکمهٔ **«دانلود بستهٔ تحویل (zip)»**: `license.lic` + `trusted-keys/*.trust.json` +
   «راهنمای-نصب.txt».
4. امضا: گیت هم‌خوانی کلید حالا **کلید نمایندگیِ دارای مجوز اعتماد برای همان نصب** را هم مجاز
   می‌داند (با هشدار که بستهٔ تحویل باید فایل trust را همراه داشته باشد).
