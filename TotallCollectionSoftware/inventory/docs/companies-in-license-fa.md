# شرکت‌های مجاز داخل لایسنس — قرارداد داده و نقطهٔ اعمال

**نسخهٔ سند:** ۱ · **تاریخ:** ۱۴۰۵/۰۸/۲۴

---

## ۱) چرا این قابلیت اضافه شد

درخواست کارفرما: «کاربر درخواست لایسنس می‌فرستد، پشتیبان همهٔ کارهای فعال‌سازی را انجام می‌دهد، و هر
چیزی که برای فعال‌سازی لازم است داخل لایسنس امضاشده خوانده شود تا دور زدن ممکن نباشد — از جمله
شرکت‌هایی که در نرم‌افزار اصلی تعریف شده‌اند.»

پس «شرکت» هم مثل ماژول، سهمیه و سقف کاربر، **دادهٔ امضاشده** است؛ نه تنظیمات نصب و نه ردیف دیتابیس.

---

## ۲) قاعدهٔ غیرقابل‌عبور (کلید اعتماد)

کلید عمومیِ لازم برای بررسی امضا **باید** داخل محصول باشد (`Keys/manifest.json` به‌صورت
EmbeddedResource). اگر کلید داخل خودِ فایل لایسنس بود، هر کسی می‌توانست کلید خودش را بگذارد و
لایسنس جعلی بسازد.

| چه چیزی | کجا | چند بار عوض می‌شود |
|---|---|---|
| کلید عمومی امضا | داخل محصول | یک‌بار برای همیشه (یا در چرخش کلید) |
| **همهٔ دادهٔ فعال‌سازی، از جمله شرکت‌ها** | داخل `.lic` امضاشده | هر مشتری / هر تمدید |

## ۳) شکل داده در سند (نسخهٔ ۳ قالب، افزونهٔ سازگار)

```json
{
  "version": 3,
  "keyId": "sup-202611",
  "serial": "LIC-20261115-9845685A",
  "customerId": "CUST-100",
  "customerName": "شرکت نمونه",
  "deployment": "OnPrem",
  "installationId": "…",
  "issuedAt": "2026-11-15T08:36:00Z",
  "companies": [
    { "companyId": "C-1001", "name": "شرکت الف", "maxUsers": 5, "modules": ["sales"] },
    { "companyId": "C-1002", "name": "شرکت ب", "maxUsers": 3 }
  ],
  "items": [ { "id": "base", "scope": ["sales","hr_fa"], "term": {…}, "users": {…}, "quotas": […] } ]
}
```

| فیلد | اجباری | معنی |
|---|---|---|
| `companies` | خیر | خالی/نبودن = **بدون محدودیت شرکت** (رفتار اسناد قدیمی) |
| `companies[].companyId` | بله | شناسهٔ شرکت در نرم‌افزار اصلی؛ یکتا در سند (بدون حساسیت به حروف) |
| `companies[].name` | خیر | فقط نمایش؛ مبنای هیچ تصمیمی نیست |
| `companies[].maxUsers` | خیر | سقف کاربر این شرکت؛ نبودن = تابع سقف کل سند |
| `companies[].modules` | خیر | خالی = همهٔ ماژول‌های همین سند؛ پر = فقط همین‌ها |

## ۴) قاعده‌های اعتبارسنجی (پس از تأیید امضا، پیش از اعمال)

| کد | شدت | شرط |
|---|---|---|
| `COMPANY_ID_MISSING` | خطا | شرکتی بدون شناسه |
| `COMPANY_ID_DUPLICATE` | خطا | شناسهٔ تکراری در یک سند |
| `COMPANY_NAME_MISSING` | هشدار | نام نمایشی ندارد |
| `COMPANY_MODULE_UNKNOWN` | خطا | کد ماژول ناشناخته |
| `COMPANY_MODULE_OUT_OF_SCOPE` | خطا | ماژولی که در هیچ آیتم این سند فروخته نشده |
| `COMPANY_MODULE_ALWAYS_ON` | هشدار | ماژول همیشه‌فعال نام برده شده |
| `COMPANY_USERS_NEGATIVE` / `COMPANY_USERS_ZERO` | خطا / هشدار | سقف منفی / صفر |
| `COMPANY_USERS_EXCEED_SEATS` | خطا | جمع سقف شرکت‌ها > سقف کاربران سند |
| `COMPANY_USERS_PARTIAL` | هشدار | بخشی از شرکت‌ها سقف دارند و بخشی نه |
| `COMPANY_USERS_WITHOUT_POLICY` | هشدار | سقف شرکت داده شده ولی سند سیاست کاربری ندارد |
| `COMPANY_SEATS_OVER_CAP` | هشدار (لایهٔ ادغام) | جمع صندلی‌های ادغام‌شده از سقف مؤثر بیشتر است |

## ۵) ادغام چند سند (پایه + افزودنی)

- شرکتی که در چند سند آمده، **یک‌بار** در نتیجه می‌آید.
- ماژول‌ها = **اجتماع**؛ اگر یک سند برای آن شرکت فهرست ماژول را خالی گذاشته باشد، نتیجه «همهٔ ماژول‌های سند».
- سقف کاربر = **جمع** سقف‌های صریح (بستهٔ افزایشی صندلی)؛ اگر یکی از اسناد سقف نداده باشد، نتیجه «تابع سقف کل».

## ۶) کاربرد در کد (موتور لایسنس)

```csharp
var ent = EntitlementMerger.Merge(documents);   // نتیجهٔ همهٔ اسناد معتبر

ent.CompaniesRestricted            // آیا سندی فهرست شرکت داشته؟
ent.IsCompanyAllowed(companyId)    // تصمیم اصلی: این شرکت مجاز است؟
ent.FindCompany(companyId)         // جزئیات: نام، سقف کاربر، ماژول‌ها
ent.IsModuleAllowedForCompany(companyId, "sales")
ent.CompanySeatsAllocated          // جمع صندلی‌های تخصیص‌یافته
```

نمونهٔ گزارش (`LicenseCheck` با فایل لایسنس):

```
────────── شرکت‌های مجاز (از سند امضاشده) ──────────
  تعداد: 2  |  صندلی تخصیص‌یافته: 8
    • C-1001 شرکت الف  | کاربر: 5  | sales
    • C-1002 شرکت ب    | کاربر: 3  | همهٔ ماژول‌های سند
```

## ۷) ⚠️ نقطهٔ اعمال در نرم‌افزار اصلی (باقی‌مانده)

> تصمیم فعلی کارفرما: فعلاً فقط **دادهٔ امضاشده + گزارش**؛ اعمال سخت‌گیرانه در نرم‌افزار اصلی به
> مرحلهٔ بعد موکول شد. تا آن زمان، قاعده در سند هست ولی جلوی دور زدن را نمی‌گیرد.

برای اعمال، نرم‌افزار اصلی باید در نقاط «ساخت/فعال‌سازی/انتخاب شرکت» یک چک بگذارد:

```csharp
// نمونه — در سرویس شرکت‌ها، پیش از هر عملیات نوشتن
if (!entitlement.IsCompanyAllowed(company.Id))
    return Result.Fail("این شرکت در لایسنس فعلی مجاز نیست؛ برای افزودن آن لایسنس جدید لازم است.");
```

قاعده‌های پیشنهادی برای همان نقطه:

1. لیست شرکت‌های قابل انتخاب = `ent.Companies` (اگر `CompaniesRestricted`)؛ نه همهٔ ردیف‌های دیتابیس.
2. ساخت شرکت تازه وقتی `CompaniesRestricted` است ⇒ رد، با پیام روشن.
3. دسترسی ماژول در هر شرکت: `ent.IsModuleAllowedForCompany(companyId, module)`.
4. سقف کاربر هر شرکت: `ent.FindCompany(id)?.MaxUsers` در کنار سقف کل (`ent.Seats`).

بدون این چک، تنها چیزی که داریم «مستندسازی امضاشدهٔ» تعهد مشتری است، نه کنترل فنی.

## ۹) جریان کاری «هر شرکت، لایسنس خودش» (تأیید کارفرما)

```
شرکت فعال در نرم‌افزار (شرکت الف)
   └─ ادمین شرکت الف  ──►  درخواست لایسنس (installationId + companyId + ماژول‌های موردنیاز)
                                  │
                          پنل پشتیبانی: پیش‌نویس (شرکت = شرکت الف) → امضا
                                  │
   ادمین شرکت الف  ◄── فایل <سریال>.lic امضاشده
        │
        ├─ بارگذاری در نرم‌افزار (فقط همان شرکت)
        ├─ تعریف نقش‌ها و کاربران شرکت
        └─ کاربران به‌اندازهٔ ماژول‌های همان سند دسترسی می‌گیرند
```

پیامد فنی: نتیجهٔ ادغام «یکی برای کل نصب» کافی نیست؛ باید **به‌ازای هر شرکت** تفکیک شود.

### ۹.۱) `CompanyLicenseResolver` (موتور لایسنس)

```csharp
var resolver = CompanyLicenseResolver.Resolve(documents);   // همهٔ اسناد معتبر روی نصب

resolver.CompanyIds                       // شرکت‌هایی که سند دارند
var ent = resolver.For("C-A");            // لایسنس مؤثر فقط همان شرکت
resolver.HasLicense("C-A");               // آیا سند معتبر دارد؟
resolver.IsModuleAllowed("C-A", "sales"); // آیا این ماژول برای این شرکت مجاز است؟
resolver.SeatCap("C-A");                  // سقف صندلی مؤثر این شرکت
resolver.Unscoped                         // اسناد قدیمی بدون فهرست شرکت (نسبت داده نمی‌شوند)
```

قاعده‌های تفکیک:

| قاعده | چرا |
|---|---|
| هر شرکت فقط از اسنادی ساخته می‌شود که `companyId` او را دارند | سند شرکت ب نباید به شرکت الف ماژول بدهد |
| ماژول‌های سند با فهرست ماژول شرکت **اشتراک** گرفته می‌شود | سند ۵ ماژول می‌فروشد، شرکت فقط ۲ ماژول خریده |
| سقف صندلی = **کمینهٔ** سقف سند و سقف همان شرکت | شرکت نمی‌تواند از سهمیهٔ شرکت دیگر استفاده کند |
| شرکت بدون سند ⇒ `Status = Missing` و پیام روشن | «بدون لایسنس» نباید با «همه‌چیز مجاز» اشتباه شود |
| سند بدون `companies` به هیچ شرکتی نسبت داده نمی‌شود + هشدار `LICENSE_WITHOUT_COMPANY` | نسبت دادن آن یعنی بخشیدن ماژول به همه = دور زدن |

### ۹.۴) کاری که در نرم‌افزار اصلی لازم است (باقی‌مانده)

| نیاز | نقطهٔ پیشنهادی |
|---|---|
| صفحهٔ «لایسنس شرکت» برای ادمین همان شرکت (بارگذاری .lic) | در ماژول لایسنس/تنظیمات شرکت |

## ۹) قاعدهٔ عملیاتی: هر لایسنس = یک شرکت

از تاریخ ۱۴۰۵/۰۸/۲۴ جریان پنل تک‌شرکتی شد؛ موتور لایسنس همچنان چند شرکت را در یک سند می‌پذیرد
(برای سازگاری و آزمون‌ها)، ولی **فرم پیش‌نویس پنل** فقط یک شرکت می‌سازد:

| موضوع | رفتار |
|---|---|
| منبع هویت | شناسه و نام شرکت از **داخل فایل درخواست** خوانده و در `Requests.CompanyId/CompanyName` ذخیره می‌شود. |
| فرم پیش‌نویس | کارت «یک شرکت — یک لایسنس»: شناسه/نام فقط-خواندنی؛ فقط «سقف کاربر این شرکت» قابل ورود است. |
| تغییر دستی | فیلد متنی شرکت‌ها حذف شده؛ مقدار ارسالی دستی در فرم نادیده گرفته می‌شود. |
| چند شرکت | ذخیره با بیش از یک شرکت رد می‌شود: «هر لایسنس فقط برای یک شرکت صادر می‌شود…». |
| شرکت دیگر | درخواست و لایسنس جداگانه صادر کنید (همان نصب می‌تواند چند سند داشته باشد). |
| درخواست بدون شرکت | فرم یک خط دستی می‌پذیرد (`شناسه | نام | سقف‌کاربر | ماژول‌ها`) — باز هم فقط یک شرکت. |
| آزمون | `support-panel/tools/test-single-company.py` (۹ سنجه روی پنل در حال اجرا). |

## ۱۰) فایل درخواست، شناسهٔ شرکت را همراه می‌برد (۱۴۰۵/۰۸/۲۴)

**نشانه:** پنل پشتیبانی در فرم پیش‌نویس پیام می‌داد «در فایل درخواست این مشتری شناسهٔ شرکت نیامده است».

**علت:** `GET /api/license/request-file` نسخهٔ دومی بود که شرکت را در JSON نمی‌نوشت؛ فقط
`installationId` و نام مشتری را می‌فرستاد. پس پنل نمی‌توانست شناسهٔ شرکت را از سند بخواند و به
مسیر «ورود دستی» می‌افتاد — که خلاف قاعدهٔ «هر لایسنس برای یک شرکت، شناسه از فایل درخواست» است.

**اصلاح (افزایشی، بدون شکستن قالب):**

```json
{
  "requestVersion": 2,
  "installationId": "…",
  "customerName": "…",
  "companyId": "DLT-77",
  "companyName": "شرکت نمونهٔ دلتا",
  "company": { "id": "DLT-77", "name": "شرکت نمونهٔ دلتا" }
}
```

| قاعده | مقدار |
|---|---|
| منبع | اولین شرکت فعال نصب (`SystemCompanies` با `IsActive`، مرتب بر `Id`) — همان شرکتی که رکوردهای نصب به آن نسبت داده می‌شوند. |
| شناسه | `Code` شرکت؛ اگر خالی بود `C-{Id}` — یک قاعدهٔ ثابت و پایدار، تا هم پنل و هم سنجش «شرکت مجاز» بعدی یک شناسه را بخوانند. |
| نام | `Name` شرکت. |
| نصب بدون شرکت | فایل درخواست **بدون** فیلد شرکت ساخته می‌شود (هیچ شناسه‌ای جعل نمی‌شود)؛ پنل به رفتار قبلی برمی‌گردد. |

هر سه شکل (`companyId` تخت، `company` شیء، و آرایهٔ `companies`) در تجزیه‌گر پنل
(`RequestParser.ParseJson`) پشتیبانی می‌شود؛ قالب تازه فقط `companyId`/`companyName` ریشه و شیء
`company` را می‌فرستد، چون «هر لایسنس یک شرکت» است و آرایه باعث هشدار «چند شرکت» می‌شد.

**پیامد عملی:** فایل درخواستِ نسخه‌های قبلی همچنان شناسهٔ شرکت ندارد؛ برای آن‌ها باید از مشتری
فایل تازه گرفته شود (یا پشتیبان همان یک خط را دستی وارد کند).
