# تکرار تقویمی و حذف مجوزدار دستور کار

## رفتار کاربر

- **روزانه:** از تاریخ/ساعت اولین نوبت تا آخر همان ماه شمسی، شامل روز شروع و تعطیلات.
- **هفتگی:** فاصله دقیق هفت روز از اولین نوبت، تا آخر همان سال شمسی.
- **ماهانه:** همان شماره روز در ماه‌های شمسی بعد تا اسفند همان سال. برای روز ۳۰/۳۱ در ماه کوتاه‌تر، آخرین روز معتبر ماه انتخاب می‌شود؛ ساعت حفظ می‌شود.
- تاریخ اولین نوبت همان «تاریخ مقرر» فرم است. پایان از سال/ماه همین تاریخ محاسبه می‌شود، نه زمان ثبت فرم.
- نوبت‌ها هنگام ثبت، در یک تراکنش ساخته می‌شوند. هر نوبت شناسه، پاسخ، چک‌لیست، تأیید و وضعیت مستقل دارد؛ همه گیرندگان در هر نوبت عضو می‌شوند و آن را در تب **تقویم دستور کار** می‌بینند.
- بستن نوبت قبلی هیچ نوبت جدیدی نمی‌سازد. هنگام ساخت سری، هر گیرنده فقط یک اعلان خلاصه می‌گیرد؛ یادآورهای مهلت برای هر نوبت مستقل باقی می‌مانند.
- انتخاب الگوی تکرار در بخش زمان‌بندی فرم انجام می‌شود؛ راهنمای متنی پیش‌فرض از رابط حذف شده است.
- ویرایش یک نوبت سری فقط همان نوبت را تغییر می‌دهد. تغییر الگوی کل سری و حذف گروهی سری در این نسخه ارائه نشده است.
- انتخاب تکرار برای دستورِ بدون سری از طریق ویرایش، نوبت‌های بعدی را نیز ایجاد می‌کند.
- سری زیر‌دستور نمی‌تواند از مهلت والد عبور کند؛ درخواست جدید نامعتبر با پیام روشن رد می‌شود.
- پیوست‌های هر نوبت مستقل‌اند؛ فایل بارگذاری‌شده روی یک نوبت خودکار به تمام نوبت‌ها کپی نمی‌شود.

## حذف و نقش‌ها

مسیر: **تنظیمات ← نقش‌ها ← ویرایش نقش ← دستور کار ← حذف**.

مجوز `WorkOrders.Delete` مستقل از `View`، `Create` و `AssignOthers` است. نقش‌های عادی به صورت خودکار این مجوز را نمی‌گیرند؛ نقش Admin طبق الگوی فعلی همگام‌سازی مجوزها آن را دریافت می‌کند. مدیر قدیمی بدون نقش RBAC نیز طبق رفتار قبلی سامانه دسترسی کامل دارد. اگر کاربر نقش RBAC دارد، نقش غیرفعال یا عنوان Admin در توکن جای مجوز واقعی را نمی‌گیرد.

- API حذف: `DELETE /api/workorders/{id}`.
- API و رابط کاربری هر دو دسترسی را بررسی می‌کنند؛ علاوه بر مجوز حذف، کاربر باید اجازه مشاهده همان دستور را داشته باشد.
- دکمه حذف در فهرست دسکتاپ، کارت موبایل و جزئیات قرار دارد و قبل از حذف تأیید می‌گیرد.
- حذف، **منطقی و تک‌نوبتی** است: `DeletedAt` و `DeletedByUserId` ذخیره و رخداد `Deleted` ثبت می‌شود.
- فیلتر سراسری EF، دستور حذف‌شده را از تقویم، فهرست، گزارش‌ها، یادآورها و جزئیات حذف می‌کند؛ سوابق فیزیکی باقی می‌مانند. API پیوست‌های مشترک نیز دستور حذف‌شده را نمی‌پذیرد.
- دستور دارای زیر‌دستور حذف نمی‌شود؛ حذف آبشاری وجود ندارد. سایر نوبت‌های یک سری، زیر‌دستور محسوب نمی‌شوند.
- پس از تغییر نقش، صفحه دستور کار را بازخوانی کنید؛ در صورت کش بودن مجوزهای منو، خروج و ورود مجدد انجام دهید.

## ارتقا و نگهداری

`WorkOrderSchemaV2` هنگام راه‌اندازی API پس از V1 اجرا می‌شود و ستون‌های جدید و ایندکس یکتای `(RecurrenceSeriesId, RecurrenceScheduledAt)` را به SQLite یا SQL Server اضافه می‌کند. مانند سایر ارتقاهای خودترمیم پروژه است؛ مایگریشن‌های قبلی بازنویسی نشده‌اند. تاریخ اولیه نوبت برای ایندکس یکتا با تمدید یا ویرایش مهلت تغییر نمی‌کند.

پس از ارتقا، آخرین نوبت باز هر زنجیره قدیمی که هنوز سری تقویمی ندارد، نوبت‌های آینده‌اش را تا پایان بازه ایجاد می‌کند. نوبت تاریخیِ از دست‌رفته بازسازی نمی‌شود؛ دستور بسته‌شده باز نمی‌شود و زنجیره از نوبت‌های قبلی دوباره تولید نمی‌شود. در زیر‌دستورهای قدیمی، نوبت‌ها به مهلت والد محدودند. اجرای مجدد ارتقا، نوبت تکراری نمی‌سازد.

قبل از نصب روی دیتابیس اصلی، بکاپ بگیرید و روی یک کپی آزمایشی اجرا کنید. ارتقا داده‌های تولید را در این محیط اجرا نکرده است.

## آزمون

از ریشه مخزن، با .NET 8 SDK:

```bash
dotnet build inventory/Inventory.sln -m:1
dotnet test tests/work-orders/Inventory.WorkOrders.Tests.csproj -m:1
```

آزمون‌ها: پایان ماه/سال شمسی و کبیسه، ماه کوتاه، حفظ ساعت و روز هفته، تقویم همه گیرندگان، استقلال پاسخ‌ها، نبود تولید نوبت هنگام بستن، مجوز حذف، نقش غیرفعال، عدم حذف رکورد نامرتبط، حفظ سوابق، عدم بازتولید نوبت حذف‌شده، زیر‌دستور، تبدیل دستور ساده به سری، ارتقای زنجیره قدیمی و ارتقای تکرارپذیر اسکیمای SQLite.

بیلد API و Blazor و تست‌ها در محیط توسعه انجام شده‌اند. رابط جدید در Chromium، در اندازه دسکتاپ و موبایل با API آزمایشی بررسی شده است؛ اجرای عملی روی SQL Server انجام نشده است.
