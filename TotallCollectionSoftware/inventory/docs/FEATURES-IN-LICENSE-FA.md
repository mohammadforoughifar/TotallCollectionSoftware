# قابلیت‌های تفکیک‌شده داخل لایسنس — راهنمای کوتاه

این سند می‌گوید وقتی یک ماژول فروخته می‌شود ولی مشتری فقط بخشی از آن را می‌خواهد
(مثلاً «اتوماسیون اداری» هست، ولی فقط «نامهٔ وارده» مجاز است) چه چیزی در سند امضاشده می‌نشیند،
چطور در پنل انتخاب می‌شود و در نرم‌افزار چطور بررسی می‌شود.

---

## ۱) قاعدهٔ اصلی

| موضوع | قاعده |
|---|---|
| مالکیت | هر قابلیت **دقیقاً یک ماژول والد** دارد؛ بدون ماژول والد بی‌معناست. |
| اعتبار | قابلیت فقط وقتی در سند معتبر است که ماژول والدش در `scope` **همان آیتم** باشد. |
| کد ثابت | کدهای قابلیت در نرم‌افزار ثابت‌اند (`FeatureCodes`)؛ در سند فقط کد و عنوان می‌نشیند. |
| سازگاری عقب‌رو | سندی که هیچ قابلیتی تفکیک نکرده باشد، مثل قبل همهٔ امکانات ماژول‌های مجازش را دارد. |

## ۲) کاتالوگ فعلی

| کد قابلیت | عنوان | ماژول والد |
|---|---|---|
| `letter.incoming` | نامهٔ وارده | `letters` — اتوماسیون اداری |
| `letter.outgoing` | نامهٔ صادره | `letters` — اتوماسیون اداری |
| `letter.inner` | نامهٔ داخلی | `letters` — اتوماسیون اداری |

> منبع حقیقت: `inventory/src/Inventory.Licensing/Modules/FeatureCodes.cs`.
> افزودن قابلیت تازه = یک ردیف در همین فایل + استفاده از `HasFeature` در همان بخش نرم‌افزار؛
> بدون تغییر قالب سند و بدون بیلد برای مشتری (فقط `.lic` جدید).

## ۳) در پنل پشتیبانی (فرم پیش‌نویس)

- فهرست ماژول‌ها **چک‌باکسی و چندتایی** است و همان فهرستِ «فرم نقش‌ها» در تنظیمات نرم‌افزار را نشان می‌دهد.
- «بستهٔ آماده» از فرم حذف شده است؛ هر ماژول جداگانه تیک می‌خورد.
- قابلیت‌ها با تورفتگی زیر ماژول والد می‌آیند؛ تا ماژول تیک نخورد، چک‌باکس قابلیت غیرفعال است.
- ماژول‌های همیشه‌فعال (`core`, `dashboard`, `cartable`, `backup`, `licensing`) تیک‌خورده و غیرقابل تغییرند.
- «پیش‌نمایش ابزار» فهرست «قابلیت‌های تفکیک‌شده» را چاپ می‌کند؛ اگر قابلیتی بی‌والد باشد،
  پیش از امضا هشدار می‌دهد و آن را از سند بیرون می‌گذارد.

در پیش‌نویس ذخیره‌شده، قابلیت‌ها در آیتم `MANUAL` پروفایل می‌نشینند:

```json
{ "id": "MANUAL", "scope": ["letters", "sales"], "features": ["letter.incoming"] }
```

## ۴) در سند امضاشده

```json
"items": [
  { "id": "MANUAL", "scope": ["letters", "sales"], "features": ["letter.incoming"], "term": {...}, "users": {...} }
]
```

## ۵) اعتبارسنجی (پس از تأیید امضا)

| کد | شدت | معنا |
|---|---|---|
| `FEATURE_UNKNOWN` | خطا | کد قابلیت در نرم‌افزار نیست. |
| `FEATURE_MODULE_OUT_OF_SCOPE` | خطا | قابلیت آمده ولی ماژول والدش در `scope` همان آیتم نیست. |
| `FEATURE_DUPLICATE` | هشدار | همان قابلیت دوبار در یک آیتم. سند معتبر است. |

## ۶) در دسترسی مؤثر

- `EffectiveEntitlement.Features` = اجتماع قابلیت‌های آیتم‌های فعال.
- `FeaturesRestricted` = «سند قابلیت‌ها را تفکیک کرده است».
- `HasFeature("letter.incoming")`:
  1. اگر ماژول والد مجاز/نوشتنی نباشد ⇒ `false`.
  2. اگر سند قابلیتی تفکیک نکرده باشد ⇒ `true` (سازگاری عقب‌رو).
  3. وگرنه فقط وقتی `true` است که قابلیت در فهرست سند باشد.
- `CompanyLicenseResolver.IsModuleAllowed(companyId, module)` هم قبل از آن، دامنهٔ شرکت را اعمال می‌کند؛
  یعنی قابلیت برای شرکتی که ماژول والدش را ندارد، باز نمی‌شود.

## ۷) آزمون

```bash
cd inventory/test/support/feature-guard
dotnet run -c Release   # هر بند PASS/FAIL + کد خروج ۰ فقط وقتی همه سبز باشند
```

پوشش: قابلیت با والد، قابلیت بی‌والد، کد ناشناخته، تکراری، دسترسی مؤثر، سازگاری عقب‌رو.
