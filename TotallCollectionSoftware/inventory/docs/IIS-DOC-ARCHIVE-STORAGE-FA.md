# آرشیو اسناد روی IIS — محل ذخیرهٔ فایل‌ها و آدرس‌دهی

این سند نتیجهٔ بررسی مسیر ذخیره و آدرس‌دهی ماژول «آرشیو اسناد و مدارک» برای استقرار روی IIS است:
مشکلات پیدا‌شده، اصلاحات انجام‌شده و چک‌لیست نصب روی سرور.

## ۱) فایل مدارک کجا ذخیره می‌شود؟

همهٔ مسیرهای ارسال فایل مدرک از **یک** سرویس (`FileStore`) روی دیسک سرور ذخیره می‌شوند.
در دیتابیس فقط مسیر نسبی ثبت می‌شود (`DocVersion/{شناسه نسخه}/{guid}_{نام فایل}`)، نه خود فایل.

| مسیر ارسال | Endpoint | محل ذخیره |
|---|---|---|
| پیوست مدرک / نسخهٔ جدید (فرم مدرک، صفحهٔ مدرک) | `POST api/attachments/DocVersion/{versionId}` | `FileStore.SaveAsync` |
| ورود انبوه (انتخاب پوشه) | `POST api/doc-archive/import/batches/{id}/files` | `FileStore.SaveAsync` (همان نمونهٔ DI) |
| دانلود، پیش‌نمایش، چاپ، مقایسه، ZIP پوشه، OCR/ایندکس | — | `FileStore.ReadBytes` |

### تنظیم پوشهٔ ثابت روی سرور (حتماً روی IIS)

پیش‌فرض (تنظیم خالی) مثل قبل است: `wwwroot\uploads\DocVersion` **داخل پوشهٔ برنامه**.
روی IIS پوشهٔ برنامه با هر انتشار جایگزین می‌شود و ممکن است همهٔ مدارک پاک شوند. پس در `appsettings.json`:

```json
"DocArchive": {
  "StorageRoot": "D:\\InventoryData\\DocArchive"
}
```

- معادل متغیر محیطی (اگر appsettings با هر انتشار بازنویسی می‌شود): `DocArchive__StorageRoot`
  (در IIS: Configuration Editor → `system.webServer/aspNetCore` → `environmentVariables`).
- مسیر نسبی نسبت به پوشهٔ برنامه حل می‌شود؛ متغیر محیطی مثل `%ProgramData%\Inventory\DocArchive` هم مجاز است.
- مسیر شبکه (`\\fileserver\archive`) مجاز است، به شرط اینکه هویت Application Pool روی آن share دسترسی داشته باشد.
- فایل‌های قدیمی که در `wwwroot\uploads\DocVersion` هستند **همچنان پیدا می‌شوند** (مسیر نسبی دیتابیس عوض نشده).
  برای یکپارچگی می‌توانید محتوای آن پوشه را با همان زیرپوشه‌ها به مسیر جدید کپی کنید:
  ```powershell
  robocopy "C:\inetpub\inventory\wwwroot\uploads\DocVersion" "D:\InventoryData\DocArchive" /E /COPY:DAT
  ```
- فایل‌های این پوشه هیچ‌وقت مستقیم (static) سرو نمی‌شوند؛ دسترسی فقط از API با بررسی مجوز است.

### دسترسی نوشتن هویت Application Pool

```powershell
icacls "D:\InventoryData\DocArchive" /grant "IIS AppPool\<نام AppPool>:(OI)(CI)M"
```

هنگام راه‌اندازی، برنامه یک فایل آزمایشی در این پوشه می‌نویسد و پاک می‌کند و نتیجه را لاگ می‌کند:
- `[Storage] پوشهٔ فایل مدارک آرشیو: …` (خروجی stdout)
- اگر نوشتن ممکن نباشد یا مسیر داخل پوشهٔ برنامه باشد، **هشدار/خطا در Event Viewer → Application** ثبت می‌شود.

اگر کاربر فایلی بفرستد و دسترسی نوشتن نباشد، پیام روشن «ذخیرهٔ فایل روی سرور ناموفق بود…» می‌گیرد (نه خطای 500 خام)،
و در ورود انبوه همان ردیف «ناموفق» با همین توضیح در گزارش اکسل می‌آید.

## ۲) مشکلات پیدا‌شده و اصلاحات

| # | مشکل | اثر روی IIS | اصلاح |
|---|---|---|---|
| 1 | `app.Run("http://0.0.0.0:5100")` همیشه اجرا می‌شد | پروژه با `OutOfProcess` منتشر می‌شود؛ IIS پورت تصادفی (`ASPNETCORE_PORT`) می‌دهد ولی برنامه روی 5100 گوش می‌داد → **502** برای همهٔ درخواست‌ها | تشخیص اجرا پشت IIS (`ASPNETCORE_IIS_PHYSICAL_PATH` / `APP_POOL_ID`) و `app.Run()` بدون آدرس؛ شنوندهٔ HTTPS داخلی Kestrel و هدایت به 5443 هم پشت IIS غیرفعال است (HTTPS با binding خود IIS) |
| 2 | `inventoryApiBase` در index.html برای میزبان بدون پورت (IIS روی 80/443) به `http://localhost:5100` می‌رفت | مرورگر کاربر هیچ درخواستی (از جمله ارسال مدرک) را به سرور نمی‌فرستاد | هر میزبان غیرمحلی ← همان مبدأ صفحه + مسیر پایه |
| 3 | ورود انبوه `new FileStore(env)` می‌ساخت | از تنظیمات سراسری مسیر ذخیره بی‌خبر بود | تزریق همان `FileStore` سراسری (DI) |
| 4 | فایل در `wwwroot\uploads` داخل پوشهٔ برنامه | با انتشار جدید پاک می‌شود | تنظیم `DocArchive:StorageRoot` + هشدار راه‌اندازی |
| 5 | `ToFull` هر مسیری که «..» داشت را رد می‌کرد | فایلی با نام مثل `نامه..نهایی.pdf` ذخیره می‌شد ولی همیشه «فایل در دسترس نیست» | فقط بخش `..` (بالا رفتن از پوشه) رد می‌شود |
| 6 | کوتاه‌سازی نام به ۸۰ کاراکتر پسوند را می‌برید؛ نقطه/فاصلهٔ انتهای نام | ویندوز نقطهٔ انتهایی را حذف می‌کند و مسیر ثبت‌شده با فایل یکی نمی‌ماند | پسوند حفظ می‌شود، کاراکترهای غیرمجاز ویندوز مستقل از سیستم‌عامل جایگزین می‌شوند |
| 7 | نوشتن مستقیم فایل | قطع ارتباط وسط آپلود انبوه = فایل نیمه‌کاره با نام نهایی | نوشتن در `.part` و سپس تغییر نام (اتمیک) |
| 8 | خطای دیتابیس بعد از ذخیرهٔ فایل | فایل بی‌صاحب روی دیسک | پاک‌کردن فایل در صورت شکست ثبت (آپلود دستی و ورود انبوه) |
| 9 | «حذف قطعی» و «خالی کردن سطل بازیافت» فقط رکوردها را پاک می‌کرد | پر شدن تدریجی دیسک سرور | پاک‌کردن فایل فیزیکی پس از ثبت موفق (فقط اگر پیوست دیگری به آن اشاره نکند) |
| 10 | ستون `FileName` حداکثر ۲۵۵ کاراکتر؛ نام بلندتر خطای SQL می‌داد | آپلود ناموفق با خطای 500 | کوتاه‌سازی با حفظ پسوند؛ حذف `C:\fakepath\` |
| 11 | نصب زیر Application/Virtual Directory (مثلاً `http://server/erp/`) | `base href="/"`، درخواست‌های `"/api/..."` و سرویس‌ورکر از ریشهٔ سایت می‌خواندند | سرور `base href` را با `PathBase` می‌نویسد؛ `PathBaseHandler` در HttpClient؛ سرویس‌ورکر و صف آفلاین آرشیو مسیر پایه را می‌شناسند. روی ریشهٔ سایت هیچ تغییری ایجاد نمی‌شود |
| 12 | سقف حجم بدنهٔ Kestrel فقط داخل بلوک HTTPS برداشته می‌شد | پشت IIS (OutOfProcess) آن بلوک اجرا نمی‌شود و سقف پیش‌فرض ۳۰ مگابایت Kestrel آپلودهای بزرگ را با 413 رد می‌کرد | برداشتن سقف سراسری در تنظیم عمومی Kestrel؛ سقف هر endpoint (`[RequestSizeLimit]`) و محدودیت‌های خود برنامه مثل قبل اعمال می‌شود |
| 13 | خطای ذخیرهٔ فایل در ورود انبوه | پاسخ به مرورگر «Pending» با پیام خالی بود («وارد نشد» بی‌دلیل) و شمارش «ناموفق» نوبت ذخیره نمی‌شد | بارگذاری دوبارهٔ ردیف و نوبت پس از برگشت تراکنش؛ پیام روشن «ذخیرهٔ فایل روی دیسک سرور ناموفق بود…» |
| 14 | مرحلهٔ ۲ اسکریپت `deploy-single.ps1`/`.sh` همهٔ محتوای `src/Inventory.Api/wwwroot` را پاک می‌کرد | اگر برنامه روی همان سیستم از سورس اجرا شده بود، پوشهٔ `uploads` (مدارک ذخیره‌شده) با هر بیلد انتشار پاک می‌شد | `uploads` و `SecureFiles` از پاک‌سازی مستثنا شدند (خروجی انتشار همچنان بدون این پوشه‌هاست تا روی فایل‌های سرور نوشته نشود) |

## ۳) چک‌لیست نصب روی IIS

1. **ASP.NET Core Hosting Bundle 8** روی سرور نصب باشد.
2. Application Pool: `.NET CLR Version = No Managed Code`.
3. خروجی کلاینت در `wwwroot` پروژهٔ API کپی شده باشد (طبق `src/Inventory.Api/wwwroot/README.md` یا `deploy-single.ps1`)، سپس `dotnet publish` پروژهٔ API.
4. `DocArchive:StorageRoot` روی مسیر ثابت بیرون از پوشهٔ برنامه + `icacls` بالا.
5. دسترسی Modify هویت AppPool روی `App_Data` پوشهٔ برنامه (کلیدهای DataProtection) هم لازم است.
6. بعد از اولین اجرا در Event Viewer هشدار `[Storage]` نباشد.
7. تست: یک مدرک با پیوست بسازید، یک پوشهٔ کوچک را «ورود انبوه» کنید و بررسی کنید فایل‌ها در `StorageRoot` نشسته‌اند؛
   سپس سایت را Recycle کنید و پیش‌نمایش/دانلود را دوباره امتحان کنید.
8. سقف حجم: `web.config` اجازهٔ ۴ گیگابایت می‌دهد؛ سقف واقعی هر فایل مدرک ۱۰ مگابایت است
   (`DocArchiveImport:MaxFileBytes` برای ورود انبوه).

## ۴) تست خودکار

```bash
cd inventory/tests/DocArchiveStorage && dotnet run
```

روی کد واقعی اجرا می‌شود: ذخیره با/بدون `StorageRoot`، شبیه‌سازی انتشار مجدد، فایل‌های قدیمی، نام‌های مشکل‌دار،
Path Traversal، ورود انبوه با SQLite (موفق و خطای دسترسی دیسک)، حذف قطعی، و بازنویسی آدرس زیر مسیر پایهٔ IIS.

نتیجهٔ آخرین اجرا: **۴۵ بررسی، همه موفق**؛ تست‌های امنیتی موجود `tests/DocArchiveSecurity` هم بعد از تغییرات: **۱۰۴ بررسی، همه موفق**.

### شبیه‌سازی میزبانی IIS (OutOfProcess زیر Application «erp»)

خود API با متغیرهایی اجرا شد که ماژول ASP.NET Core در IIS به پروسه می‌دهد
(`ASPNETCORE_PORT`، `ASPNETCORE_TOKEN`، `ASPNETCORE_APPL_PATH=/erp`) و `DocArchive__StorageRoot` روی یک پوشهٔ بیرونی:

| بررسی | نتیجه |
|---|---|
| گوش دادن روی پورت داده‌شده توسط IIS (`127.0.0.1:ASPNETCORE_PORT`) به‌جای 5100 | ✔ |
| `GET /erp/` و لینک عمیق `/erp/doc-archive/...` ← `index.html` با `<base href="/erp/" />` | ✔ |
| `/erp/_framework/...` ← 200؛ `/erp/api/...` بدون توکن ← 401 (نه 404/HTML) | ✔ |
| ورود انبوه دو فایل (نام فارسی، زیرپوشه، نام دارای «..») ← Imported، فایل‌ها در پوشهٔ بیرونی، هیچ فایلی در `wwwroot\uploads\DocVersion` | ✔ |
| دانلود همان پیوست از `/erp/api/attachments/download/{id}` ← 200 و محتوای درست | ✔ |
| آپلود تکی با نام `C:\fakepath\گزارش: نهایی?.pdf` ← نام اصلی در دیتابیس، نام امن روی دیسک، دانلود 200 | ✔ |
| درخواست ۳۵ مگابایتی به برنامه رسید (دیگر 413 از Kestrel نیست؛ پیام سقف ۱۰ مگابایتی خود برنامه برگشت) | ✔ |
| پوشهٔ ذخیره بدون دسترسی نوشتن ← ردیف Failed با پیام روشن فارسی، شمارش «ناموفق» نوبت = ۱، لاگ خطا با راهنمای دسترسی AppPool | ✔ |
