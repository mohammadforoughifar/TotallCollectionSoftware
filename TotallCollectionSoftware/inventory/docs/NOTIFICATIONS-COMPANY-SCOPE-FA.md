# نمایش اعلان‌ها بر اساس «شرکت فعال» — یادداشت پیاده‌سازی

> هدف: در سامانهٔ فروشگاهی (ویزیتوری) و هر جای دیگری که اعلان به دادهٔ یک شرکت مربوط است،
> اعلان فقط وقتی دیده شود که **همان شرکت در کمبوی بالای برنامه فعال** باشد؛ هرگز فهرست
> درهم‌آمیختهٔ چند شرکت نمایش داده نشود. اعلان‌های عمومی سامانه (چت، IT، منابع انسانی،
> اتوماسیون اداری، فروغ آریا) مثل قبل در همهٔ شرکت‌ها دیده می‌شوند.

## ۱) قاعدهٔ نمایش

| مقدار `CompanyId` اعلان | معنا | کجا دیده می‌شود |
|---|---|---|
| `NULL` | اعلان عمومی/سیستمی | در **همهٔ** شرکت‌ها |
| عدد (مثلاً `3`) | اعلان دادهٔ همان شرکت | فقط وقتی شرکت ۳ فعال است |
| `NULL` و اعلان قدیمی (پیش از این تغییر) | عمومی به‌صورت پیش‌فرض | همهٔ شرکت‌ها (سازگاری با گذشته) |

شرط نمایش در سرور:

```csharp
company > 0
    ? q.Where(n => n.CompanyId == null || n.CompanyId == company)
    : q.Where(n => n.CompanyId == null);          // بدون زمینهٔ شرکت → فقط عمومی
```

`company` همان «شرکت فعال» درخواست است که میان‌افزار `ActiveCompanyMiddleware` از هدر
`X-Company-Id` (با اعتبارسنجی دسترسی کاربر) تعیین و در `HttpContext.Items["ActiveCompanyId"]`
می‌گذارد. مقدار `0` یعنی «کاربر به هیچ شرکتی دسترسی ندارد» و مطابق سیاست fail-closed بقیهٔ
سامانه، هیچ دادهٔ شرکتی دیده نمی‌شود. اگر شرکتی در سیستم تعریف نشده باشد (نصب تک‌شرکتی قدیمی)،
کلید زمینه ست نمی‌شود و همان «فقط عمومی» اعمال می‌شود.

## ۲) چرا `ICompanyOwned` نیست

`AppNotification` عمداً به الگوی `ICompanyOwned` / فیلتر سراسری `HasQueryFilter` وصل **نشده** است.
آن الگو در `AppDbContext.ApplyCompanyScopeOnSave` شرکت فعال را روی رکورد جدید «مهر» می‌کند؛
نتیجه این بود که اعلان چت یا منبع انسانی هم شرکت‌دار می‌شد و از شرکت دیگر پنهان می‌ماند.
اینجا `CompanyId` یک صفت اختیاری است و «نبودِ مقدار» خودش معنا دارد: عمومی.

## ۳) تغییرات دیتابیس

- ستون: `AppNotifications.CompanyId int NULL`
- ایندکس: `IX_AppNotifications_UserId_CompanyId` روی `(UserId, CompanyId, IsRead)`
- فایل خودتعمیر: `inventory/src/Inventory.Api/Data/NotificationCompanySchemaV1.cs`
  - مسیر SQL Server: `ALTER TABLE` و `CREATE INDEX` با نگهبان `IF` (اجرای دوباره بی‌خطر است).
  - مسیر SQLite: بررسی `PRAGMA table_info` و `CREATE INDEX IF NOT EXISTS`.
  - فراخوانی در `DbInitializer` **هر دو شاخه** (SQLite و SQL Server)، کنار سایر `*SchemaV1`.
- مایگریشن دست‌نویس (هم‌راستا با بقیهٔ مایگریشن‌های این مخزن، بدون Designer):
  `inventory/src/Inventory.Api/Migrations/20261108120000_AddNotificationCompany.cs`
  - `Up`: نگهبان `ActiveProvider` (روی SQLite خطا می‌دهد؛ مثل بقیه) و اجرای همان `SqlServer`.
  - `Down`: `NotSupportedException` — حذف ستون نسبت‌دادن اعلان به شرکت را از بین می‌برد.
- `AppDbContextModelSnapshot` و نگاشت `AppDbContext` هم به‌روز شده‌اند.

رکوردهای قدیمی `NULL` می‌مانند (Backfill انجام نمی‌شود) چون هیچ اطلاعاتی برای نسبت‌دادن آن‌ها
به یک شرکت وجود ندارد؛ رفتارشان همان رفتار گذشته است.

## ۴) سرویس اعلان (`INotifyService`)

امضاها سازگار با قبل شده‌اند و پارامتر اختیاری `companyId` از انتها اضافه شده است:

```csharp
Task SendAsync(int userId, string title, string? body, string fromName, string formName,
               string? link, int? companyId = null);
Task SendManyAsync(IEnumerable<int> userIds, ... , string? link, int? companyId = null);
Task SendToRoleAsync(string roleName, ... , string? link, int? companyId = null);
```

- `companyId <= 0` به `null` نرمال می‌شود (یعنی عمومی).
- عنوان ذخیره‌شدهٔ اعلان دست‌نخورده می‌ماند؛ فقط **عنوان اعلان گوشی (Web Push)** به شکل
  `[نام شرکت] عنوان` پیشوند می‌گیرد، چون روی گوشی «شرکت فعال» معنا ندارد و کاربر باید بداند
  اعلان به کدام شرکت مربوط است. خطای واکشی نام شرکت، ارسال را نمی‌شکند.
- پیام بلادرنگ SignalR (`notify` روی گروه `u{userId}`) اکنون `CompanyId` را هم می‌فرستد.
- ارسال به پیام‌رسان‌ها (بله/ایتا) مثل قبل با همان متن است.

## ۵) فرستنده‌ها

| فرستنده | وضعیت |
|---|---|
| `Services/SalesVisit/VisOrderService.cs` | **شرکت‌دار**: `order.CompanyId` (شرکتِ خودِ سفارش، نه شرکتِ جاری درخواست) |
| چت، IT، منابع انسانی، اتوماسیون اداری، FaAtt، پروژه‌ها، اسناد | عمومی (`NULL`) — رفتار قبلی حفظ شده |
| `FaAttService.NotifyAsync` و درخواست‌های اسناد | عمومی |

قاعدهٔ کلی: هر اعلانی که به **دادهٔ شرکتی** اشاره می‌کند باید `companyId` همان داده را بدهد؛
اعلان‌هایی که به کاربر/سامانه مربوط‌اند (نه به دادهٔ یک شرکت) عمومی می‌مانند.

## ۶) API

`Controllers/System/NotificationsController.cs` — همهٔ مسیرهای خواندن/شمارش/علامت‌گذاری با
`VisibleToActiveCompany(...)` محدود شده‌اند:

| مسیر | اثر |
|---|---|
| `GET /api/notifications` | فهرست ساده؛ فقط شرکت فعال + عمومی، همراه `companyId` |
| `GET /api/notifications/page` | فهرست صفحه‌بندی‌شده + `companyId` و `companyName` هر ردیف؛ `total`/`unread` هم محدود |
| `GET /api/notifications/unread-count` | شمارندهٔ زنگوله — فقط شرکت فعال + عمومی |
| `POST /api/notifications/read-all` | فقط اعلان‌های قابل‌مشاهده |
| `DELETE /api/notifications/clear-all` | فقط اعلان‌های قابل‌مشاهده (اعلان شرکت دیگر پاک نمی‌شود) |
| `POST /api/notifications/{id}/read` | فقط اعلان خودِ کاربر (بدون تغییر نسبت به قبل) |

`companyName` در `page` با یک کوئری دسته‌ای روی `SystemCompanies` پر می‌شود (بدون N+1).

## ۸) سناریوهای پذیرش

1. کاربر دارای دو شرکت A و B؛ اعلان سفارش شرکت A ساخته می‌شود.
   - شرکت فعال A → اعلان در زنگوله، توست، کارتابل و شمارنده دیده می‌شود.
   - شرکت فعال B → هیچ‌کدام از آن‌ها دیده نمی‌شود (نه فقط پنهان‌شدن بصری؛ شمارنده هم کم است).
2. اعلان چت (عمومی) → در هر دو شرکت دیده می‌شود.
3. «علامت‌گذاری همه به‌عنوان خوانده» در شرکت B، اعلان شرکت A را نخوانده باقی می‌گذارد.
4. «پاک کردن همه» در شرکت B، اعلان شرکت A را حذف نمی‌کند.
5. سفارش تغییر شرکت می‌دهد (اگر دادهٔ قدیمی `CompanyId` دارد) → اعلان با شرکت سفارش مهر می‌شود،
   نه شرکتِ کاربر در آن لحظه.
6. کاربر بدون دسترسی به هیچ شرکت → فقط اعلان‌های عمومی.
7. نصب تک‌شرکتی/قدیمی بدون `SystemCompanies` → فقط اعلان‌های عمومی؛ خطا ندارد.

## ۹) استقرار

- **ترتیب انتشار:** ابتدا API (ستون + ایندکس ساخته می‌شود) و بعد کلاینت. کلاینت قدیمی روی API جدید
  هم کار می‌کند (فیلدهای اضافی را نادیده می‌گیرد) و فقط اعلان‌های شرکت فعال را می‌بیند.
- پیش از ارتقا نسخهٔ پشتیبان بگیرید. `NotificationCompanySchemaV1` در هر دو مسیر SQLite/SQL Server
  خودتعمیر است و اجرای دوباره‌اش بی‌خطر است.
- روی دیتابیس بزرگ، `ALTER TABLE ADD` ستون `NULL` سبک است؛ ساخت ایندکس روی `AppNotifications`
  معمولاً کوتاه است، ولی در ساعات کم‌ترافیک انجام شود.
- پس از انتشار، اعلان‌های قدیمی (بدون شرکت) همان‌طور که بودند در همهٔ شرکت‌ها دیده می‌شوند؛ اگر
  لازم شد، پاک‌سازی اعلان‌های قدیمی از همان صفحهٔ زنگوله (شرکت‌به‌شرکت) انجام شود.
