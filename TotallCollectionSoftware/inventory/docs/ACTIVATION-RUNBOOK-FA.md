# راهنمای گام‌به‌گام فعال‌سازی لایسنس مشتری

**نسخه:** ۱ · **تاریخ:** ۱۴۰۵/۰۸/۲۴ · **مخاطب:** تیم پشتیبانی و ادمین شرکت مشتری

> این سند «دستور کار» است: از لحظه‌ای که ادمین شرکت درخواست می‌فرستد تا لحظه‌ای که کاربرانش
> وارد سیستم می‌شوند — با دستورهای دقیق، نقطه‌های بازرسی و جدول عیب‌یابی.
> اگر خطای «کلید امضا شناخته‌شده نیست» گرفتید، مستقیم بروید به [بخش ۰](#۰-قاعدهٔ-طلایی-و-همان-خطای-تکراری).

## ۰) قاعدهٔ طلایی (و همان خطای تکراری)

**کلید عمومی امضا داخل فایل اجرایی محصول جاسازی می‌شود، نه در فایل لایسنس.**
پس:

| واقعیت | نتیجه |
|---|---|
| هر بار کلید عمومی عوض شود (یا کلید تازه ساخته شود) | **یک‌بار** بیلد/انتشار Release لازم است |
| هر مشتری تازه، تمدید، افزودن شرکت یا ماژول | **هیچ** بیلدی لازم نیست؛ فقط فایل `.lic` جدید |

خطای زیر یعنی **نصب قدیمی است**، نه اینکه فایل لایسنس خراب باشد:

```
کلید امضای «sup-202611» روی این نصب شناخته‌شده نیست.
فایل باید با یکی از کلیدهای معتبر صادر شده باشد.
```

### تشخیص ریشه‌ای در یک دستور

اسمبلی‌ای که واقعاً روی سرور/مشتری اجرا می‌شود را بازرسی کنید (هیچ چیزی اجرا نمی‌شود، فقط خوانده می‌شود):

```powershell
dotnet LicenseTool.dll keys --dir "D:\deploy\inventory-server" --expect sup-202611
```

خروجی خراب (همان خطای شما):

```
  ⛔ کلید «sup-202611» در manifest این بیلد نیست ⇒ خطای «کلید شناخته‌شده نیست» طبیعی است.
```

| کد خروج | معنا | کار |
|---|---|---|

| `6` | کلید در این بیلد نیست | انتشار Release تازه از سورس دارای کلید + جایگزینی نصب |
| `2` | اسمبلی/پوشه پیدا نشد | مسیر درست را بدهید (برای Single-File خودِ `app.exe` را با `--assembly` بدهید) |

> اگر در گزارش بالا این عدد نبود، کلید نصب شما با کلید امضاکننده یکی نیست.

## ۱) پیش‌نیاز یک‌بارهٔ محصول (فقط یک‌بار برای هر کلید)

1. سورس محصول شامل این‌ها باشد:
   - `inventory/src/Inventory.Licensing/Keys/manifest.json` با ردیف `sup-202611` و `debugOnly: false`
   - `inventory/src/Inventory.Licensing/Keys/sup-202611.pem` (کلید عمومی)
2. `git log -1 --oneline` باید `3a8911e` یا جدیدتر باشد.
3. انتشار تازه:
   ```powershell
   dotnet clean ; dotnet publish <پروژهٔ سرور> -c Release -o D:\deploy\inventory-server
   ```
4. تأیید پیش از تحویل:
   ```powershell
   dotnet LicenseTool.dll keys --dir D:\deploy\inventory-server --expect sup-202611   # باید 0 برگرداند
   dotnet LicenseCheck.dll --keys                                                     # باید «تعداد: 1 • sup-202611» بدهد
   ```
5. جایگزینی نصب مشتری (کل پوشهٔ انتشار؛ اگر IIS است، App Pool را ری‌استارت کنید).

> ⛔ هرگز برای «مشتری جدید» این مرحله را تکرار نکنید. فقط وقتی کلید عوض شود.
> ⛔ کلید خصوصی (`*.private.pem`) هرگز روی سرور/ماشین مشتری یا در مخزن گذاشته نمی‌شود.

## ۲) سمت مشتری: فرستادن درخواست

ادمین **همان شرکت** از داخل نرم‌افزار «درخواست لایسنس» می‌سازد. فایل JSON باید این‌ها را داشته باشد:

```json
{
  "requestVersion": 2,
  "requestType": "new",
  "installationId": "<شناسهٔ همین نصب — از صفحهٔ لایسنس نرم‌افزار>",
  "customerName": "نام شرکت",
  "contactName": "نام ادمین",
  "contactPhone": "…",
  "deployment": "OnPrem",
  "modules": ["sales", "hr_fa"],
  "companies": [ { "companyId": "C-1001", "name": "شرکت الف" } ],
  "users": 10
}
```

| فیلد | چرا مهم است |
|---|---|
| `installationId` | فایل فقط روی همان نصب معتبر است (`INSTALLATION_MISMATCH` در غیر این صورت) |
| `companies[0].companyId` | همان شرکتی که لایسنس برایش صادر می‌شود؛ با ویرایش دیتابیس قابل جعل نیست |
| `modules` | پیشنهاد برای پیش‌نویس (پشتیبان می‌تواند تغییر دهد) |
| `users` | برآورد اولیهٔ سقف صندلی |

---

## ۳) سمت پشتیبانی: از درخواست تا فایل امضاشده

1. **ثبت درخواست:** پنل → `درخواست‌ها → ثبت درخواست` → محتوای JSON را بچسبانید → «ثبت».
   نتیجه: شمارهٔ پرونده (`REQ-…`) و ثبت `companyId` و ماژول‌های درخواستی.
2. **بررسی هویت:** `پرونده → بررسی هویت` (تماس با شمارهٔ ثبت‌شده) → تأیید.
3. **پیش‌نویس:** `پرونده → پیش‌نویس امضا`
   - **ماژول‌ها (چک‌باکسی):** فهرست کامل ماژول‌های برنامه، همان فهرستِ فرم نقش‌ها در تنظیمات،
     گروه‌بندی‌شده و چندتایی. «بستهٔ آماده» از فرم حذف شده است؛ هر ماژول را جدا تیک بزنید.
     ماژول‌های پایه (`core`, `dashboard`, `cartable`, `backup`, `licensing`) همیشه‌فعال‌اند:
     تیک‌خورده و غیرقابل تغییر.
   - **قابلیت‌های داخلی:** زیر هر ماژول با تورفتگی می‌آیند؛ مثلاً «نامهٔ وارده» (`letter.incoming`)،
     «نامهٔ صادره» و «نامهٔ داخلی» زیر «اتوماسیون اداری» (`letters`). تیک ماژول، قابلیت‌هایش را باز می‌کند.
     اگر ماژول تیک نخورد، پنل قابلیتش را ثبت نمی‌کند (دلیلش را هم می‌نویسد).
   - مدت، حالت کاربر، سقف کاربر.
   - **شرکت‌های مجاز:** یک خط برای شرکت درخواست‌کننده، مثال:
     ```
     C-1001 | شرکت الف | 10 | sales,hr_fa
     ```
     فقط شناسه اجباری است. جمع سقف شرکت‌ها از «سقف کاربر» بیشتر نشود.
   - «پیش‌نمایش ابزار» ⇒ باید بخش «شرکت‌های مجاز» و «قابلیت‌های تفکیک‌شده» را ببینید.
4. **امضا:** `پرونده → امضا` با Key ID = `sup-202611`، گذرواژهٔ کلید خصوصی، تیک بازبینی.
   > اگر ابزار هشدار داد «کلید … در حلقهٔ اعتماد بیلد محصول نیست»، امضا نکنید؛ فایل روی نصب مشتری
   > کار نمی‌کند. اول بخش ۰ را حل کنید.
5. **تحویل:** `.eml` / SMTP / ثبت دستی. فایل نهایی: `<سریال>.lic`.

## ۴) سمت مشتری: بارگذاری و راه‌اندازی

1. ادمین شرکت فایل `.lic` را در `صفحهٔ لایسنس` بارگذاری می‌کند.
   سیستم این‌ها را چک می‌کند: امضا → `installationId` → `companyId` → سریال تکراری نبودن.
2. کنترل‌های بعد از بارگذاری:
   - `صفحهٔ لایسنس` وضعیت را «فعال» نشان دهد و ماژول‌های فعال فهرست شوند.
   - `/api/health` فیلد `licensing` داشته باشد.
   - در گزارش خطا هیچ‌کدام از `INSTALLATION_MISMATCH`، `SERIAL_ALREADY_APPLIED` یا `کلید … شناخته‌شده نیست` نباشد.
3. ادمین شرکت **نقش‌ها و کاربران** را تعریف می‌کند؛ دسترسی هر کاربر به ماژول‌ها = ماژول‌های همان سند.
4. شروع کار. (تمدید/افزودن ماژول یا شرکت ⇒ فایل `.lic` جدید؛ باز هم بدون بیلد.)

## ۵) جدول عیب‌یابی — پیام دقیق ⇒ علت ⇒ کار

| پیام / کد | علت ریشه‌ای | کار |
|---|---|---|
| «کلید امضای «X» روی این نصب شناخته‌شده نیست» | کلید در بیلد نصب نیست (نصب قدیمی یا Single-File قدیمی) | `LicenseTool keys --dir … --expect X`؛ انتشار Release تازه + جایگزینی |
| «امضای فایل لایسنس معتبر نیست» | کلید درست است ولی فایل با کلید دیگری امضا شده، یا فایل دست‌کاری شده | اثر انگشت کلید امضاکننده را با manifest مقایسه کنید؛ فایل را دوباره صادر/ارسال کنید |
| `INSTALLATION_MISMATCH` | فایل برای نصب دیگری صادر شده | درخواست با `installationId` درست؛ صدور مجدد |
| `SERIAL_ALREADY_APPLIED` | همان فایل قبلاً اعمال شده | فایل جدید همان لایسنس را ندهید؛ اگر تمدید است، سریال تازه صادر کنید |
| `DEPLOYMENT_MISMATCH` | فایل SaaS برای OnPrem (یا برعکس) | پیش‌نویس با `OnPrem` |
| `FEATURE_MODULE_OUT_OF_SCOPE` | قابلیتی در سند هست که ماژول والدش در scope همان آیتم نیست | ماژول والد (مثلاً `letters`) را تیک بزنید و دوباره پیش‌نویس کنید |
| `FEATURE_UNKNOWN` | کد قابلیت در نرم‌افزار وجود ندارد | کد را از فهرست فرم پیش‌نویس بردارید (کدها ثابت‌اند) |
| `FEATURE_DUPLICATE` (هشدار) | یک قابلیت دو بار در یک آیتم | فقط یک بار تیک بزنید؛ سند معتبر است ولی پیام می‌آید |
| `COMPANY_MODULE_OUT_OF_SCOPE` | شرکت ماژولی دارد که در سند فروخته نشده | ماژول را به پیش‌نویس اضافه کنید یا از فهرست شرکت حذف |
| `COMPANY_USERS_EXCEED_SEATS` | جمع سقف شرکت‌ها > سقف کاربران سند | سقف کاربر را بالا ببرید یا سهم شرکت‌ها را کم کنید |
| `COMPANY_LICENSE_MISSING` (در گزارش `companies`) | برای این شرکت هیچ سند معتبری روی نصب نیست | ادمین همان شرکت باید `.lic` خودش را بارگذاری کند |
| `LICENSE_WITHOUT_COMPANY` | سند قدیمی که `companies` ندارد | سند جدید با `companyId` صادر کنید |
| `TERM_ALREADY_EXPIRED` | تاریخ پایان گذشته | تمدید |
| «بدون --yes امضا نشد» (کد ۳) | پیش‌نمایش است، نه خطا | با `--yes` اجرا کنید یا از پنل امضا کنید |

## ۶) برگهٔ دستورهای سریع

```powershell
# یک‌بار برای هر کلید: تأیید بیلد محصول
dotnet LicenseTool.dll keys --dir D:\deploy\inventory-server --expect sup-202611
dotnet LicenseCheck.dll --keys

# هر مشتری: صدور از پنل انجام می‌شود؛ برای صدور خط فرمان:
dotnet LicenseTool.dll issue --profile profile.json --installation-id <id> \
    --private-key <path>\sup-202611.private.pem --key-id sup-202611 --out out.lic
# (بدون --yes فقط پیش‌نمایش است)

# بازبینی فایل پیش از ارسال
dotnet LicenseTool.dll verify out.lic --installation-id <id> --public-key sup-202611.pem

# وضعیت شرکت‌ها روی یک نصب (چند شرکت)
dotnet LicenseTool.dll companies a.lic b.lic --public-key sup-202611.pem
```

```bash
# روی لینوکس/سرور: بازرسی اسمبلی
dotnet LicenseTool.dll keys --assembly /opt/inventory/Inventory.Licensing.dll --expect sup-202611
```
