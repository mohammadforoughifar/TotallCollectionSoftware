# خطای «امضای فایل لایسنس معتبر نیست» (LICENSE_REJECTED) — تشخیص و رفع

_آخرین به‌روزرسانی: ۱۴۰۵/۰۸/۲۶_

## ۱) این خطا یعنی چه؟

پیام مشتری:

```
LICENSE_REJECTED — فایل لایسنس رد شد: امضای فایل لایسنس معتبر نیست
(محتوای فایل تغییر کرده یا کلید اشتباه است).
```

این متن از `KeyVerify.Verify` در `Inventory.Licensing/Crypto/PublicKeyRing.cs` می‌آید و **فقط یک معنا** دارد:

> شناسهٔ کلید (`keyId`) در فایل لایسنس شناخته شد و کلید عمومی‌اش هم پیدا شد،
> ولی **امضای دیجیتال با آن کلید عمومی جور در نیامد**.

اگر شناسهٔ کلید ناشناخته بود، پیام دیگری می‌آمد («کلید امضای … روی این نصب شناخته‌شده نیست»).
پس دو حالت باقی می‌ماند:

| حالت | توضیح | نشانه |
|---|---|---|
| **الف) کلید اشتباه** | کلید خصوصی‌ای که امضا کرده، جفتِ کلید عمومیِ جاسازی‌شده در نصب مشتری نیست | با `doctor` معلوم می‌شود |
| **ب) تغییر فایل** | فایل لایسنس پس از امضا دست‌کاری/تبدیل شده (ویرایش دستی، تبدیل کدگذاری، کپی ناقص) | `doctor --license` می‌گوید «کلیدها یکی هستند» ولی امضا نمی‌خواند |

## ۲) تشخیص بدون خط فرمان (از داخل پنل)

پنل ← **تنظیمات** ← کارت **«تشخیص: چرا مشتری «امضای فایل لایسنس معتبر نیست» می‌گیرد؟»**:

1. رمز کلید خصوصی را در کادر بگذارید و **«۱) کلید امضا با کلید محصول می‌خواند؟»** را بزنید.
   * نتیجهٔ سبز («✔ کلید امضا با کلید داخل محصول می‌خواند») ⇒ problem در کلید نیست؛ برو به حالت ب.
   * نتیجهٔ سرخ («❌ کلید امضا با کلید داخل محصول نمی‌خواند») ⇒ حالت الف؛ همان‌جا راه رفع نوشته می‌شود.
2. برای اطمینان از خود فایل، از فهرست **«۲) همین فایل روی نصب مشتری پذیرفته می‌شود؟»** فایل لایسنس را
   انتخاب و بررسی کنید — این دقیقاً همان کاری است که نصب مشتری انجام می‌دهد.

> این کارت اثر انگشت کلیدِ امضا را از خود کلید خصوصی مشتق می‌کند و با اثر انگشت کلیدهای جاسازی‌شده
> در بیلد محصول مقایسه می‌کند؛ فقط `keyId` مقایسه نمی‌شود (همان چیزی که قبلاً از چشم پنهان می‌ماند).

## ۳) تشخیص با خط فرمان (برای خودتان یا سرور)



روی **ماشین پشتیبانی** (همان‌جا که کلید خصوصی هست):

```bash
export LICENSETOOL_KEY_PASSWORD='رمز کلید خصوصی'      # در تاریخچهٔ شل نماند
dotnet LicenseTool.dll doctor --private-key /path/keys/sup-202611.private.pem
```

خروجی نمونه (کلید سالم):

```
■ کلیدهای جاسازی‌شده در این بیلد محصول:
   • sup-202611  RS256  اثر انگشت: 47d2032f86afedc76162be99ed7094cfd7d8274901ced34479a57951b58ac07a

■ کلید امضا (از کلید خصوصی): 47d2032f86afedc76162be99ed7094cfd7d8274901ced34479a57951b58ac07a
   ✔ این کلید با کلید «sup-202611» در بیلد محصول می‌خواند.
```

و اگر جفت نباشند، صریح می‌گوید «این کلید با هیچ کلید جاسازی‌شده‌ای نمی‌خواند» و کد خروج `7` می‌دهد.

برای دیدن کلیدهای **نصب مشتری** (بدون اجرای کد، فقط خواندن منابع اسمبلی):

```bash
dotnet LicenseTool.dll keys --dir "C:\Program Files\Inventory"
```

برای بررسی خود فایل لایسنس:

```bash
dotnet LicenseTool.dll doctor --license /path/to/SUP-xxxx.lic --private-key /path/keys/….private.pem
```

## ۴) رفع

### حالت الف — کلید امضا با کلید داخل محصول جفت نیست

دو راه دارد؛ یکی را انتخاب کنید:

1. **به‌روزرسانی محصول (پیشنهادی، اگر کلید خصوصیِ قبلی در دست نیست):**
   1. پنل → تنظیمات ← کلیدهای امضا → «ثبت در manifest محصول» و مسیر پوشهٔ
      `…/inventory/src/Inventory.Licensing/Keys` همان چک‌اوت مخزن را بدهید.
   2. تغییر `Keys/sup-202611.pem` و `Keys/manifest.json` را کامیت و پوش کنید.
   3. بیلد Release تازه بگیرید و **همان بیلد** را روی نصب مشتری جایگزین کنید.
   4. همان فایل `.lic` قبلی را دوباره بارگذاری کنید — امضا عوض نشده، فقط کلید عمومیِ نصب عوض شده است.
2. **امضا با کلید خصوصیِ جفتِ نصب مشتری** (اگر نسخهٔ پشتیبان آن کلید را دارید): فایل را با همان کلید دوباره صادر کنید.

> نکته امنیتی: هیچ‌گاه برای «حل کردن سریع» کلید خصوصی تازه نسازید؛ نصب‌های موجود همه بی‌اعتبار می‌شوند.

### حالت ب — فایل دست‌کاری شده

فایل را دوباره از پنل بگیرید (پوشهٔ `licenses` روی ماشین پشتیبانی) و همان را **به‌صورت فایل** (نه متن کپی‌شده در پیام‌رسان) تحویل دهید. فایل باید پایان `.lic` داشته باشد و بی‌تغییر منتقل شود.

## ۵) چرا این اتفاق اصلاً ممکن بود؟

پنل پیش از ذخیره، فایل را با **کلید عمومیِ همان ماشین پشتیبانی** (`Signer:PublicKeyPath`) تأیید می‌کرد؛
پس اگر کلید خصوصی و کلید عمومیِ آن ماشین جفت بودند، «سبز» می‌شد — حتی اگر کلید عمومیِ
**جاسازی‌شده در محصول** (که مشتری با آن تأیید می‌کند) چیز دیگری بود.
شناسهٔ کلید هم یکی بود، پس هیچ هشداری داده نمی‌شد.

### دروازهٔ تازه (از این پس)

`LicenseTool issue` پس از ساخت فایل، آن را با **کلیدهای جاسازی‌شده در همان بیلد محصول** می‌سنجد:

* اگر جفت نباشند یا امضا نخواند ⇒ **فایل نوشته نمی‌شود**، کد خروج `7`، همراه با اثر انگشت هر دو کلید و راه‌حل.
* استثنای توسعه (نصب مشتری آن را رد می‌کند): `--allow-foreign-key`.
* پنل برای کد `7` پیام فارسی روشن نشان می‌دهد (نه «کد ۷» خام).

## ۶) چک‌لیست پیش از تحویل لایسنس

- [ ] `LicenseTool doctor --private-key …` ⇒ «✔ می‌خواند»
- [ ] `LicenseTool verify <file.lic>` ⇒ «✅ امضا معتبر است» و شناسهٔ نصب درست
- [ ] روی نصب مشتری: `LicenseTool keys --dir <install>` اثر انگشت `sup-202611` را نشان می‌دهد
