# نتیجهٔ قابل اتکا و سابقهٔ ارسال ایمیل

تاریخ تهیه: ۲۰۲۶-۱۱-۲۱ — مبنای تغییرات: `4e645dd7ca459105b727ea39be469cc410577309`

## دامنه و وضعیت

دامنهٔ تأییدشده: **ثبت و ارسال نامه از دبیرخانهٔ یکپارچه + فرم ایمیل سازمانی/شخصی مشترک، همراه سابقهٔ پایدار و کنترل ارسال تکراری**. این کار، بازنویسی مرکز خطا برای تمام اتوماسیون نیست.

تغییرات در سورس اعمال شده‌اند؛ هنوز commit/push جدید، استقرار، اجرای اسکیمای بانک اصلی یا ارسال ایمیل واقعی انجام نشده است. دریافت واقعیِ مورد گزارش‌شده نیز تأیید نشده و متن exception آن مورد ارائه نشده است؛ بنابراین تشخیص قطعی حادثه ادعا نمی‌شود.

## چه مسیرهایی در کد قبلی مشکل‌ساز بودند؟

در نسخهٔ مبنا، ردیف «ارسالی» **پیش از تماس با SMTP** ایجاد می‌شد. بنابراین وجود آن ردیف، حتی قبلاً هم مدرک ارسال نبود. از طرف دیگر، پس از `SmtpClient.SendAsync` هنوز قطع اتصال، نوشتن فایل‌های پیوست، ذخیرهٔ بانک، ثبت مخاطب و اعلان باقی می‌ماند؛ خطای این مراحل می‌توانست به فرم به شکل خطای عمومی برگردد، در حالی که SMTP پیام را پذیرفته بود. این یافتهٔ سورس است، نه اثبات علت مورد واقعی کاربر.

تولید PDF نامه، خواندن برخی پیوست‌ها و انتخاب فایل‌های مرورگر نیز مسیرهایی داشتند که خطا/فایل نامعتبر را کنار می‌گذاشتند و ادامه می‌دادند. نسخهٔ جدید ارسال ناقص را متوقف می‌کند.

## رفتار جدید

| وضعیت | معنی |
|---|---|
| ثبت دبیرخانه ذخیره شد | عملیات اداری ذخیره شده؛ نتیجهٔ ایمیل جداست. |
| Preparing / Sending | درخواست ثبت شده و هنوز نتیجهٔ نهایی ندارد. |
| Accepted | SMTP پیام را پذیرفته؛ تحویل قطعی به صندوق مقصد یا خوانده‌شدن تأیید نشده است. |
| AcceptedWithWarnings | پذیرش حفظ می‌شود؛ خطای تکمیلی مثل بانک مخاطبین، اعلان، قطع اتصال یا ثبت نتیجه به‌صورت هشدار دیده می‌شود. |
| Failed | شکست قطعی پیش از پذیرش، مانند آماده‌سازی ناموفق یا پاسخ رد SMTP. تلاش تازه فقط با اقدام صریح و پس از ثبت پایدار شکست در دسترس است. |
| Unknown | پذیرش/عدم پذیرش معلوم نیست؛ قطع پاسخ HTTP یا SMTP را «ارسال‌نشدن قطعی» تلقی نمی‌کنیم. |
| رکورد قدیمی/IMAP بدون سابقهٔ پیگیری | وضعیت ساختگی برای رکوردهای قبلی تولید نمی‌شود. |

- فرم نتیجه و کد پیگیری را نگه می‌دارد و پس از ارسال روی نتیجه اسکرول می‌کند، از جمله در موبایل.
- «ایمیل کاملاً جدید — فرم خالی» از ارسال دوباره جداست: پس از ثبت پایدارِ نتیجهٔ قطعی، گیرنده، متن و فایل‌های قبلی را پاک و کد تازه می‌سازد؛ خودش ایمیلی نمی‌فرستد. نتیجهٔ نامشخص/ثبت‌نشده با این گزینه دور انداخته نمی‌شود و باید ابتدا پیگیری شود.
- «بررسی وضعیت» و گزارش، فقط بانک را می‌خوانند؛ نه SMTP را دوباره اجرا می‌کنند، نه IMAP را همگام می‌کنند و نه نامه/پیام را خوانده‌شده می‌کنند.
- فرم‌ها بعد از قطع پاسخ، همان UUID و snapshot درخواست را برای «تکرار امن همین درخواست» نگه می‌دارند. اگر درخواست اول ثبت شده باشد این فراخوانی ایمیل دوم نمی‌فرستد؛ اگر اصلاً به سرور نرسیده باشد ارسال را شروع می‌کند. این عمل خودکار نیست.
- در `sessionStorage` فقط یادآوری نتیجه/کدِ در انتظار، جدا برای کاربر و فرم، ذخیره می‌شود؛ نه بدنه، آدرس‌ها، رمز یا فایل‌ها. بازیابی فقط استعلام است. بعد از refresh، فایل‌ها و پیش‌نویس گم‌شده خودکار دوباره ارسال نمی‌شوند. ذخیره‌سازی مرورگر ممکن است غیرفعال باشد؛ گزارش سرور جایگزین آن است.
- نتایج پذیرفته‌شدهٔ مشاهده‌شده در فرم با یک پاسخ قدیمی/نامشخصِ گزارش به «ناموفق» تبدیل نمی‌شوند.
- حساب رسمی دبیرخانه باید صریحاً انتخاب شود؛ حساب شخصی مجاز نیست و اولین حساب به‌طور خودکار انتخاب نمی‌شود.
- PDF رسمی با الزام امضا و همهٔ پیوست‌های نامه/فرم باید پیش از SMTP آماده و ذخیره شوند. فایل گم‌شده، PDF خالی و خطای خواندن/نوشتن/ذخیرهٔ پیوست، ارسال را متوقف می‌کند.
- محدودیت پیوست: فایل غیرخالی، ۲۰ MiB هر فایل، ۱۰۰ MiB مجموع، حداکثر ۱۰۰ فایل و ۲۵۵ نویسهٔ نام. حد درخواست multipart برابر ۱۱۰ MiB است؛ محدودیت IIS/reverse proxy و SMTP نیز باید رعایت شود. کدگذاری MIME ممکن است حجم شبکه را بیشتر کند.
- فهرست مقصد نامه مطابق ستون فعلی نامه حداکثر ۲۵۰ نویسه است؛ گیرندگان فرم ایمیل تابع محدودیت مستقل آن هستند.

## سابقه و کنترل تکرار

جدول افزوده‌شده: `Oto_EmailSendAttempts`، مستقل از جداول قدیمی با ارجاعات عددی و بدون cascade.

- `RequestId` با ایندکس یکتا، fingerprint سمت سرور (شامل hash محتوای پیوست برای compose)، کاربر، حساب و نامه؛ استفاده از همان UUID برای محتوای متفاوت، conflict است.
- `MessageId` ثابت برای همان درخواست.
- `GuardKey` یکتای nullable برای نامه/حساب/مجموعهٔ مقصد، با نرمال‌سازی دامنهٔ آدرس. شکست قطعی guard را آزاد می‌کند؛ پذیرش یا ابهام آن را نگه می‌دارد.
- UUID تازه به‌تنهایی مجوز ارسال دوبارهٔ همان نامه نیست. ارسال دوباره باید predecessor دقیق را معرفی کند؛ نتیجهٔ Unknown نیاز به تأیید احتمال دریافت تکراری دارد. تلاش تازهٔ در حال اجرا قابل دورزدن نیست.
- وقتی درخواست دیگری سرکوب شود، پاسخ **کد پیگیری تلاش قبلی** را برمی‌گرداند و فرم همان را دنبال می‌کند.
- claim در transaction بانک و با unique index انجام می‌شود، نه قفل حافظهٔ یک پردازش؛ SMTP داخل retry strategy بانک قرار ندارد.
- به‌روزرسانی نتیجه با UPDATE مستقل، شرط نسخهٔ زمانی و حفظ guard آزادشده انجام می‌شود. ChangeTracker نامعتبرِ پیوست، ثبت خطای آن را مسموم نمی‌کند. آماده‌سازی دیررس نمی‌تواند پس از انتقال guard، SMTP را شروع کند.
- Preparing/Sending قدیمی‌تر از ۱۰ دقیقه به‌صورت خواندنی Unknown نمایش داده می‌شود؛ «شکست قطعی» جعل نمی‌شود و رکورد خام بازنویسی نمی‌شود.
- خطاهای عمومی/اعلان، رمز، بدنه، محتوای فایل و پاسخ خام SMTP در دفتر سابقه ذخیره نمی‌شوند. کد امن، مرحله، نوع exception و در صورت وجود عدد SMTP ثبت می‌شود. رخدادها و طول متن‌ها محدودند.

**مرز تضمین:** بانک و SMTP transaction مشترک ندارند. UUID/guard جلوی اجرای دوبارهٔ همان درخواست را می‌گیرند، اما ادعای تحویل دقیقاً یک‌بارِ انتهابه‌انتها نداریم. اگر SMTP پذیرفته ولی ثبت نهایی شکست خورده باشد، پاسخ مشاهده‌شده «پذیرفته با هشدار» و `ResultPersisted=false` است؛ سابقهٔ سرور ممکن است موقتاً Sending/Unknown باقی بماند. ارسال دوباره راه تعمیر این حالت نیست.

| `SMTP_AUTH_ERROR` | فعال‌بودن SMTP برای حساب و رمز برنامه/روش مجاز سرویس بررسی شود؛ رمز را در گزارش پشتیبانی ننویسید. |
| `SMTP_REJECTED` | عدد SMTP، گیرنده، محدودیت حجم/سهمیه و سیاست سرویس‌دهنده بررسی شود؛ علت دقیق را بدون حدس از سمت سرویس‌دهنده پیگیری کنید. |
| `LETTER_PDF_ERROR` / `LETTER_PDF_EMPTY` | چاپ نامه با همان سربرگ و امضا بررسی شود. PDF در این کار ساختگی آزمایش شده؛ موتور چاپ واقعی باید در محیط مقصد بررسی شود. |
| `LETTER_ATTACHMENT_UNAVAILABLE` / `ATTACHMENT_LIMIT` | وجود و مجوز خواندن فایل و محدودیت تعداد/نام/حجم بررسی شود؛ ارسال ناقص ادامه پیدا نمی‌کند. |
| `PREPARATION_ERROR` / `DELIVERY_LOG_UNAVAILABLE` | دسترسی بانک، جدول جدید، مسیر پیوست و فضای دیسک با کد درخواست بررسی شود. نبود سابقه، مجوز ارسال دوباره با کد تازه نیست. |
| `SMTP_RESULT_UNKNOWN` / `INTERRUPTED_RESULT_UNKNOWN` | ارسال جدید نکنید؛ کد درخواست/MessageId را در گزارش سرویس‌دهنده و در صورت لزوم نزد گیرنده بررسی کنید. |
| `RESULT_SAVE_WARNING` | اگر پذیرش دیده شده، ارسال را تکرار نکنید؛ سلامت بانک و ثبت نتیجه را پیگیری کنید. |
| `CONTACTS_SAVE_WARNING` / `NOTIFICATION_WARNING` / `BROADCAST_WARNING` | بانک مخاطب یا زیرسامانهٔ اعلان/تازه‌سازی بررسی شود؛ خطای تکمیلی نتیجهٔ SMTP را باطل نمی‌کند. |
| `SMTP_QUIT_WARNING` / `SMTP_DISPOSE_WARNING` | پاک‌سازی اتصال مشکل داشته است؛ وضعیت ارسال را از نتیجهٔ مستقل SMTP بخوانید، نه از این هشدار. |
| `REQUEST_ID_CONFLICT` | یک UUID برای دو محتوای متفاوت استفاده شده؛ نتیجهٔ قبلی را بررسی کنید، آن را بازنویسی یا بی‌بررسی تکرار نکنید. |

## API و دسترسی

- `POST /api/email/send`: multipart با `requestId` غیرخالی؛ پاسخ `EmailDeliveryResultDto`. HTTP 200 به‌تنهایی معادل پذیرش ایمیل نیست؛ `Status` بررسی شود.
- `POST /api/outgoing-letters/{id}/dabirkhane`: `EmailRequestId`، حساب رسمی و در صورت ارسال دوباره `ResendOfRequestId` / `AcceptDuplicateRisk`. پاسخ `DabirkhaneRegisterResultDto` شامل `RegistrationSaved`، نتیجهٔ Email و هشدار جداست.
- `GET /api/email/delivery-status/{requestId}`: استعلام مجاز، بدون side effect.
- `GET /api/email/delivery-history`: فیلتر accountId / letterId / sentId / status و صفحه‌بندی؛ `pageSize <= 100`.
- خواندن سابقه تابع دسترسی **فعلی** به حساب است؛ مدیر ایمیل هم به حساب خصوصی دیگران دسترسی اضافه نمی‌گیرد. `personal=true` حساب‌های رسمی را حذف می‌کند و مجوز شخصی را حفظ می‌کند.
- 400 دارای `requestRejected=true` فقط رد قبل از پردازشِ همان فراخوانی است. اگر پاسخ تلاش قبلی گم شده باشد، رد یک استعلام/بازپخش تازه نتیجهٔ قبلی را پاک نمی‌کند.
- خطای عمومی این دو مسیر، متن خام exception/inner exception را به کاربر نمی‌دهد. exception filter سراسری سایر ماژول‌ها بازنویسی نشده است.
- ثبت دبیرخانهٔ ذخیره‌شده با خطای ایمیل یا اعلان rollback فرضی نمی‌خورد. replay شناخته‌شده، ثبت‌کننده/فیلدهای قبلی را دوباره بازنویسی نمی‌کند و اعلان ایجادکننده را تکرار نمی‌کند.
- **مرز هم‌زمانی ثبت اداری:** بررسی زودهنگام UUID از بازنویسی ثبت در replay/conflict متوالی جلوگیری می‌کند؛ اما ذخیرهٔ فیلدهای دبیرخانه و claim ارسال در یک transaction مشترک نیستند. ثبت هم‌زمانِ اطلاعات متفاوتِ یک نامه توسط چند کاربر همچنان می‌تواند آخرین مقدار ذخیره‌شده را غالب کند، حتی اگر ایمیل اضافه سرکوب شود. کنترل تکرار SMTP را با کنترل نسخهٔ فیلدهای اداری یکی ندانید؛ این سناریو در staging بررسی و تا آن زمان برای یک نامه هم‌زمان ثبت انجام نشود.

### سازگاری فراخوان‌های داخلی قدیمی

سه مصرف‌کنندهٔ موجودِ سرویس ایمیل (فیش حقوق، اطلاع‌رسانی FaCom و endpoint قدیمی صورتجلسه) قرارداد عددی داشتند. تغییر آن‌ها فقط به استفاده از adapter `SendSystemEmailAsync` محدود شده است. adapter نتیجهٔ ناموفق/نامشخص را موفق حساب نمی‌کند و هر تلاش را در همین سابقه ثبت می‌کند؛ هشدار پس از پذیرش باعث شکست مصنوعی نمی‌شود.

این سه رابط قدیمی UUID پایدار از کلاینت ندارند؛ اگر UUID عرضه نشده باشد برای هر فراخوانی داخلی یک کد جدید می‌گیرند. **تضمین بازپخش HTTP فرم‌های جدید را به کل گردش مالی/منابع انسانی تعمیم ندهید.** بازطراحی idempotency عملیات گروهی آن ماژول‌ها خارج از دامنهٔ این اصلاح است. هیچ منطق محاسبه/توزیع مالی تغییر نکرده است.

## بانک و انتشار بعدی — هنوز اجرا نشده

1. API، Shared و Client باید با هم منتشر شوند؛ کلاینت‌های قدیمیِ این دو فرم UUID ندارند و عمداً پیش از SMTP رد می‌شوند. کش/service worker مرورگر نیز باید نسخهٔ تازه را بگیرد.
2. از بانک و پوشهٔ پیوست‌ها پشتیبان بگیرید. برای SQLite و SQL Server، bootstrap افزایشی `EmailDeliverySchemaV1` از مسیر موجود `OfficeEmailSchemaV1` فراخوانی می‌شود. جدول‌های قبلی پاک/بازنویسی نمی‌شوند.
3. در محیط staging با بانک و تنظیمات مشابه مقصد، ایجاد جدول و ایندکس‌های Request/Guard، مجوز DDL، نوشتن پیوست و چاپ واقعی سربرگ/امضا بررسی شود. در استقرار چندنمونه‌ای، bootstrap پیش از فعال‌کردن همهٔ نمونه‌ها تکمیل شود.
4. SQL Server در این محیط **اجرا نشده**؛ ترجمهٔ UPDATE، مدل و فرمان bootstrap با provider SQL Server و interceptor بدون اتصال بررسی شده‌اند. تست transaction/concurrency روی SQL Server واقعی هنوز لازم است.
5. تست اتصال SMTP و ارسال سیاست یکسان دارند: اگر SSL/TLS فعال است، ۴۶۵ TLS مستقیم و سایر پورت‌ها STARTTLS الزامی دارند. برای عبور از خطا TLS را بی‌اطلاع خاموش نکنید؛ تنظیم درست را از سرویس‌دهنده بگیرید.
6. قبل از بهره‌برداری، build کامل اجرایی/انتشار در CI مناسب و تست کنترل‌شدهٔ حساب مجاز با اجازهٔ جداگانه انجام شود. هیچ ارسال واقعی در این کار انجام نشده است.
7. سابقه/guardها را برای «رفع خطا» حذف نکنید. rollback/restore بانک باید با آگاهی از ارسال‌های انجام‌شده باشد؛ حذف شاهد قبلی می‌تواند کنترل تکرار را از بین ببرد.

| بازگشت تغییرات قبلی عکس/گردش نامه | **۲۳ source/projection + ۲۲۱ Razor موفق**؛ بدون تغییر منطق هویت و خوانده‌شدن. ۷۱ آزمون مرورگر قدیمی عکس‌ها در این مرحله تکرار نشده‌اند. |
| build متمرکز server و Razor | موفق؛ nullable در آزمون‌های متمرکز فعال بود. هشدار قبلی `MinutesApiService` در build وابستگی‌ها دیده شد. |
| build اجرایی کامل API | **موفق: صفر خطا، ۳ هشدار** در `SnmpClient` دست‌نخورده؛ ۹۵ ثانیه با تنظیمات کم‌حافظهٔ زیر. |
| build کامل Client و خروجی Blazor WebAssembly | **موفق: صفر خطا، ۱۳ هشدار** در فایل‌های دست‌نخورده؛ ۱۲۲ ثانیه با تنظیمات زیر. |
| بررسی مستقل اسمبلی‌ها | هر دو دارای entry point و بدنهٔ واقعی IL و فاقد `ReferenceAssemblyAttribute` هستند؛ API دارای ۵۶۸۹۵ و Client دارای ۳۸۹۹۷ بدنهٔ متد است. کد برنامه برای این بررسی اجرا نشد. |
| SQL Server واقعی، SMTP مقصد، اجرای تولیدی و استقرار | انجام نشده؛ آزمون‌های ساختگی جایگزین بررسی محیط عملیاتی نیستند. |

۹۰+۱۹+۴۰+۳۲ = **۱۸۱ بررسی جدید**. آزمون‌های بازگشت قدیمی جدا شمرده شده‌اند، نه به‌جای تست بانک/محیط عملیاتی.

فایل‌های آزمون: `tests/EmailDelivery` و `tests/EmailDeliveryUi`. کانتکست و وابستگی‌های نامرتبط/چاپ/اعلان در harness ساختگی‌اند؛ کد واقعی مسیر ایمیل و registration partial لینک و اجرا می‌شود. آزمون endpoint از stub مجوز در base controller استفاده می‌کند؛ کنترل حسابِ خود سرویس/store واقعی است. آزمون مرورگر روی host ساختگی Razor انجام شد، نه مسیر احراز هویت/مجوز و startup کامل API تولیدی. چاپ واقعی سربرگ/امضا، مجوزهای تولیدی و مسیر کامل WASM به API در staging باید بررسی شوند.

### ساخت کم‌حافظه و تفاوت با انتشار نهایی

تلاش‌های اولیهٔ API با تحلیل کامل nullable در محدودیت حدود ۲ GiB حافظه شکست خوردند/متوقف شدند. build اولیهٔ reference-only فقط ابزار تشخیص بود. پیش از ساخت نهایی، DLLهای reference-only و stamp کامپایل API حذف شدند؛ ساخت جدید واقعاً متدها را کامپایل و خروجی اجرایی تولید کرد، نه استفادهٔ مجدد از آن DLL.

ساخت‌های موفق با SDK `8.0.428`، یک پردازنده، heap سقف `0x38000000` و `DOTNET_GCConserveMemory=9` اجرا شدند. برای کاهش حافظه، تنها در خط فرمان تحلیل nullable و analyzers خاموش شدند؛ فایل پروژه و سیاست nullable سورس تغییر نکرد. بنابراین نتیجهٔ ساخت اجرایی را داریم، اما اجرای کامل analyzer/nullable در CI و publish نهایی همچنان مرحلهٔ جداست. فرمان‌ها از ریشهٔ `inventory/`:

```sh
# Shared قبلاً همراه harnessها با تنظیمات معمول ساخته شده بود.
dotnet build src/Inventory.Api/Inventory.Api.csproj --no-restore -m:1 \
  -p:UseSharedCompilation=false -p:RunAnalyzers=false -p:NuGetAudit=false \
  -p:DebugType=None -p:DebugSymbols=false -p:Optimize=true \
  -p:Nullable=annotations -p:Features=run-nullable-analysis=never \
  -p:ProduceOnlyReferenceAssembly=false -p:ProduceReferenceAssembly=false \
  -p:BuildProjectReferences=false

dotnet build src/Inventory.Client/Inventory.Client.csproj -m:1 \
  -p:UseSharedCompilation=false -p:RunAnalyzers=false -p:NuGetAudit=false \
  -p:DebugType=None -p:DebugSymbols=false \
  -p:Nullable=annotations -p:Features=run-nullable-analysis=never \
  -p:UseRazorSourceGenerator=false -p:BuildProjectReferences=false
```

بستهٔ تحویل **سورس و شواهد آزمون** است، نه خروجی قابل استقرار؛ DLL، تنظیمات حساب/بانک، کلید DataProtection، گواهی محلی، `bin`/`obj` و credential در آن قرار ندارند.
