# اعلان اندروید برای PWA

## وضعیت

پیاده‌سازی و آزمون محلی انجام شده؛ **هنوز منتشر یا روی گوشی واقعی کاربر آزمایش نشده است**. آدرس و وضعیت HTTPS سامانه مشخص نیست. موفقیت در تست محلی به معنی تحویل واقعی از FCM به اندروید نیست.

## تغییرات

- ثبت دستگاه فقط بعد از تأیید ثبت سمت سرور فعال شناخته می‌شود. اجازه اعلان قبل از انتظار شبکه و هنگام کلیک درخواست می‌شود.
- زنگ اعلان‌ها: **فعال‌سازی / غیرفعال‌سازی، بررسی وضعیت، آزمایش**. خطای HTTPS، اجازه مسدود، نبود کلید، ثبت ناموفق و صف ارسال نمایش داده می‌شود.
- اشتراک موجود در شروع برنامه بازبینی می‌شود؛ تغییر کلید، حذف ثبت سرور و منقضی شدن اشتراک قابل بازیابی‌اند. اجازه اعلان بدون کلیک دوباره درخواست نمی‌شود.
- اشتراک به یک حساب روی همان مرورگر تعلق دارد؛ کلیدهای آن به‌روز می‌شوند. خروج، اشتراک را لغو و مالک ذخیره‌شده در Worker را صفر می‌کند. Worker اعلان حساب قبلی را نشان نمی‌دهد و اعلان‌های نمایش‌داده‌شده قبلی را هنگام تغییر مالک می‌بندد. اعلان دریافت‌شده پیش از خروج یا سابقه اعلان سیستم قابل پس‌گرفتن قطعی نیست.
- توکن ورود در Worker ذخیره نمی‌شود. اتصال SignalR اعلان‌ها نیز اکنون احراز هویت دارد؛ شناسه و نقش از query string پذیرفته نمی‌شود.
- ارسال Push از درخواست اصلی جدا شده است: `PushDeliveries` همراه اعلان در همان SaveChanges ذخیره می‌شود. کارگر هر پنج ثانیه، حداکثر ۲۵ کار در نوبت را بررسی می‌کند؛ ادعای اتمیک، اجاره دو‌دقیقه‌ای، مهلت شبکه ۲۰ ثانیه، شش تلاش با فاصله افزایشی و انقضای ۴۸ ساعته دارد. رکوردهای غیرمشغولِ بیش از هفت روز پاک می‌شوند.
- 404/410 اشتراک را منقضی می‌کند؛ خطاهای شبکه، 429، 5xx و خطای احراز هویت سرویس Push با سقف تلاش دوباره امتحان می‌شوند. خطاهای دائمی وضعیت Failed دارند. Retry-After سرویس‌دهنده فعلاً جداگانه تفسیر نمی‌شود؛ فاصله تلاش، backoff داخلی است.
- ارسال رمزنگاری‌شده، VAPID، `Urgency: high` و TTL متناسب با زمان باقی‌مانده تا انقضا دارد. پذیرش توسط سرویس Push با وضعیت **Accepted** ثبت می‌شود؛ **این رسیدِ نمایش روی گوشی نیست**. اعلان آزمایشی حداکثر ده دقیقه عمر دارد و هر کاربر در ۳۰ ثانیه یک آزمایش می‌تواند درخواست کند.
- دریافت ممکن است حداقل یک‌بار باشد، نه exactly-once؛ tag ثابت تلاش مجدد، اعلان نمایش‌داده‌شده را جایگزین می‌کند. قطع سرویس پس از پذیرش سرویس‌دهنده و قبل از ثبت موفقیت ممکن است ارسال دوباره ایجاد کند.
- لینک اعلان فقط هم‌مبدأ باز می‌شود. کلیک، پنجره مرتبط را باز/متمرکز می‌کند؛ مجوز محتوای مقصد همچنان سمت API کنترل می‌شود.
- تمام اعلان‌های مسیر فعلی `NotifyService` و اعلان‌های مستقیم حضور و غیاب فروغ آریا در صف قرار می‌گیرند. پیام جدید چت هم برای سایر اعضای غیرخاموش و غیرآرشیوشده اعلان دارد و `/chat/{id}` را باز می‌کند؛ متن خود پیام روی اعلان چت فرستاده نمی‌شود.
- رویدادهایی که قبلاً اعلان ایجاد نمی‌کردند، صرفاً با این تغییر تبدیل به اعلان نشده‌اند. اعلان‌های تاریخی پیش از این تغییر یا پیش از ثبت یک دستگاه، به‌صورت انبوه بازپخش نمی‌شوند.

## راه‌اندازی واقعی

1. آدرس نصب‌شده PWA باید **HTTPS با گواهی معتبر و مورد اعتماد گوشی** باشد. IP داخلی با HTTP کافی نیست. نصب مجدد روی مبدأ جدید به فعال‌سازی مجدد اعلان نیاز دارد.
2. گوشی و سرور باید به سرویس Push مرورگر دسترسی اینترنتی داشته باشند. برای Android/Chrome، FCM لازم است. باز شدن سایت به‌تنهایی این دسترسی را ثابت نمی‌کند. در شبکه داخلی/VPN، ممکن است اعلان برسد ولی باز شدن لینک تا اتصال VPN ممکن نباشد.
3. یک جفت کلید VAPID **تازه و پایدار** روی محیط مطمئن بسازید. کلیدهای پیش‌فرض قبلی داخل مخزن بودند؛ از آن‌ها در تولید استفاده نکنید. اکنون مقدارشان در `appsettings.json` خالی است تا کلید خصوصی مشترک ناخواسته استفاده نشود.

   ```bash
   dotnet run --project inventory/tools/GenerateVapidKeys -- mailto:admin@your-domain.example
   ```

   خروجی حاوی کلید خصوصی است؛ آن را در چت، Git، اسکرین‌شات یا گزارش ثبت نکنید. در تنظیمات امن فرایند API این مقادیر را تنظیم کنید:

   - `VAPID_SUBJECT` (ایمیل یا URL تماس معتبر خودتان)
   - `VAPID_PUBLIC_KEY`
   - `VAPID_PRIVATE_KEY`

   تنظیمات `PushNotifications:*` از Configuration نیز پشتیبانی می‌شود؛ متغیرهای فوق اولویت دارند. همه نمونه‌های API باید کلید یکسان داشته باشند. کلید را در هر اجرا دوباره نسازید. تغییر کلید مستلزم فعال‌سازی مجدد دستگاه‌هاست.
4. پیش از انتشار از DB نسخه پشتیبان بگیرید. `PushDeliverySchema` هنگام راه‌اندازی جدول صف و در صورت نبودن، جدول اشتراک را می‌سازد و ایندکس‌ها را اضافه می‌کند. برای endpointهای تکراری قدیمی، جدیدترین LastSeenAt/Id نگه داشته می‌شود؛ هر endpoint فقط یک مالک دارد. داده‌های کسب‌وکار حذف نمی‌شوند. ارتقا را نخست روی کپی محیط واقعی، با یک نمونه API و دسترسی DDL اجرا کنید.
5. API و کلاینت را هماهنگ منتشر کنید. فایل‌های `push-worker.js`، `js/push-notifications.js` و service worker منتشرشده باید در همان مبدأ و scope ریشه قابل دریافت باشند، نه پاسخ fallback HTML. ثبت Worker با `updateViaCache: none` است. فایل JS دارای query نسخه نیز از کش نسخه منتشرشده درست خوانده می‌شود؛ API و فایل‌های دارای توکن وارد offline cache نمی‌شوند.
6. روی گوشی با Chrome به‌روز وارد شوید، PWA را نصب/باز کنید؛ زنگ اعلان‌ها → **فعال‌سازی** → اجازه دادن → **آزمایش**. پیام «در صف» به معنی دریافت نیست؛ باید خود اعلان در نوار اندروید دیده شود.
7. صفحه PWA را ببندید (Force Stop نکنید)، از کاربر دیگری دستورکاری ارجاع دهید یا پیام ارسال کنید، سپس رسیدن اعلان و باز شدن رکورد مربوطه را کنترل کنید. حساب مقصد، دستگاه درست و مجوز دسترسی مقصد باید آزمایش شوند.
8. اگر تأخیر وجود دارد: اجازه اعلان در تنظیمات سایت و برنامه اندروید (PWA یا Chrome)، حالت مزاحم نشوید، محدودیت باتری/پس‌زمینه و اینترنت سرویس Push را بررسی کنید. بعضی ROMها یا دستگاه‌های فاقد خدمات لازم گوگل محدودیت دارند. در Force Stop، نبود اینترنت یا منع سیستم‌عامل، تحویل فوری تضمین‌پذیر نیست.

### تشخیص سمت سرور

- `GET /api/notifications/push-vapid-key`: publicKey و configured؛ هرگز کلید خصوصی برنمی‌گرداند.
- `POST push-subscribe / push-unsubscribe / push-status`: فقط دستگاه متعلق به کاربر احرازشده.
- `POST test-push` با endpoint: پاسخ 202 یعنی وارد صف شد؛ 503 تنظیم کلید، 400 ثبت دستگاه و 429 فاصله آزمایش را بررسی کنید.
- `push-status.last` وضعیت آخرین کار همان دستگاه را نشان می‌دهد. `PROVIDER_401/403` معمولاً نیازمند بررسی کلیدها/اشتراک است؛ `NETWORK_OR_TIMEOUT` ارتباط خروجی سرور را بررسی می‌کند.
- برای جلوگیری از SSRF، endpointهای شناخته‌شده FCM، Mozilla و Apple با HTTPS پذیرفته می‌شوند و HTTP redirect دنبال نمی‌شود. سرویس‌های Push دیگر نیاز به افزودن صریح و بررسی‌شده دارند؛ هدف اصلی این تغییر Android/Chrome است.

## آزمون‌ها و محدودیت تأیید

- بیلد کامل solution: موفق، صفر خطا؛ در آخرین بیلد کامپایل‌شده ۲۴ هشدار موجود بود.
- تست Push: **۲۰/۲۰**؛ SQLite، ثبت و جابه‌جایی مالک، کلیدها، endpoint غیرمجاز، rollback، صف، backoff، منقضی، fence، API آزمایش و تطبیق مدل فقط جداول Push. رمزنگاری واقعی WebPush و هدرهای TTL/Urgency/Authorization با HTTP handler آزمایشی و بدون تماس شبکه بررسی شدند.
- آرشیو **۳۴/۳۴** و دستورکار **۲۶/۲۶** موفق.
- مجموعه قدیمی چت **۵۶ موفق / ۱ ناموفق**: `Sql_server_upgrade_is_guarded_and_snapshot_matches_model` به علت اختلاف عمومی snapshot در جدول‌های منابع انسانی و دستورکار ناموفق است؛ اختلاف تشخیص‌داده‌شده مربوط به جداول Push نیست. این مشکل عمومی در این کار بازنویسی نشده؛ بنابراین ادعای «تمام تست‌های پروژه موفق‌اند» نداریم. قبل از مهاجرت SQL Server باید جداگانه بررسی شود.
- UI واقعی کامپایل‌شده دسکتاپ/موبایل با PushManager، permission و API شبیه‌سازی‌شده موفق؛ مدل دریافت Worker، تعویض حساب، expiry، لینک امن و cache در Node موفق. چهار مجموعه قبلی مرورگر آرشیو، توسعه آرشیو، دانلود و دستورکار نیز موفق بودند.
- **FCM زنده، گوشی واقعی، SQL Server عملیاتی، بار بالا و چند نمونه همزمان** در این محیط آزمایش نشده‌اند. بیلد و mock موفق جای آزمون روی گوشی مقصد را نمی‌گیرد.
- کد محلی است؛ commit، push، انتشار، تماس با سرویس Push واقعی یا تغییر DB عملیاتی انجام نشده است.
