# مهاجرت صفحه‌بندی به دیتابیس — ۲۰۲۶-۰۹-۲۹

## وضعیت: گسترده، اما هنوز کامل نشده

این تغییر **تکمیل تمام GETهای پروژه نیست**. مسیرهای مهاجرت‌کرده و موارد باقی‌مانده
در ادامه تفکیک شده‌اند. به‌خصوص گزارش‌های تجمیعی و درخت‌ها را نباید صرفاً با
قرار دادن `Skip/Take` قبل از اولین `ToListAsync` تغییر داد: این کار مانده‌ها،
ترتیب جهانی، شمارش یا دسترسی‌ها را خراب می‌کند.

## آنچه تغییر کرده است

- ۲۱۹ محل خواندن فهرست از `ToPageListAsync` استفاده می‌کنند؛ درخواست صفحه‌بندی
  به‌صورت صریح از کنترلر به کوئری اصلی سرویس منتقل می‌شود، نه با وضعیت سراسری یا
  `HttpContext` مخفی. این عدد تعداد محل فراخوانی است، نه تعداد endpoint مستقل.
- `COUNT` روی کوئری فیلترشده و `Skip/Take` قبل از materialization اجرا می‌شوند.
  نگاشت DTO و خواندن فایل پیوست روی صفحهٔ انتخاب‌شده انجام می‌شود.
- سقف‌های قدیمی مانند `Take(100)` در مسیرهای مهاجرت‌کرده فقط برای درخواست‌های
  **بدون صفحه‌بندی** حفظ می‌شوند؛ `total` و دسترسی به صفحه‌های بعد را محدود نمی‌کنند.
- کلید یکتا به مرتب‌سازی کوئری‌های مهاجرت‌کرده اضافه شده است.
- فهرست کالا/موجودی در هر دو سرویس Catalog و Warehousing بازنویسی شده است.
  فیلتر موجودی/نقطهٔ سفارش قبل از شمارش و انتخاب صفحه قرار دارد. موجودی‌های لازم
  برای DTOهای کالا به شناسه‌های همان صفحه محدود می‌شوند.
- بایگانی نامهٔ وارده و inbox ترکیبی نامهٔ صادره ابتدا کلیدهای صفحه را از اجتماع
  کوئری‌ها می‌خوانند؛ سپس فقط همان ردیف‌ها را hydrate می‌کنند. ادغام دو فهرست کامل
  و `Skip/Take` حافظه‌ای این مسیرها حذف شده است.
- بسیاری از فهرست‌های HR، FaAtt، FaCom، FaLms، FaPay، حسابداری، خزانه، مؤدیان،
  پروژه‌ها، صورتجلسات، اطلاعات IT و پیوست‌ها به مسیر دیتابیسی منتقل شده‌اند.
- فهرست مدارک: دسترسی و فیلتر انقضا قبل از صفحه‌بندی اعمال می‌شود.
- کلاینت پاسخ‌های `{ total, items }` و `{ totalCount, items }` را هر دو می‌خواند.
  خطاهای دریافت صفحه دیگر به‌صورت خاموش به یک صفحهٔ خالی تبدیل نمی‌شوند.
- صفحه‌بندی مرورگری یازده بخش به درخواست صفحه‌ای سرور منتقل شده است:
  انبارها، طرف‌حساب‌ها، واحدها، معرف‌ها، کارفرماها، انواع فاکتور، محصولات معرف،
  پرداخت‌های معرف، پیش‌نویس داخلی، پیش‌نویس صادره و نقطهٔ سفارش. جستجوی واحد/معرف نیز سمت
  دیتابیس است و هنگام تغییر فیلتر شمارهٔ صفحه از ابتدا شروع می‌شود.

## ادامهٔ مهاجرت پس از بررسی دوم

- شمار یافته‌های ممیزی از ۵۹ به **۲۵** کاهش یافت: اکنون ۱۳ `Paging.Result`،
  ۵ `Paging.Slice` و ۷ مورد سمت کلاینت باقی است (دو مورد کلاینت صفحه‌بندی نیست).
  این کاهش، اثبات پوشش تمام GETها نیست.
- سفارش‌های تمدید مدارک و خطاهای صف نمایه‌سازی، شرکت‌های مجاز، کد پروژه‌های
  برگشتی، فیش‌های شخصی، کانبان و قوانین HR/حقوق اکنون از SQL صفحه می‌گیرند.
  انتخاب شرکت فعال مستقل از صفحهٔ شرکت‌هاست.
- `DatabaseTreePaging.ReadTreePageAsync` ریشه‌ها را در SQL می‌شمارد و صفحه‌بندی
  می‌کند، سپس فقط فرزندان ریشه‌های منتخب را، با حفظ scope، می‌خواند.
  پنج مصرف‌کننده: درخت حساب‌ها، گروه انبار، سازمان HrCore، سازمان HrMain و گردش نامه.
  `total` در این مسیرها تعداد ریشه است؛ اندازهٔ زیرشاخه‌ها به `take` محدود نمی‌شود.
- فهرست تخت حساب‌ها نیز صفحهٔ SQL دارد؛ اجداد لازم برای مسیر/عمق و در حالت
  مانده‌دار، زیرشاخه‌های حساب‌های منتخب برای تجمیع بازیابی می‌شوند. درخت بایگانی
  و فهرست تخت گروه کالا هنوز جداگانه باقی مانده‌اند.
- گزارش عملکرد دستورکار ابتدا در SQL گروه‌بندی و رتبه‌بندی می‌شود. گردکردن
  درصدهای نیمه به عدد زوج حفظ شده؛ رتبه از offset ادامه پیدا می‌کند. محاسبهٔ
  تأخیر فقط برای گیرندگان منتخب داده می‌خواند.
- سابقهٔ شغلی و تقویم آموزش، اجتماع کلیدها را قبل از hydrate صفحه‌بندی می‌کنند.
  تاریخچهٔ حضور شخصی، گزارش حضور و خلاصهٔ ماهانه نیز صفحه‌بندی SQL دارند.
- گزارش بودجه، داشبورد، گزارش آموزشی پرسنل و نظرسنجی، خلاصه‌های مستقل از صفحه
  دارند. نظرسنجی برای حفظ گردکردن قبلی، metadata تجمیعی هر سؤال را جدا می‌خواند؛
  خود سؤال‌ها و پاسخ‌های تکمیلی به صفحه محدودند.
- ReportStudio ابتدا سیاست‌های متمایز `ModulesCsv` را برای مجوز داده ارزیابی
  می‌کند و کلیدهای مجاز را پیش از شمارش/صفحه‌بندی در predicate SQL قرار می‌دهد.
  این lookup سیاست‌ها به معنی خواندن همهٔ بدنه‌ها/اشتراک‌های گزارش نیست.
- نقطهٔ سفارش، جمع موجودی، فیلتر حداقل و ترتیب کمبود را قبل از انتخاب صفحه اجرا
  می‌کند؛ صفحهٔ کلاینت نیز از total سرور و درخواست صفحه استفاده می‌کند.
- کاردکس Catalog ردیف‌های انتخاب‌شده را از join تراکنش/خط می‌خواند. ماندهٔ شروع
  از آخرین Initial/Adjustment پیش از صفحه و جمع گردش بعد از آن به دست می‌آید.
  کلید ترتیب: تاریخ، شناسهٔ تراکنش، شناسهٔ خط. کاردکس ریالی Warehousing و
  صفحه‌بندی مرورگری کاردکس هنوز مهاجرت نکرده‌اند؛ جمع‌های UI نباید به صفحه محدود شوند.

## قرارداد و ملاحظات سازگاری

- فراخوانی‌های قدیمی **بدون** `skip/take` همچنان شکل آرایه و رفتار بدون صفحه‌بندی
  قبلی را دارند. این کار جلوی ناقص‌شدن lookupها، چاپ، export و استفاده‌های داخلی
  سرویس‌ها را می‌گیرد. تبدیل اجباری همهٔ مصرف‌کننده‌ها به پاسخ صفحه‌ای انجام نشده است.
- `skip` منفی صفر می‌شود؛ رفتار قدیمی `take` تهی/صفر و درخواست فقط با `skip`
  حفظ شده است. سقف عمومی جدید برای اندازهٔ صفحه اعمال نشده است.
- `Paging.Request` فقط باید به **کوئری ردیف‌های نتیجه** داده شود؛ نه به کوئری
  مجوزها، نقش‌ها، تنظیمات یا داده‌های تکمیلی. استفادهٔ دوبارهٔ آن خطا می‌دهد.
- بعد از انتخاب صفحه، فیلتر یا تغییر ترتیب جهانی مجاز نیست. نگاشت و مرتب‌سازی
  مجدد همان کلیدها برای بازسازی ترتیب نتیجهٔ hydrateشده مجاز است.
- SQL Server تجمیع مقدار decimal را مستقیماً اجرا می‌کند. SQLite/EF8 از SUM
  decimal پشتیبانی نمی‌کند؛ در تجمیع مقدار موجودی/کاردکس Catalog، مقدار به REAL تبدیل و مطابق
  دقت سه‌رقمی مدل گرد می‌شود. مبالغ/قیمت‌های خروجی همچنان decimal هستند. این
  انتخاب برای داده‌های SQLite که خارج از دقت مدل ذخیره شده‌اند نیاز به بررسی دارد.
- `COUNT` و خواندن صفحه دو فرمان جدا هستند؛ snapshot مشترک یا تضمین ثبات نتیجه
  در برابر درج/حذف همزمان اضافه نشده است.
- تبدیل قدیمی `skip/take` به `page/pageSize` در endpointهای قبلی حفظ شده است؛
  offsetهای غیرمضربِ اندازهٔ صفحه در آن adapter هنوز نیاز به اصلاح مستقل دارند.
  مسیر جدید Request offset را مستقیماً به SQL می‌دهد.

## باقی‌مانده‌ها

در پایان این مرحله هنوز **۱۳ فراخوانی `Paging.Result`** و **۵ فراخوانی
`Paging.Slice`** در API وجود دارد. کاتالوگ Export دادهٔ ثابت است؛ سایر موارد
نیازمند بررسی یا مهاجرت‌اند. دسته‌های باقی‌مانده:

1. فهرست تخت گروه کالا در Catalog و Warehousing و درخت بایگانی شخصی/صادره؛
   ترتیب سلسله‌مراتبی یا ترتیب برگ‌ها نباید با برش خام گره‌ها عوض شود.
2. کیف پول معرف‌ها (هزینه‌یابی/پورسانت محاسبه‌شده)، ارزیابی عملکرد HrPerf و
   HrTalent، برچسب‌های دستورکار و کاردکس ریالی Warehousing.
3. چت (فهرست گفتگو و جستجوی کاربران): نرمال‌سازی Unicode، عنوان مخاطب، unread
   و ترتیب نهایی باید قبل از انتخاب صفحه اجرا شوند.
4. تقویم غیبت FaAtt، تداخل آموزشی، کسری‌های حضور، وضعیت امروز، موجودی مرخصی
   و گزارش ماهانهٔ مرخصی. بعضی خروجی‌ها روزها/دسته‌های تولیدشده‌اند، نه ردیف خام.
5. کلاینت: گروه کالا، کیف پول معرف، درخواست IT و کاردکس هنوز برش محلی دارند.
   مقایسهٔ محتوای فایل نیز local است. در IT و کاردکس API صفحه‌بندی دارد ولی UI
   به مهاجرت با حفظ شمارنده‌ها، خلاصه‌ها و لینک مستقیم نیاز دارد.
6. adapterهای قدیمی `Paging.ToPage` (۳۷ محل کنترلر) هنوز offset غیرمضرب صفحه
   را گرد می‌کنند؛ الگوی اصلی ابزار ممیزی این موارد را نمی‌شمارد.
7. فیلترهای محلی برخی کارتابل‌ها، از جمله starred که دو صفحه را ترکیب می‌کند.
8. ReportStudio در `RsExecutor.BuildTable` برش حافظه‌ای دارد؛ اجرای آن از POST
   انجام می‌شود و بازنویسی موتور گزارش مستقل از این فهرست GET است.

دو `Skip` در کلاینت مربوط به کنارگذاشتن سربرگ فایل و استخراج نام خانوادگی هستند؛
این‌ها صفحه‌بندی دیتابیس نیستند. `Skip` در چاپ برای چیدمان نیز باید حفظ شود.

فهرست دقیق فایل/خط و دستور بازتولید:

```sh
python inventory/tools/audit_database_pagination.py
# تا زمانی که یافته‌ها باقی باشند، عمداً exit code=1 می‌دهد:
python inventory/tools/audit_database_pagination.py --strict
```

این ابزار الگوهای شناخته‌شده را گزارش می‌کند؛ نبودن یک الگو اثبات بررسی کامل
تمام مسیرهای GET یا نبود فیلتر حافظه‌ای نیست.

## اعتبارسنجی

انجام‌شده در محیط فعلی:

- `git diff --check`: بدون خطا.
- بررسی syntax ۱۲۸ فایل C# تغییرکرده، helperها و تست‌ها با parser C#: بدون خطای syntax.
- تطبیق وجود پارامتر اختیاری paging در interface/implementation: بدون ناهماهنگی یافت‌شده.
- بررسی بلوک‌های C# صفحات تغییرکرده؛ LetterCartable دارای Razor توکار است و
  parser ساده برای آن جایگزین کامپایل Razor نیست (همین وضعیت در نسخهٔ قبلی وجود دارد).
- اجرای ابزار ممیزی و ثبت صریح باقی‌مانده‌ها.

**Build و تست اجرایی اجرا نشده‌اند:** دستور `dotnet` در محیط موجود نیست. تلاش
برای دانلود SDK از میزبان‌های Microsoft نیز با خطای اتصال SSL مواجه شد. بنابراین
صحت کامپایل کامل و ترجمهٔ تمام کوئری‌های سرویس‌ها تأیید نشده است.

تست رگرسیون قابل اجرا در `inventory/tests/DatabasePagination` اضافه شده است:

```sh
dotnet run --project inventory/tests/DatabasePagination
dotnet build inventory/src/Inventory.Api/Inventory.Api.csproj
dotnet build inventory/src/Inventory.Client/Inventory.Client.csproj
```

تست از SQLite واقعی و ثبت SQL استفاده می‌کند و helperهای production و parser
کلاینت را مستقیماً لینک می‌کند؛ count، offset، cap، صفحهٔ خالی، union، predicate
موجودی و ترجمهٔ OFFSET/FETCH در SQL Server را بررسی می‌کند. جایگزین تست یکپارچهٔ
تمام endpointها و کنترل دسترسی نیست. پیش از merge باید build و این تست‌ها، سپس
آزمون دادهٔ حجیم و مجوزهای چندکاربره روی دیتابیس واقعی انجام شوند.

### تست‌های اضافه‌شده در بررسی دوم

تست helper درخت، total ریشه‌ها، فرزندان چندسطحی، ریشهٔ یتیم در scope مجاز،
صفحهٔ خارج از محدوده و عدم خواندن شاخه‌های دیگر اضافه شد. قرارداد پاسخ دیکشنری
و ترجمه/گردکردن گروه‌بندی رتبه‌بندی نیز پوشش داده شده است. **این تست‌های دات‌نت
هنوز اجرا نشده‌اند**؛ syntax check جای compilation یا تست EF translation نیست.
مرتب‌سازی رشته‌ای و precision/rounding، به‌ویژه در SQLite و collationهای متفاوت
SQL Server، همچنان به تست واقعی provider نیاز دارند.
