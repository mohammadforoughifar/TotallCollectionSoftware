# طراحی ۵ ماژول تکمیلی ERP — جایگذاری

> پیش‌نمایش تعاملی: `erp-preview/index.html`

این سند فقط **جا** و **مرز ماژول** را قفل می‌کند. پیاده‌سازی بعد از تأیید همین نقشه شروع می‌شود.

---

## اصل جاگذاری

هر قابلیت کنار ماژولی می‌نشیند که **سند حسابداری یا گردش نقد** را صادر می‌کند.
منوی جدا بیرون از گروه ERP ساخته نمی‌شود. ماژول موازی برای چیزی که همین حالا هست (دفتر چک، تنخواه به‌عنوان نوع حساب) ساخته نمی‌شود — گسترش داده می‌شود.

جریان فعلی سیستم:

```
انبار (Inv) → حسابداری (Acc) → فاکتور (Fac) → خزانه (Trs)
                  ↑ ابعاد تحلیلی / بودجه / دارایی ثابت
```

---

## ۱) تخصیص هزینه و بهای تمام‌شده

| | |
|---|---|
| منو | `ERP → حسابداری — عملیات → تخصیص هزینه` · `بهای تمام‌شده` |
| گزارش | `ERP → حسابداری — گزارش‌ها → گزارش بهای تمام‌شده` |
| مسیر | `/acc/costing` · `/acc/cogs` · `/acc/reports/cogs` |
| پیشوند | `Cst` |
| تکیه بر | `AccDimensions` (مرکز/پروژه)، کاردکس `OutCost`، استهلاک دارایی ثابت |

**چرا اینجا؟** خروجی آرتیکل Acc روی ابعاد تحلیلی است، نه سند انبار جدید.

گردش: استخر سربار دوره → مبنای سرشکن (ساعت ماشین / نفر-ساعت / وزن) → تخصیص به مرکز/پروژه → جذب به کالا/سفارش → COGS.

قواعد: فقط دوره باز · جمع تخصیص = استخر · سند با `Source = CostAlloc` · برگشت تخصیص سند را حذف می‌کند.

## ۲) تنخواه و هزینه سفر

| | |
|---|---|
| منو | `ERP → خزانه‌داری → تنخواه‌گردان` · `هزینه سفر` |
| مسیر | `/trs/petty-cash` · `/trs/travel` |
| پیشوند | `Ptc` / `Trv` |
| تکیه بر | `TrsAccount.Kind = PettyCash` (از قبل هست) |

**چرا خزانه نه «عملیات / هزینه‌ها»؟** صفحه `/expenses` سند Acc نمی‌زند. تنخواه باید روی حساب تنخواه بنشیند، سقف داشته باشد و با سند پرداخت تسویه شود.

گردش تنخواه: درخواست → تصویب → پرداخت از خزانه → ثبت فیش → تسویه و شارژ مجدد.

گردش سفر: درخواست → تصویب مدیر → سفر → فیش‌ها → تسویه (تنخواه یا خزانه). لینک اختیاری به مأموریت HR — پول اینجا ثبت می‌شود، حضور آنجا.

صفحهٔ هزینه‌های متفرقه در «عملیات» باقی می‌ماند.

---

## ۳) چک و بانک (سامانه کامل)

| | |
|---|---|
| منو | همان `خزانه‌داری → دفتر چک` + سه آیتم جدید |
| مسیر | `/trs/cheques` (گسترش) · `/trs/sayad` · `/trs/bank-reconcile` |
| تکیه بر | `TrsCheque` / `ChequeStatus` / `SayadId` / `TrsAccounts` |

**چرا ماژول جدید نیست؟** چرخه واگذاری/وصول/برگشت/خرج همین حالا در دفتر چک پیاده شده. لایهٔ کامل:

- کانبان گردش و تقویم سررسید روی همان رکوردها
- استعلام/ثبت صیاد روی فیلد موجود `SayadId`
- مغایرت‌گیری بانکی: صورت‌حساب بانک در برابر گردش `TrsAccount` (کارمزد، چک در جریان، واریز درگاه)

منطق «چک تا وصول روی مانده بانک اثر ندارد» حفظ می‌شود.

---

## ۴) تسویه حساب طرف حساب

| | |
|---|---|
| منو | **زیرگروه جدید** `ERP → طرف حساب و تسویه` — بین فاکتور و خزانه |
| مسیر | `/erp/parties/statement` · `/erp/parties/aging` · `/erp/parties/settle` |
| پیشوند | `Stl` |
| تکیه بر | `Party`، `FacInvoice`، `TrsVoucher`، حساب‌های دریافتنی/پرداختنی Acc |

**چرا زیرگروه جدا؟** هم فاکتور می‌سازد هم سند خزانه. اگر داخل فاکتور برود خزانه گم می‌شود؛ اگر داخل خزانه برود صورت‌حساب فروش گم می‌شود.

تکمیل `/trs/vouchers/settle/{invoiceId}` فعلی: چند فاکتور همزمان + تهاتر بدهکار/بستانکار + aging.

چک تا وصول در صورت‌حساب به‌صورت «اسناد در جریان» جدا دیده می‌شود.

---

## ۵) درگاه پرداخت آنلاین

| | |
|---|---|
| منو | `خزانه‌داری → پرداخت آنلاین` · `تنظیمات درگاه` |
| مسیر | `/trs/payments` · `/trs/gateways` |
| پیشوند | `Pay` |
| تکیه بر | `TrsVoucher` (Receipt + PayMethod.Card) · `TrsRule.FeeAccountId` |

هر پرداخت موفق = سند دریافت + کاهش مانده فاکتور. کارمزد درگاه روی حساب کارمزد خزانه.

تا اتصال واقعی درگاه: لینک پرداخت + ثبت دستی رسید + وضعیت callback.

## ترتیب پیاده‌سازی پیشنهادی

1. طرف حساب و تسویه (بیشترین ارزش روی Fac+Trs موجود)

4. درگاه (سند دریافت موجود)
5. تخصیص و COGS (نیاز به قواعد حسابداری دقیق‌تر)
