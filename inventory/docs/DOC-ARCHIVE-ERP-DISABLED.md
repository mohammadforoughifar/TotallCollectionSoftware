# غیرفعال‌سازی اتصال آرشیو به ERP

تاریخ: ۲۰۲۶-۰۹-۱۴ — تغییر در کد محلی؛ بدون استقرار یا تغییر دیتابیس عملیاتی.

## محدوده

- کارت اتصال، مودال افزودن/حذف اتصال، نشان تعداد اتصالات و فیلتر ERP از آرشیو حذف شده‌اند.
- پنل آرشیو و دکمه/تب/مودال ورود به آن از پنل منابع انسانی، پروفایل پرسنل، فرم فاکتور، فرم سند انبار، فهرست تجهیزات IT، کارفرمایان و فهرست پروژه‌ها حذف شده‌اند. پیوست‌ها و مدارک بومی هر بخش باقی هستند.
- کامپوننت `DocArchiveEntityPanel` و متدهای اتصال در سرویس کلاینت حذف شده‌اند.
- ارتباط بین خود مدارک (`DocumentLinks`) و دستورکارهای تمدید با `SourceModule = Document` تغییری نکرده‌اند. اشتراک داخلی، مقایسه، صف OCR و صفحه‌بندی نیز باقی هستند.

## APIهای بازنشسته

درخواست معتبر و مجاز به این مسیرها به‌جای اجرای عملیات، پاسخ JSON با کد HTTP **410 Gone** و `code = DOC_ARCHIVE_ERP_DISABLED` می‌گیرد:

| متد | مسیر |
|---|---|
| GET | `/api/doc-archive/entity-links/{module}/{entityId}` |
| POST | `/api/doc-archive/entity-links` |
| DELETE | `/api/doc-archive/entity-links/{id}` |
| POST | `/api/doc-archive/entity-links/quick-create` |
| GET | `/api/doc-archive/entity-lookups/{module}` |

احراز هویت و اعتبارسنجی استاندارد ASP.NET همچنان قبل از اکشن اجرا می‌شود؛ درخواست نامعتبر یا غیرمجاز ممکن است 400/401/403 بگیرد. اکشن‌های بازنشسته هیچ خواندن یا نوشتنی در دیتابیس انجام نمی‌دهند؛ حتی مدیر نمی‌تواند اتصال ایجاد/حذف یا مدرک متصل ایجاد کند. نگه‌داشتن مسیرها مانع افتادن درخواست کلاینت قدیمی روی fallback صفحه SPA می‌شود.

هر دو مسیر `/search` و `/search-page` مقدار غیرخالی `LinkedModule` یا مقدار غیرnull `LinkedEntityId` را صریحاً با 410 رد می‌کنند، نه اینکه فیلتر را نادیده بگیرند و مدارک نامرتبط برگردانند.

در لیست، جستجو و جزئیات، متادیتای اتصال دیگر از دیتابیس خوانده نمی‌شود. فیلدهای DTO صرفاً برای سازگاری باقی‌اند: `EntityLinkCount = 0`، `LinkedModules = []`، `EntityLinks = []`.

خروجی ZIP همچنان پوشه‌ها، فایل‌ها، تگ‌ها و شناسنامه را دارد؛ ستون ERP از شناسنامه حذف و تعداد ستون‌ها از ۱۱ به ۱۰ تبدیل شده است. ستون دهم تعداد پیوست است.

## حفظ داده و استقرار

جدول، مدل، نگاشت و ردیف‌های تاریخی `DocEntityLinks` حفظ شده‌اند. هیچ migration حذف جدول یا پاک‌سازی داده برای این تغییر وجود ندارد. گزارش‌های تاریخی عملیات نیز پاک نشده‌اند. این به معنی فعال بودن اتصال نیست؛ رابط و API عملیاتی آن بازنشسته‌اند.

برای اعمال تغییر باید API و کلاینت جدید با هم منتشر شوند؛ کش کلاینت قدیمی نیز تازه شود. این تغییر به‌تنهایی ارتقای اسکیما ندارد، اما قابلیت‌های قبلی توسعه آرشیو ارتقای افزایشی خود را دارند؛ به [سند توسعه آرشیو](DOC-ARCHIVE-EVOLUTION.md) مراجعه کنید. بازگرداندن نسخه قدیمی سرور اتصال را دوباره فعال می‌کند، چون داده‌های آن عمداً حفظ شده‌اند.

## راستی‌آزمایی محلی

- بیلد کامل `inventory/Inventory.sln`: موفق، ۰ خطا، ۱۲ هشدار موجود در بخش‌های دیگر در اجرای نهایی.
- تست توسعه آرشیو: **۳۴/۳۴**؛ شامل ۱۳ مورد جدید بازنشستگی ERP، حفظ ردیف‌ها، نبود عملیات DB در اکشن‌های بازنشسته، رد فیلتر قدیمی، متادیتای خالی، حفظ ارتباط بین مدارک و شناسنامه ZIP.
- یکی از تست‌ها کنترلرهای واقعی را روی HTTP محلی با احراز هویت آزمایشی اجرا و هر پنج مسیر را بررسی می‌کند؛ این تست اجرای محیط عملیاتی یا کل pipeline تنظیم‌شده در `Program.cs` نیست.
- تست دستورکار: **۲۶/۲۶**، از جمله عدم تکرار نامناسب و دسترسی‌ها. تست‌های تمدید خودکار نیز در مجموعه آرشیو باقی‌اند.
- هر سه مجموعه مرورگر آرشیو، توسعه آرشیو و دستورکار با Blazor کامپایل‌شده و API شبیه‌سازی‌شده در دسکتاپ/موبایل موفق، بدون page error. حتی با متادیتای ERP در پاسخ آزمایشی، کارت/نشان آن ظاهر نمی‌شود؛ هیچ درخواست اتصال/lookup ERP ارسال نمی‌شود.
- هفت فرم سایر ماژول‌ها در بیلد کامل بررسی شده‌اند؛ آزمون تعاملی مرورگر جداگانه برای تک‌تک آن‌ها اجرا نشده است.
- تست‌ها از SQLite موقت استفاده کرده‌اند؛ SQL Server عملیاتی و استقرار واقعی بررسی نشده‌اند. کد push یا deploy نشده است.
